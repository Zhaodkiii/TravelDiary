# 订阅重构实施记录

## 当前代码

正常 Pro 页面统一调用 SubscriptionService；删除 BillingStore 的订阅购买、恢复与持久化 membershipPending 流程。钻石业务仍由 BillingStore 负责。

商品直接通过 StoreKit 获取本地化价格，不依赖会员接口。购买／恢复使用返回的 CustomerInfo 更新客户端；RevenueCat customerInfoStream 和本地 Transaction.updates 更新同一会员模型。服务器权益单独同步，最多三次；失败不把已购买状态退回“正在确认”。等待批准与正在付款分开，恢复购买持续可用。

Debug 的 --local-storekit Scheme 使用 TravelDiary.storekit 和正常页面；真实沙盒与生产使用 RevenueCat。Debug/Release 的后端配置保持编译期选择，没有 TRAVELDIARY_BACKEND。

服务端新增 subscription-bootstrap，不创建钻石钱包。钱包改为业务需要时初始化。会员查询增加共享 Redis 合并和限流退避，保留失败前的可靠快照，最多容忍24小时且不超过已验证有效期；退款、到期事件仍立即使旧快照失效。订阅详情分页读取，匹配商店环境后授权。赠券预留30分钟超时释放，取消购买释放预留；既有首次购买事件幂等发券路径保留。

## 尚不能宣称完成的事项

- RevenueCat 控制台 Restore Behavior 尚未重新确认；登录已有账号不会自动合并另一个账号的订阅、AI 消耗和赠券。不能依靠客户端修改安全解决跨账号归属。
- 真实交易前仍需要 AppTransaction 验证和服务端订阅身份初始化；已拆除钱包初始化，但尚未改为完全离线的 RevenueCat 身份创建。
- 年付承诺赠礼仍需付款前成功预留，接口失败会明确阻止这次带赠礼购买；尚未新增独立补偿队列。
- 本地 StoreKit 不解锁服务器 AI 额度／素材／赠券；需要沙盒完成这些服务端功能的端到端验收。
- 本地运行仍由 Scheme StoreKit 文件与 --local-storekit 配对；不能只依赖 DEBUG 判断交易来源。

因此这是已落地的核心链路重构和服务端修正，不代表审计报告全部21项都已关闭。
