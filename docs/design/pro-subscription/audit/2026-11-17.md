# 订阅流程代码审计与简化方案

日期：2026-11-17。范围：当前本地 iOS 与相邻 SparkService 代码、Apple/RevenueCat 官方文档。未修改业务代码、未发版、未再次核实线上控制台配置；未执行真实购买。代码风险不等于已经发生的线上事故。

## 当前链路

真实沙盒/生产：设备或正式账号 → AppTransaction 验证 → billing/bootstrap（创建计费身份、钱包、12 小时会话）→ RevenueCat configure/logIn → 服务端会员查询（RC customer + subscriptions）→ RC offerings → Pro 页面 → 年付赠券预留 → 再查会员 → 持久化 pending=true → RC purchase → 再查服务端会员 → 刷新 AI 额度。

本地：Debug Scheme --local-storekit + TravelDiary.storekit → 相同 Pro 页面 → StoreKit Product.purchase → 验证 xcode 交易 → Transaction.currentEntitlements → 本地 MembershipStatus。恢复使用 AppStore.sync；交易监听仅本地分支安装。此链路不授予服务器 AI/内容/赠券权益。

环境是三个维度：编译 Debug/Staging/Release；服务开发/生产；商店 Xcode/Sandbox/Production。不能互相等同。当前 Debug 默认开发 API，Staging/Release 生产 API；线上可处理真实沙盒和生产交易。本地标记只存在于 Debug Run，不应进入发布包。

## 已确认的问题和代码证据

### 高优先级

1. **pending 可永久卡住**。BillingStore.purchaseMembership 在调用 SDK 前保存布尔值；catch 只清除 purchaseCancelledError。明确失败、待批准、SDK/网络异常混用一个状态。refreshMembership 仅 active && fresh 清除，已到期或没有权益不会清除。恢复在 fresh 时又无条件清除，语义相互矛盾。需要有交易关联的状态机与有界对账，不能按时间直接当成功或当失败。
2. **忽略购买/恢复返回的 CustomerInfo**。购买只读取 userCancelled；恢复丢弃返回值，完全等自有后端再次 GET RevenueCat。代码搜索未发现 PurchasesDelegate/customerInfoStream 接入。导致 SDK 已有明确权益但 UI 仍待确认。应以 SDK CustomerInfo 支撑客户端状态，同时服务端独立验证服务器权益。
3. **购买入口前置依赖过多**。商品加载必须先 AppTransaction、bootstrap、RC 登录、服务端权益状态；bootstrap 还创建钱包数据。展示商品不应依赖钻石钱包和订阅同步成功。身份准备应提前完成，商品与状态并行加载，恢复按钮应可用。
4. **环境身份错误会冻结整个钱包**。billing/tasks.py 对 event environment 不一致直接 quarantine BillingIdentity。AppTransaction 表示 App 环境，不能用它替代每笔交易的环境依据。购买恢复/收据跨身份行为需核验，环境不一致应隔离事件并调查，避免错误冻结无关有效权益。
5. **恢复与账号迁移没有闭环**。账号服务支持新身份原地升级；已有账号登录切换 account_id，仅记录旧设备账号。TRANSFER 只失效双方会员缓存，不迁移额度和赠券。实际行为依赖 RC Restore Behavior，需明确策略及跨设备验收，不能假设 logIn 自动合并两个自定义 ID。
6. **服务端会员新鲜度与有效性混合**。membership.is_active 在验证超过 1 小时后直接 false，即使订阅到期日仍在未来；ai_production.entitlement 遇 needs_sync 即拒绝确定计划。普通续订/取消回调短暂失效也可能暂停 AI。应区分有效、过期、撤销、验证暂不可用，并对已验证未到期权益制定有限容错策略；退款等撤权不能忽略。
7. **年付赠券成了支付必经依赖**。BillingViews.purchase 必须先预留成功；取消才明确释放，多类失败/进程退出未闭环，预留可能长期占用。需要预留过期与幂等确认。赠礼异常时应付款前明确展示可选处理，不能暗中取消承诺。

### 中优先级

8. **读接口强制同步过重**。客户端会员刷新用 POST force=True；服务端串行调用两个 RC API，每个超时 15 秒。进入设置、进入购买页、前台恢复、付款前后可能重复查询。采用缓存读取、请求合并、购买/恢复后按需强制对账及退避。
9. **会员详情请求失败也标为 fresh**。membership.refresh 在 customer 成功而 subscriptions 请求失败/分页未完整时仍将 needs_sync 清除，并覆写 product、续订状态为 unknown。权益快照和续订详情应分开记录新鲜度，失败保留最后可靠值。
10. **分页处理不完整**。active_entitlements 后续页只在没找到 until 时返回失败；subscriptions 有 next_page 就放弃详情。应完整分页或明确单订阅约束，不能用缺失详情当确定无数据。
11. **新客户 404 没有区分**。provider.customer 非 200 一律返回 refresh=False；若 RC 返回尚未创建客户的 404，页面可能永远 stale，阻止首次购买。需验证实际初始化时序并定义不存在客户的处理，不能把所有网络错误视作未订阅。
12. **后台刷新队列缺少公平性与退避**。tasks.process_pending 取前 100 个按 verified_at 排序；失败保留旧时间，可长期占据前列。没有按身份 next_retry_at；provider Retry-After 没被会员刷新采用。
13. **多处布尔值与字符串拼接状态**。busy、processing、loading、membershipPending、sync_state、active、appStoreVerificationFailed 共同控制页面。stale 或 pending 就跳“我的 Pro”，即使从未买过；难区分加载失败和付款待处理。
14. **计费会话跨模块耦合**。AI quota 依赖 BillingStore.ready，并按是否已有 bootstrapInfo 决定是否携带 X-Billing-Session；无头时服务端只选择生产身份。沙盒会员在初始化前可能显示免费额度。应该明确环境上下文，不能让调用顺序决定权益。
15. **本地状态模拟不完整**。refreshLocalMembership 将无有效交易写为 inactive，不区分未购买、到期、退款；续订状态固定 unknown；AI included 固定 true，但服务端权益未改变。状态模型应标明来源与可用能力，测试结果不可冒充完整服务器解锁。
16. **本地模式开关可能与配置脱节**。--local-storekit 和 Scheme StoreKit 配置是两个设置；强制本地标记会绕过环境探测，只有付款返回后才检查交易环境。应保持成对配置验证，并在错误配置时阻止误走真实购买；另设真实沙盒 Scheme 可减少误操作。
17. **本地交易监听生命周期不完整**。监听在首次本地会员刷新后才启动；没有显式启动/停止策略，账号切换使用当前 owner。需要定义本地 Apple 购买在多 App 账号间的语义；使用 App 生命周期协调监听与重新计算到期。
18. **错误诊断覆盖不完整**。本地环境探测在 refreshMembership 的 do/catch 外；恢复错误和部分 SDK 失败没有统一诊断。类型/domain/code 不足以分辨所有 BillingFailure。需要稳定业务错误码、阶段、请求 ID，无敏感正文。
19. **会员和钱包共享 busy/identityTask/sdkTail**。串行化身份切换是正确的，但钱包业务对订阅展示的阻塞应拆开；保留购买操作互斥及账号 generation 校验。
20. **赠礼使用硬编码 member**。campaigns/tasks 部分判断固定 entitlement_ids 包含 member，会员查询使用配置项 REVENUECAT_MEMBER_ENTITLEMENT_ID。修改配置会导致会员生效而赠礼不发。
21. **首购与恢复跨账号去重仍需验证**。年付 grant_key 按交易摘要去重，活动参与按 account 去重；切换账号/转移后的优惠券归属与首购限制需明确。AI 窗口也按 account 记账，自动转移不能顺便重置已消费额度。

## 已有正确基础

Apple 本地化价格；月付年付同权益等级；游客设备账号购买；恢复与订阅管理入口；服务端秘密不在客户端；webhook 鉴权、持久化、事件去重；重新查询权威状态而非盲信旧事件；generation 校验及 SDK 身份串行；服务器拒绝本地伪造权益。应保留这些约束。

## 推荐简化架构

UI 保留一套。SubscriptionService 负责商品、购买、恢复、状态监听；两个实现 LocalStoreKit（仅 Debug）与 RevenueCat（真实沙盒/生产）。View 不持有 RC.Package 或调用赠礼预留，统一 SubscriptionProduct / SubscriptionState。

订阅状态：unknown/loading、notSubscribed、purchasing、awaitingApproval、active、expired、revoked。服务端能力同步状态另列 syncing/ready/failed；错误为可恢复信息，不是永久会员状态。

常规流程：进入 Pro → 展示商品与已知状态 → 用户购买 → Apple 确认 → RC 返回 CustomerInfo → 客户端立即展示明确结果 → 服务端验证同步 AI/内容/赠礼。已付款但服务器暂未就绪时明确“已订阅，制作服务正在同步”，限制尚未获授权的服务端功能，有限自动重试。

后端职责：可信验证、业务授权、配额、赠券、审计；webhook 更新+主动对账补偿。客户端上报 userID/交易线索不能直接授予权益。只需轻量稳定计费身份接口，不必在加载购买页时创建钻石钱包。

不要直接改成完全另一套支付框架。已有 RevenueCat 集成可继续使用，不必再做第二套生产收据验证系统；AppTransaction 校验如因环境隔离需要保留，应移出商品展示关键路径。

## 实施顺序与验收

1. 状态机、pending 恢复、消费 CustomerInfo、监听 SDK 更新、错误提示。
2. 拆商品加载与后台授权，降低重复查询，缓存/退避/失效策略。
3. 收敛本地适配器，统一真实 UI；赠礼移入服务层并补偿。
4. 确定恢复归属策略，测试新游客、绑定新账号、已有账号登录、重装、多设备。
5. 真实沙盒测试取消、待批准、断网、支付后杀进程、续订、到期、退款、退款撤销、宽限期、账号切换及赠券失败。
6. Release 检查无本地模式入口；生产配置只读核对后再决定发布。

本地测试不代替沙盒端到端测试；模拟器编译成功不等于购买闭环已验收。
