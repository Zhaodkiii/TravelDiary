## 3. Web 当前协议与业务语义

### 3.1 Web 当前客户端消息类型

根据 [unified-ws.ts](/Users/hua/Documents/project/DeepTutor/DeepTutorSerevr/web/lib/unified-ws.ts)，Web 当前实际发送的消息类型包括：

| 类型 | 用途 |
| --- | --- |
| `start_turn` / `message` | 发起一轮对话 |
| `subscribe_turn` | 补追某个 turn 的事件 |
| `subscribe_session` | 补追某个 session 的事件 |
| `resume_from` | 重连后续传某个 turn |
| `cancel_turn` | 停止当前生成 |
| `regenerate` | 对当前 session 重新生成 |
| `submit_user_reply` | 对 ask-user 中断点补答 |

这说明 iOS `server` 模式当前的协议方向是对的，而 `local` 模式并不是要重新发明“另一种对话 API”，而是要在本地复用同样的领域语义。

### 3.2 Web 当前事件类型

根据 [unified-ws.ts](/Users/hua/Documents/project/DeepTutor/DeepTutorSerevr/web/lib/unified-ws.ts)，Web 当前消费的事件类型包括：

| 事件 | 作用 |

| `tool_call` | 工具调用开始 |
| `tool_result` | 工具调用返回 |
| `progress` | 中间进度 |
| `sources` | 来源引用 |
| `result` | 阶段性结果 |
| `error` | 错误 |
| `session` | session / turn 绑定信息 |
| `session_meta` | session 元数据，如标题 |
| `done` | 一轮 turn 收口 |

### 3.3 Web 当前 session REST 语义

根据 [session-api.ts](/Users/hua/Documents/project/DeepTutor/DeepTutorSerevr/web/lib/session-api.ts)，Web 当前的 session 语义包括：

| REST 能力 | 语义 |
| --- | --- |
| `listSessions()` | 拉会话列表 |
| `getSession()` | 拉单个会话详情 |
| `updateSessionTitle()` | 改标题 |
| `deleteSession()` | 删除会话 |
| `updateBranchSelection()` | 更新某个分支选择 |

这说明：

- Web 把“会话实体”与“turn 流事件”拆开了。
- iOS `local` 模式如果要对齐 Web，不应该在没有 session store 的前提下直接接本地模型流。
- 本地模式必须先有一层本地 session store，才能对齐 Web 的 session list / detail 基础语义。

### 3.4 Web 当前恢复语义

根据 [unified-ws.ts](/Users/hua/Documents/project/DeepTutor/DeepTutorSerevr/web/lib/unified-ws.ts)，Web 重连时会：

1. 保存 `activeTurnId` 和 `lastSeq`。
2. 连接恢复后自动发送 `resume_from`。
3. 继续接收未完成 turn 的流。

这对 iOS 的重要结论是：

- `server` 模式应继续保留这种恢复语义。
- `local` 模式不能伪装成这种恢复语义。
- `local` 模式恢复只能是“从本地缓存重建状态”，而不是“向 `DeepTutorSerevr` 追流”。

## 4. iOS 当前业务流程

### 4.1 页面进入流程

根据 [AIChatViewModel.swift](/Users/hua/Documents/project/DeepTutor/SupportClient/SupportClient/Projects/Features/AIChat/Application/AIChatViewModel.swift)，当前页面进入流程是：

```text
AIChatEntryView
  -> AIChatRootView
  -> AIChatViewModel.onAppear()
  -> connectIfNeeded()
  -> restoreIfNeeded()
```

这意味着：

- 进入页时一定会走统一 `repository`，但真正连接的是当前激活模式对应的仓储。
- `AIChatViewModel.onAppear()` 已经会比较 `lastKnownRuntimeMode`，一旦模式变化就 `disconnect + reset state + 清空 sessions`。
- 进入页时默认仍会尝试从 resume snapshot 恢复，但恢复下钻路径已经受统一仓储控制。

如果要继续做双后端切换，关键不是重写 `onAppear()`，而是把 `restoreIfNeeded()` 在 `local` 模式下的 replay 语义补得更完整。

### 4.2 当前发送消息流程

当前 `sendMessage()` 流程可以概括为：

```text
1. 清理 composerText
2. optimistic append user message
3. 如果当前连接未 ready，则 repository.connect()
4. resolveLLMSelection()
5. 构造 AIStartTurnPayload.chatTurn(...)
6. repository.startTurn(payload)
7. 等待服务端事件流
8. reducer 更新 state
```

关键结论：

- optimistic user bubble 已经做好了。
- iOS 当前消息发送主链路并没有绑死在某个具体页面，而是绑在仓储协议上。
- 这给 `local` 模式切换留下了很好的落点。
- 但当前 `resolveLLMSelection()` 只是针对 `DeepTutorSerevr` 的 `llm_selection` 补充；如果进入 `local` 模式，真正要消费的模型配置必须改为走 `AIConfigCenter.resolve(for: .chat)`。

### 4.3 当前会话列表流程

当前 `loadSessions()` 流程是：

```text
loadSessions()
  -> loadSessionsUseCase.execute()
  -> repository.listSessions()
  -> sessions = result
```

当前 `openSession(_:)` 流程是：

```text
openSession(session)
  -> loadSessionDetailUseCase.execute(sessionID)
  -> state.activeSession = detail.session
  -> state.messages = detail.messages
  -> repository.saveResumeSnapshot(...)
  -> resumeTurnUseCase.execute(sessionID, accountID)
```

关键结论：

- 当前 iOS 会话列表逻辑是典型的“详情 + 恢复”双步骤。
- `local` 模式必须给出本地版 `listSessions` 和 `loadSession`，否则列表 UI 无法对齐 Web。

### 4.4 当前恢复流程

当前 `restoreIfNeeded()` 流程是：

```text
repository.loadResumeSnapshot(accountID)
  -> loadSessionDetailUseCase.execute(sessionID)
  -> applyResumeSnapshot(snapshot.pendingEvents)
  -> resumeTurnUseCase.execute(sessionID, accountID)
```

关键结论：

- `restoreIfNeeded()` 当前会统一走 `repository.loadResumeSnapshot(accountID)`。
- 随后 `loadSessionDetailUseCase`、`resumeTurnUseCase` 也都会继续走当前激活仓储。
- 对 `server` 模式，这会落到服务端详情与 active turn 检查。
- 对 `local` 模式，`loadSession(id:)` 已经是本地实现，`checkActiveTurn(sessionID:)` 当前是 no-op。

所以更准确的判断是：

- `local` 模式当前不会因为 `resumeTurnUseCase` 而自动追服务端 active turn。
- 但 `local` 模式的恢复仍然偏“加载本地 session + 空检查”，还没有形成完整的 pending event replay 语义。

### 4.5 当前 `local` 骨架业务流程

根据 [LocalAIChatRepository.swift](/Users/hua/Documents/project/DeepTutor/SupportClient/SupportClient/Projects/Features/AIChat/Infrastructure/LocalAIChatRepository.swift) 和 [LocalAIChatRuntime.swift](/Users/hua/Documents/project/DeepTutor/SupportClient/SupportClient/Projects/Features/AIChat/Infrastructure/LocalAIChatRuntime.swift)，当前本地模式已经形成一条最小骨架：

```text
AIChatRoutingRepository.activate(accountID)
  -> LocalAIChatRepository.activate(accountID)

进入页面
  -> LocalAIChatRepository.connect()
  -> lastAuthMode = iosLocalRuntime
  -> connectionState = ready

发送消息
  -> ensureSession(existingID, accountID, title)
  -> appendMessage(userMessage)
  -> 读取本地 history
  -> LocalAIChatRuntime.runTurn()
  -> 发出 session / thinking / content / done / error
  -> append assistant message to local session store

打开本地会话
  -> listSessions()
  -> loadSession(id)
```

这说明两件事：

1. `local` 模式已经不是空白，它已经能验证“切换 -> 进入页 -> 发消息 -> 出内容 -> 会话入列表”这条最小交互路径。
2. 当前差的不是 session 骨架，而是把“真实 API 流、GGUF/local endpoint、本地恢复 replay、更多事件类型”补成和 Web 更接近的一致语义。

### 4.6 当前 `local` 真实执行器分层

根据真实代码，当前 `local` 不是单一 stub，而是下面这条链：

```text
AIChatViewModel.sendMessage()
  -> AIChatRoutingRepository.startTurn(payload)
  -> LocalAIChatRepository.startTurn(payload)
  -> LocalAIChatSessionStore.ensureSession / appendMessage / messages(history)
  -> LocalAIChatRuntime.runTurn(...)
  -> AIConfigCenter.resolve(for: .chat)
  -> if endpoint.scheme != "local":
       LocalAIChatStreamClient.streamCompletion(...)
     else:
       streamStub(...)
  -> LocalAIChatStreamAdapter
  -> AIStreamEvent(session / thinking / content / done / error)
  -> AIChatEventReducer
  -> LocalAIChatSessionStore.upsertAssistantMessage(...)
```

这条链已经说明三件事：

1. chat 场景模型解析已经统一收口到 `AIConfigCenter.resolve(for: .chat)`。
2. OpenAI-compatible 流式 API 已经能在 `local` 模式下被直接消费。
3. 当前真正未完成的是 `endpoint.scheme == local` 时的直接本地推理执行器，以及更丰富的事件语义。

## 5. `local` 模式应该怎么对齐 Web

### 5.1 不是照抄 UI，而是照抄语义

`local` 模式需要对齐 Web 的不是布局，而是这些基础语义：

- session list 能浏览。
- session detail 能加载。
- 首条消息会进入某个 session。
- optimistic user row 先出现。
- assistant 内容逐步流出。
- turn 最终会 `done` 收口。
- 错误时上下文不丢。
- 恢复时能回到用户上次看到的会话状态。

### 5.2 `local` 模式主流程

推荐的 `local` 主流程：

```text
AIChatEntryView
  -> AIChatRootView
  -> AIChatViewModel.onAppear()
  -> if runtimeMode == local:
       localRepository.connect()
       load local snapshot + local session detail

用户发送
  -> sendMessage()
  -> optimistic append user row
  -> localRepository.startTurn(payload)
  -> 本地 session store 写入 user message
  -> AIConfigCenter.resolve(for: .chat)
  -> 本地 AI runtime 开始跑
  -> 本地 stream adapter 生成 AIStreamEvent
  -> reducer 更新 state
  -> UI 渲染
```

### 5.3 `local` 模式会话流程

推荐的 `local` 会话流程：

```text
打开会话列表
  -> localRepository.listSessions()
  -> read local session summaries

点击会话
  -> localRepository.loadSession(id)
  -> state.activeSession = local session
  -> state.messages = local messages

恢复续聊
  -> localRepository.loadResumeSnapshot(accountID)
  -> localRepository.loadSession(id)
  -> replay local cached events / pending snapshot
```

这里必须写死：

- 不能调 `DeepTutorSessionAPI.listSessions`
- 不能调 `DeepTutorSessionAPI.loadSession`
- 首期不能依赖 `resume_from`
- 首期不能依赖 `subscribe_turn`
- 首期不能依赖 `subscribe_session`

### 5.5 `local` 模式的模型消费必须接入现有场景系统

项目内已经存在一套真实的统一模型消费链：

```text
AISettingsSnapshot
  -> scenarioBindings
  -> scenarioModelSources
  -> trialModelPolicy
  -> AIConfigCenter.resolve(for: scenario)
  -> ScenarioPolicyResolver.resolve(...)
  -> AIResolvedConfig
  -> AIClientFactory / 具体执行器
```

根据 [AIConfigCenter.swift](/Users/hua/Documents/project/DeepTutor/SupportClient/SupportClient/Projects/Core/AI/AIConfigCenter.swift) 和 [ScenarioPolicyResolver.swift](/Users/hua/Documents/project/DeepTutor/SupportClient/SupportClient/Projects/Core/AI/ScenarioPolicyResolver.swift)，当前 chat 场景的模型解析优先级已经固定为：

1. 显式首选模型 `preferredModelName`
2. `runtimeOverride`
3. bundle 默认解析链

这意味着 `local` 模式必须遵守三个要求：

1. 不允许在 `LocalAIChatRepository` 里直接保存一套新的 chat endpoint/model/apiKey。
2. 不允许在 `AIChatViewModel` 里单独拼“本地 chat 模型选择”。
3. 必须先拿到 `AIResolvedConfig`，再决定由本地 runtime 如何执行。

### 5.6 `local` 模式模型消费的推荐流程

```text
AIChatViewModel.sendMessage()
  -> runtimeMode == local
  -> LocalAIChatRepository.startTurn(payload)
  -> LocalAIChatRuntime.runTurn(...)
  -> AIConfigCenter.resolve(for: .chat)
  -> LocalAIChatStreamClient / stub fallback
  -> LocalAIChatStreamAdapter -> AIStreamEvent
```

关键点：

- `local` 模式和 `server` 模式的差异在“执行器”。
- `local` 模式和 `server` 模式不应在“chat 场景模型解析”这里分叉两套规则。

## 5.7 业务流程对齐总图

下面把 Web、iOS `server`、iOS `local` 三条主流程并排对齐，避免后面只对齐 API、不对齐业务手感。

### 5.7.1 首次进入对话页

| 阶段 | Web | iOS `server` | iOS `local` |
| --- | --- | --- | --- |
| 页面初始化 | 初始化 composer、session panel、WS client | `AIChatViewModel.onAppear()` | `AIChatViewModel.onAppear()` |
| 连接准备 | `UnifiedWSClient.connect()` | `repository.connect()` -> `AIChatRepository.connect()` | `repository.connect()` -> `LocalAIChatRepository.connect()` |

| 用户可见结果 | 可继续当前会话或进入 ready | ready / reconnecting / waitingForUser | ready / 从本地缓存恢复的 ready |

### 5.7.2 首条消息建会话

    accountID: Int64,
    sessionID: String,
    turnID: String,
    userInput: String,
    history: [AIChatMessage],
    emit: @Sendable (AIStreamEvent) async -> Void
) async -> LocalAIChatRunResult {
    var adapter = LocalAIChatStreamAdapter()
    await emit(adapter.makeSessionEvent(sessionID: sessionID, turnID: turnID))
    await emit(adapter.makeThinkingEvent(sessionID: sessionID, turnID: turnID, content: "正在生成回复"))

    let resolved = try? await aiConfigCenter.resolve(for: .chat)
    if let resolved, resolved.endpoint.scheme != "local" {

            history: history,
            userInput: userInput,
            sessionID: sessionID,
            turnID: turnID,
            adapter: &adapter,
            emit: emit

        return await streamStub(
            userInput: userInput,
            resolved: resolved,
            sessionID: sessionID,
            turnID: turnID,

}

## 9.4 业务流程对齐的实现要点

把 Web 语义真正落到 iOS 上，最容易出错的是下面 6 个点：

| 点位 | Web 的真实语义 | iOS 应如何对齐 |
| --- | --- | --- |
| session 创建时机 | 首条消息触发隐式建会话 | `server` 等服务端 session，`local` 先本地建 session |
| optimistic row | 先看到 user message，再等 assistant 流 | 两种模式都必须先写 user row |
| turn 收口 | `done` 之后固化 assistant 消息 | 两种模式都必须经由 reducer 收口 |
| cancel 语义 | 停止当前 turn，不清空历史 | 两种模式都必须保留已显示内容 |
| session list 来源 | 会话是实体，不是页面临时状态 | `server` 走 REST，`local` 走 session store |
| reconnect / restore | Web 允许服务端追流，本地不允许 | `local` 恢复只能 replay 本地缓存 |

## 9.5 核心能力对齐的落地实现顺序

为了避免后面边改边串模式，建议严格按下面顺序落地：

1. 先把 `P0` 冻结的事件集继续守住：`session / thinking / content / error / done`。
2. 再把 `local` 的历史加载、列表、重命名、删除、账号清理全部走统一仓储。
3. 再补 `local` 的完整 replay，而不是先上更多新事件类型。
4. 再决定 `regenerate`、`wait_for_input`、`sources`、`tool_call` 这些增强能力的优先级。

如果顺序反过来，最容易出现的问题就是：

- UI 看起来能切模式，但会话来源串了。
- 本地也能出流，但列表和详情对不上。
- 停止生成和恢复续聊在两种模式下给出两套体验。

下面这张表更偏“业务手感”而不是纯协议，适合作为实现时的验收清单。

| 业务场景 | Web 真实体验 | iOS `server` 当前 | iOS `local` 应对齐到什么程度 |
| --- | --- | --- | --- |

| 打开旧会话 | 详情立即展示，必要时续流 | 已有 | 详情立即展示，首期不追服务端，仅本地 replay |
| 重命名会话 | 列表与详情同步改名 | 已有 | 已有，继续保持 |
| 删除会话 | 列表移除，当前会话删除时回到新会话态 | 已有 | 已有骨架，需继续验证 |
| 切换账号 | 清理当前账号上下文 | 已有 | 已有骨架，需继续验证本地缓存完全隔离 |
| 切换模式 | 进入另一条数据源与执行链路 | 已有骨架 | 已有骨架，必须保证不串列表、不串恢复 |

## 10. 实施建议

推荐顺序：

1. 先补设置层字段与开关。
2. 再补装配层仓储切换。
3. 再补本地 session store。
4. 再把 `endpoint.scheme == local` 的真实本地执行器补上。
5. 最后补本地 replay、重生成等增强语义。

不推荐的做法：

- 先改 UI，再回头补仓储。
- 先让 `local` 模式继续复用服务端 session API 过渡。
- 先写 GGUF / 本地模型执行器，但没有会话与恢复语义。

## 11. 结论

“对齐 Web”的真正含义不是把 Web 的组件翻译成 SwiftUI，而是把 Web 已经跑通的会话语义、事件语义和恢复语义变成 iOS 可复用的统一边界。

对这次双后端切换来说，最关键的不是“能不能请求本地模型”，而是：

- `server` 模式继续完整复用 `DeepTutorSerevr`。
- `local` 模式从会话、消息、恢复开始就完全本地闭环。
- 现有 `AIChatViewModel`、`AIChatEventReducer`、消息 UI 继续只面对一套领域语义。
