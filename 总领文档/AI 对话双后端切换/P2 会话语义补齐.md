# SupportClient｜AI 对话双后端切换 P2 会话语义补齐

## 1. 对标范围与结论

P2 关注的不是“能不能聊天”，而是“会话语义是否完整”。

这一阶段要补齐的五条语义是：

1. 重生成。
2. 历史会话加载。
3. 重命名 / 删除。
4. 账号切换清理。
5. 模式切换隔离。

### 1.1 P2 的目标

P2 的目标是让 `server` 与 `local` 两条链路在会话语义层面尽量同构：

- `server` 继续保持 Web 语义。
- `local` 在不写正式数据库、不做多端同步的前提下，至少要有一致的会话生命周期、列表行为、恢复行为和账号隔离行为。

### 1.2 这份文档对 P0 / P1 的偏差纠偏

在前两份文档里，有几处表述需要随着当前工程事实一起收紧：

- 不是“local 没有任何基础”，而是 `LocalAIChatRepository`、`LocalAIChatSessionStore`、`LocalAIChatRuntime`、`AIChatRoutingRepository`、`AIChatRuntimeModeStore` 都已存在。
- 不是“local 仅 stub”，而是 local 现在已经具备“两段式执行器”：先尝试真实 OpenAI-compatible 流，再回退 stub。
- 不是“会话切换还未收口”，而是 `AIChatViewModel` 已经把 `onAppear` 的 runtime mode 变化、`startNewSession`、`openSession`、`renameSession`、`deleteSession`、`regenerateLastTurn` 和 `disconnectAndClear` 收口在同一个状态机里。
- 不是“账号切换还没做”，而是 `AIChatRoutingRepository.clearAccountState`、`LocalAIChatRepository.clearAccountState`、`AIChatViewModel.disconnectAndClear()`、`AIChatRuntimeModeStore.clear()` 已经给出了隔离骨架。

因此，P2 的真实任务不是“再发明一次会话系统”，而是把这些已经存在但还不完全对齐的语义，整理成可执行、可验收、可回归的会话层方案。

## 3. 分层职责与请求链路

### 3.1 Web 语义基线

Web 对会话语义的基本做法是：

- WS 管 turn 流。
- REST 管 session 实体。
- `resume_from` 负责断线续流。
- `listSessions` / `getSession` / `updateSessionTitle` / `deleteSession` 负责会话列表与详情。

P2 需要做的是：

- `server` 继续遵守这套语义。
- `local` 在本机模拟同样的会话生命周期。

### 3.2 `server` 模式链路

```text
AIChatViewModel
  -> Start / Resume / Rename / Delete 用例
  -> AIChatRepository
  -> DeepTutorSessionAPI / DeepTutorWebSocket
  -> server session / turn / resume 语义
  -> AIChatEventReducer
  -> SwiftUI 会话列表 / 详情 / 当前对话
```

### 3.3 `local` 模式链路

```text
AIChatViewModel
  -> Start / Resume / Rename / Delete 用例
  -> AIChatRoutingRepository
  -> LocalAIChatRepository
  -> LocalAIChatSessionStore / AIChatResumeStore
  -> LocalAIChatRuntime
  -> 本地流式事件
  -> AIChatEventReducer
  -> SwiftUI 会话列表 / 详情 / 当前对话
```

### 3.4 P2 需要统一的职责

| 语义 | `server` 负责什么 | `local` 负责什么 |
| --- | --- | --- |
| 重生成 | 通过服务端 regenerate 重新跑上一轮 | 先明确占位还是重新执行本地 prompt |
| 历史会话加载 | REST 拉详情 | 本地 session store 拉消息 |
| 重命名 | PATCH / rename | 本地 session store 更新 title |
| 删除 | REST delete | 本地 session store 删除记录 |
| 账号切换清理 | 清 session / resume / mode cache | 清 session / resume / mode cache |
| 模式切换隔离 | route 到 server repository | route 到 local repository，不串 session |

## 4. 核心关键技术与实现方案

### 4.1 重生成

#### 4.1.1 现状

- `server` 模式已有 `RegenerateAIChatTurnUseCase`，实际落到 `AIChatRepository.regenerate(sessionID:)`，再转成 WebSocket `regenerate`。
- `local` 模式当前仍是占位错误，还没有真正形成“重复生成上一轮”的会话语义。

#### 4.1.2 P2 目标

P2 要先定义语义，再决定实现：

- 如果是 `server`，重生成应继续复用服务端能力。
- 如果是 `local`，需要决定是：
  - 重新执行上一轮输入并复用当前会话历史，还是
  - 直接提示暂不支持，但保留按钮位置和错误态。

#### 4.1.3 建议结论

P2 阶段推荐把 `local` regenerate 先定义为“语义占位但可见”：

- 按钮可以保留。
- 点击后给出明确的“本地模式暂不支持重新生成”提示。
- 不破坏当前会话、历史和消息列表。

这样做的原因是：

- 本地模式核心优先级还在新建、发送、流式、停止、列表。
- regenerate 属于上层会话增强能力，不该阻塞 P2 主路径。

### 4.2 历史会话加载

#### 4.2.1 现状

`AIChatViewModel.openSession(_:)` 已经把历史会话加载收口到一个固定流程：

```text
loadSessionDetailUseCase.execute(sessionID:)
  -> state.activeSession
  -> state.messages
  -> resetTurnScopedState
  -> saveResumeSnapshot
  -> resumeTurnUseCase.execute(sessionID:accountID:)
```

但这个流程对 `local` 与 `server` 的语义不完全一样：

- `server` 模式会继续追服务端恢复。
- `local` 模式应该只加载本地消息和本地恢复快照，不该碰服务端接口。

#### 4.2.2 P2 目标

- `server` 模式：继续 REST 详情 + resume 续聊。
- `local` 模式：只读本地 session store + 本地 resume snapshot。

#### 4.2.3 关键要求

- 进入历史会话时，要保留当前模式。
- 不能把 `local` 会话误当成 `server` 会话去追流。
- 不能把 `server` 的 session detail 逻辑泄漏到 `local` 分支。

### 4.3 重命名 / 删除

#### 4.3.1 现状

- `server` 模式已通过 `RenameAIChatSessionUseCase` / `DeleteAIChatSessionUseCase` 走后端接口。
- `local` 模式已通过 `LocalAIChatSessionStore.renameSession` / `deleteSession` 在内存里完成。

#### 4.3.2 P2 目标

P2 要确认的是“同一页面，两种后端，同一套交互”：

- 重命名后，列表项要立刻更新。
- 删除后，列表项要立刻消失。
- 如果删掉的是当前打开的会话，要自动回到新会话状态。

#### 4.3.3 细节要求

| 场景 | 期望行为 |
| --- | --- |
| 重命名当前会话 | 列表、标题栏、当前 session 同步更新 |
| 删除当前会话 | 自动 `startNewSession()`，不留悬空 session |
| 删除非当前会话 | 仅从列表移除 |
| `local` 重命名 | 只改本地 store，不碰服务端 |
| `local` 删除 | 只删本地 store，不碰服务端 |

### 4.4 账号切换清理

#### 4.4.1 现状

当前工程已经具备账号级清理骨架：

- `AIChatViewModel.disconnectAndClear()`
- `AIChatRoutingRepository.clearAccountState(accountID:)`
- `LocalAIChatRepository.clearAccountState(accountID:)`
- `AIChatRuntimeModeStore.clear(accountID:)`
- `AIChatResumeStore.clear(accountID:)`

#### 4.4.2 P2 目标

账号切换时必须清掉这些内容：

- 当前连接。
- 当前 active session / active turn。
- 当前账号的本地会话列表。
- 当前账号的 resume snapshot。
- 当前账号的运行模式缓存。

#### 4.4.3 不能清掉的内容

- 其他账号的设置。
- 其他账号的本地会话。
- 服务端的账号级真实历史数据。

### 4.5 模式切换隔离

#### 4.5.1 现状

模式切换已经有明确骨架：

- `AISettingsSnapshot.chatRuntimeMode`
- `AIChatRuntimeModeStore`
- `AIChatRoutingRepository.runtimeMode`
- `AIChatViewModel.onAppear()` 的 runtime mode 变更处理

#### 4.5.2 P2 目标

切换 `server` / `local` 时，必须保证：

- 当前连接先断开。
- 当前 state 重置。
- 新模式下重新激活对应仓储。
- 列表数据不串。
- 历史恢复路径不串。

#### 4.5.3 切换策略建议

| 动作 | 建议处理 |
| --- | --- |
| `server -> local` | disconnect + reset state + 激活 local repository |
| `local -> server` | disconnect + reset state + 激活 server repository |
| 切换时有正在生成的 turn | 优先收口当前 turn，再切模式 |
| 切换后进入对话页 | 只读当前模式的 session 数据 |

### 5.1 会话实体

`AIChatSession` 在 P2 的语义应明确为：

| 字段 | 语义 |
| --- | --- |
| `id` | 会话唯一标识 |
| `title` | 会话标题 |
| `status` | 会话状态 |

| `messageCount` | 消息条数 |
| `lastMessagePreview` | 列表预览 |
| `accountID` | 账号归属 |
| `serverSessionID` | 服务端会话标识，local 可为空或不使用 |

### 5.2 恢复快照

`AIChatResumeSnapshot` 在 P2 的语义应明确为：

| 字段 | 语义 |
| --- | --- |
| `sessionID` | 当前恢复目标会话 |
| `turnID` | 当前恢复目标 turn |
| `lastSeq` | 已确认事件序号 |
| `cursor` | 恢复游标 |
| `pendingEvents` | 待重放事件 |
| `serverToken` | 服务端恢复 token，local 不应依赖它 |

### 5.3 重命名 / 删除契约

| 操作 | `server` 契约 | `local` 契约 |
| --- | --- | --- |
| rename | 持久化到后端 session 实体 | 写入本地 session store |
| delete | 后端删除 | 本地 store 删除 |
| list after rename | 返回新 title | 返回新 title |
| list after delete | 不再返回 | 不再返回 |

### 5.4 模式隔离契约

P2 还要明确以下契约：

- 运行模式属于账号偏好，不是 session 偏好。
- `server` / `local` 的 session 列表互相隔离。
- `resume snapshot` 的清理必须跟随账号，不允许跨账号复用。

### 6.1 Web 对齐判断

P2 和 Web 对齐的重点不是页面，而是 session 语义：

- Web 的 session 实体和 turn 流已经分层。
- iOS `server` 模式已基本对齐这条语义。
- iOS `local` 模式要补的是“同等的会话列表 / 历史 / 重命名 / 删除 / 清理”语义，而不是继续补 UI。

### 6.2 当前真实代码与 P0 / P1 的进一步纠偏

P2 阶段再看一次真实代码，需要把下面几件事彻底说准：

| 主题 | 早期容易写偏的判断 | 当前更准确的事实 |
| --- | --- | --- |
| `local` 发送链路 | 只有 stub | 已有 `LocalAIChatRuntime`，会先尝试真实 OpenAI-compatible SSE，再回退 stub |
| `local` 恢复 | 一定会误走服务端续流 | 当前 `loadSession` 已是本地实现，`checkActiveTurn` 在 `local` 下是 no-op |

这意味着 P2 的重点已经不是“证明双链路能存在”，而是“把会话层的行为补得和 Web 一样稳定”。

## 6.3 P2 需要对齐的业务流程

### 6.3.1 打开历史会话

Web 的真实体验是：

1. 列表点击某项。
2. 立即切到该 session 的详情。
3. 如果该会话仍有进行中的 turn，再补恢复或追流。

iOS `local` 在 P2 应对齐到：

1. `loadSession(id:)` 立即返回本地 session 与 messages。
2. UI 立即展示本地历史。
3. `resume snapshot` 只做本地状态恢复，不做服务端追流。

### 6.3.2 重命名与删除

Web 的真实体验是：

1. 列表项修改后立即反映。
2. 当前打开会话被删时，页面切回可发送的新会话态。

iOS `local` 在 P2 应对齐到：

1. `renameSession` 后同步更新 `sessions` 与 `state.activeSession`。
2. `deleteSession` 删除当前会话时，调用 `startNewSession()` 或等价状态重置。
3. 不保留悬空的 `resume snapshot`。

### 6.3.3 账号切换与模式切换

Web 侧本质上只有账号与服务端上下文切换，而 iOS 这里多了一层 runtime mode，所以 P2 要额外对齐：

1. 切账号时，当前账号的 local session、resume、mode cache 必须一起清掉。
2. 切模式时，`server/local` 两侧会话列表必须完全隔离。
3. 切模式时如果当前还有 active turn，必须先收口，再进入新模式。

## 7.4 P2 关键代码落点示例

下面不是要重写工程，而是把 P2 最关键的落点钉在现有代码结构上。

### 7.4.1 会话打开统一走仓储

```swift
func openSession(_ session: AIChatSession) async {
    let detail = try await loadSessionDetailUseCase.execute(sessionID: session.id)
    state.activeSession = detail.0
    state.messages = enrichAssistantMessages(detail.1)
    repository.saveResumeSnapshot(
        AIChatResumeSnapshot(sessionID: session.id, turnID: nil, lastSeq: 0, cursor: 0),
        accountID: accountID
    )
    try await resumeTurnUseCase.execute(sessionID: session.id, accountID: accountID)
}
```

P2 对这段代码的要求不是改入口，而是确保：

- `server` 仍走服务端详情与恢复。
- `local` 走本地详情与本地恢复。
- UI 永远只感知“打开会话”，不感知后端来源。

### 7.4.2 本地历史详情必须只读本地 store

```swift
func loadSession(id: String) async throws -> (AIChatSession, [AIChatMessage]) {
    let accountID = try requireAccountID()
    guard let record = sessionStore.loadSession(accountID: accountID, id: id) else {
        throw AIChatError.sessionLoadFailed("本地会话不存在")
    }
    return (record.session, record.messages)
}
```

这段代码就是 P2 的核心边界之一：

- 读取历史本地会话时，不允许偷打 `DeepTutorSessionAPI`。
- 列表、详情、重命名、删除都必须共享同一个本地事实源。

### 7.4.3 本地 regenerate 当前必须明确占位

```swift
func regenerate(sessionID: String) async throws {
    throw AIChatError.terminalTurn("本地模式暂不支持重新生成")
}
```

这段代码虽然简单，但它在 P2 里是合理的：

- 行为明确。
- 不静默失败。
- 不破坏现有 session 语义。

### 7.4.4 模式切换时先断开再重置

```swift
func onAppear() async {
    let currentMode = repository.runtimeMode
    if let lastKnownRuntimeMode, lastKnownRuntimeMode != currentMode {
        repository.disconnect()
        state = AIChatState.initial
        sessions = []
    }
    lastKnownRuntimeMode = currentMode
    await connectIfNeeded()
    await restoreIfNeeded()
}
```

P2 对这段代码的要求是继续收紧：

- 这已经是模式隔离的第一道防线。
- 后续要补的是“列表数据源”和“resume replay”在新模式下完全一致，而不是重新换一套页面。

## 8. 实施拆分与验收

### 8.1 P2 实施拆分

#### Step 1：固化会话列表语义

- 明确 `server` / `local` 的列表数据源。
- 明确列表刷新后数据应如何排序。
- 明确列表中当前会话的高亮规则。

#### Step 2：统一历史加载语义

- `server` 继续走 REST detail + resume。
- `local` 走本地 session store + 本地 resume snapshot。
- 不允许混用两边接口。

#### Step 3：统一重命名 / 删除回写

- `server` 通过后端接口回写。
- `local` 通过本地 store 回写。
- 回写后列表和当前详情同步更新。

#### Step 4：统一账号切换清理

- 切账号时清理当前账号的 session、resume、模式缓存。
- 保证切换后不会读到前一个账号的残留状态。

#### Step 5：统一模式切换隔离

- 模式切换时先断开当前连接。
- 再重置 ViewModel state。
- 再激活新模式的仓储。

### 8.1 P2 与 Web 对齐的最低验收手感

如果只用一句话判断 P2 是否真的做完，不看代码，只看体验，应至少满足：

1. 在 `local` 模式里，用户可以像 Web 一样创建多个会话、来回打开、重命名、删除，而不会觉得这只是一个临时演示页。
2. 在 `server` 模式里，所有原有会话行为完全不回退。
3. 在 `server/local` 之间切换时，用户看到的是“切到另一套后端”，不是“当前页面状态乱了”。

### 8.2 P2 验收标准

- [ ] `server` 模式重生成行为不变。
- [ ] `local` 模式重生成要么明确占位，要么明确本地重跑，不出现静默失败。
- [ ] `server` / `local` 都能加载历史会话。
- [ ] `server` / `local` 都能重命名和删除会话。
- [ ] 账号切换后，本地会话、resume snapshot、运行模式不会串号。
- [ ] 模式切换后，session 数据源和恢复逻辑完全按当前模式走。

### 8.3 手工验收场景

1. 在 `local` 模式创建两个会话，重命名其中一个并删除另一个，确认列表实时变化。
2. 切到 `server`，确认服务端会话列表仍然正常，且不会看到 `local` 的本地缓存项。
3. 在 `server` 模式打开一个历史会话，确认恢复逻辑仍然通过服务端 detail + resume 流程。
4. 切账号后，确认原账号的 `local` 会话和 resume snapshot 不可见。
5. 切模式时正在生成的 turn 能够被收口，不留下半截状态。

## 9. 风险与待确认项

### 9.1 风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| regenerate 语义不一致 | server 和 local 可能给出两套体验 | P2 先冻结占位还是重跑的最终语义 |
| 本地历史过度依赖 resume | 如果 resume 过强，会把 local 伪装成 server | 本地 resume 只作为本机状态恢复 |
| 列表与详情不同步 | 重命名/删除后 UI 没同步刷新 | 统一由 ViewModel 回写 `sessions` 和 `state.activeSession` |
| 账号切换残留 | 前一个账号的本地缓存未清干净 | 所有清理入口都必须按 accountID 执行 |
| 模式切换串流 | 旧模式的 turn 还在跑，新模式已经切入 | 切换时必须先 disconnect 并 reset state |

### 9.2 待确认项

- `local` regenerate 最终是否支持真正的重跑。
- `local` 历史会话是否在 App 重启后保留。
- `server/local` 是否允许共享同一个会话列表视图，但按来源分组。
- 切换模式时，是否需要把当前 session 自动迁移到新模式。
- 删除会话后，是否需要同时清理对应 resume snapshot。

### 9.3 最终判断

P2 的目标是让会话语义不再分裂成“一个 server、一个 local、两个标准”。

如果 P2 做完，应该能看到这五件事都成立：

- 同一个页面能切换两条链路。
- 同一个会话列表能在两条链路下保持稳定。
- 同一个账号切换前后不会串状态。
- 同一个模式切换前后不会串 session。
- 同一个状态机能同时承接 server 与 local。
