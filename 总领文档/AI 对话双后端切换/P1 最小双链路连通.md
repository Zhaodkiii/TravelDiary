# SupportClient｜AI 对话双后端切换 P1 最小双链路连通

## 1. 对标范围与结论

P1 只解决一个问题：让 `server` 与 `local` 两条 AI 对话链路都能被同一个 `AIChat` 页面稳定驱动，并且 `local` 至少完成下面 5 个最小能力：

1. 新建会话。
2. 发送消息。
3. 流式文本。
4. 停止生成。
5. 本地会话列表。

### 1.1 本阶段的目标不是“再写一套聊天页”

这点必须先钉死：

- `server` 模式保持现状，不回退、不重写、不换协议。
- `local` 模式不新开页面，不新开 Tab，不新开一套独立 UI。
- 两条链路都必须继续喂给同一个 `AIChatViewModel` 和同一套 SwiftUI 消息列表。
- 本阶段允许 `local` 仍然只覆盖最小功能，但不能再把它当成“纯占位草图”。

### 1.2 这次和 P0 / 技术细节文档的偏差修正

和之前的文档相比，当前工程状态已经有了真实变化，所以 P1 必须明确修正以下认知：

- 不是“`local` 还没有任何架构”，而是 `LocalAIChatRepository`、`LocalAIChatSessionStore`、`AIChatRoutingRepository`、`AIChatRuntimeModeStore` 都已经存在。
- 不是“运行模式还停留在概念”，而是 `AISettingsSnapshot.chatRuntimeMode` 已经落盘，`AISettingsView` 已经提供切换入口。
- 不是“`local` 必须再单独设计一套模型解析链”，而是应继续复用 `AIConfigCenter` / `ScenarioPolicyResolver` 的统一模型消费链。
- 不是“`local` 模式已经完整可用”，而是当前 `local` 仍是内存级 session 骨架 + stub 流式事件，真实 AI 执行器还没接上。

因此，本 P1 的准确定位是：

> 在现有双后端骨架上，把 `local` 模式从“能切、能看、能记”推进到“能新建会话、能发消息、能流式显示、能停止、能看本地列表”的最小闭环。

## 3. 分层职责与请求链路

### 3.1 `server` 链路保持现状

```text
AISettingsView
  -> AISettingsViewModel
  -> AISettingsSnapshot.chatRuntimeMode = server
  -> AIChatRuntimeModeStore
  -> AIChatRoutingRepository.activeRepository = serverRepository
  -> AIChatRepository
  -> DeepTutorTokenAPI
  -> DeepTutorSessionAPI / DeepTutorLLMOptionsAPI
  -> AIChatWebSocketClient
  -> AIChatEventReducer
  -> AIChatViewModel
  -> SwiftUI 消息列表 / 输入框 / 结束按钮
```

这个链路 P1 的约束是“不动它”：

- 不改对话协议。
- 不改 session REST。
- 不改 WebSocket 事件解码。
- 不改 UI 组件树。

### 3.2 `local` 链路的最小闭环

```text
AISettingsView
  -> AISettingsViewModel
  -> AISettingsSnapshot.chatRuntimeMode = local
  -> AIChatRuntimeModeStore
  -> AIChatRoutingRepository.activeRepository = localRepository
  -> LocalAIChatRepository
  -> LocalAIChatSessionStore
  -> LocalAIChatStreamAdapter / stub stream
  -> AIChatEventReducer
  -> AIChatViewModel
  -> SwiftUI 消息列表 / 输入框 / 停止按钮 / 本地会话列表
```

P1 的 `local` 目标不是“模拟一套 Web 服务端”，而是：

- 用户能在本地新建一个会话。
- 用户能发出消息。
- 页面能看到流式文本增长。
- 用户能按停止按钮中断当前生成。
- 用户能打开本地会话列表看到刚刚产生的记录。

### 3.3 页面进入时的链路决策

`AIChatViewModel.onAppear()` 现在已经能感知 `repository.runtimeMode`，所以 P1 应明确：

- 如果 runtime mode 没变，继续走当前仓储。
- 如果账号切换或运行模式变更，先断开旧仓储，再重置 state。
- `server` 与 `local` 的切换不应造成消息列表 UI 重建，只应造成仓储切换和状态重置。

### 3.4 停止生成链路

P1 的停止按钮必须做到：

- `server` 模式发送 `cancel_turn`。
- `local` 模式取消本地运行任务、清理当前 turn 状态、保留已生成内容。

这两条路径都要最终收口到同一套 `AIChatEventReducer.cancelTurn` 语义。

## 4. 核心关键技术与实现方案

### 4.1 运行模式读写

运行模式已经由 `AISettingsSnapshot.chatRuntimeMode` 承载，P1 要保证三件事：

1. 设置页改动能立即写入账号级快照。
2. `AIChatRuntimeModeStore` 能同步拿到最新值。
3. `AIChatRoutingRepository` 能根据账号读取正确仓储。

### 4.2 路由仓储的职责

`AIChatRoutingRepository` 是 P1 的关键过渡层。它应该只做一件事：

- 根据当前账号的运行模式，把所有 `AIChatRepositoryProtocol` 调用路由到 `serverRepository` 或 `localRepository`。

它不应该做的事情：

- 不解析模型配置。
- 不渲染 UI。
- 不自己实现 session 存储。
- 不自己决定 prompt 或 provider。

### 4.3 本地会话存储

`LocalAIChatSessionStore` 在 P1 的职责是：

- 按账号隔离本地 session。
- 管 list / load / rename / delete。
- 为 `local` 模式提供当前会话和历史会话。

P1 里它的最小数据语义已经足够覆盖：

| 字段 | 作用 |
| --- | --- |
| `session.id` | 本地会话唯一标识 |
| `session.title` | 列表展示和详情标题 |
| `session.status` | 当前状态 |
| `session.messageCount` | 列表摘要 |
| `session.lastMessagePreview` | 最新消息预览 |
| `messages` | 本地消息历史 |

### 4.4 本地流式事件适配

当前 `LocalAIChatRepository` 已经能发出 `session`、`thinking`、`content`、`done` 这四类核心事件，并通过 `LocalAIChatRuntime` 做两段式执行：

- 如果 `AIConfigCenter.resolve(for: .chat)` 返回的是可直接请求的 OpenAI-compatible endpoint，就走真实流式请求。
- 如果模型解析失败，或者配置落到 `local` 方案，就回退到 stub 流。

P1 的任务不是再发明一套新的本地流式协议，而是把这个“双路径执行器”定义成稳定的最小闭环：

- 真实流和 stub 流都必须走同一套 `AIStreamEvent` 归约链。
- 停止按钮必须能中断真实流和 stub 流两种执行。
- 对 UI 来说，不能区分“这是 API 流还是 stub 流”，只能看到统一的内容增量。

### 4.5 `AIConfigCenter` 的继续复用

本地模式不能自己再造一套模型配置逻辑。P1 必须继续复用：

- `AIConfigCenter.resolve(for: .chat, preferredModelName:)`
- `ScenarioPolicyResolver.resolve(...)`
- `AIResolvedConfig`

也就是说：

- `local` 只决定“怎么执行”。
- 模型怎么选，还是由现有 AI 配置体系决定。

## 5. 接口契约与数据模型

### 5.1 运行模式

```swift
enum AIChatRuntimeMode: String, Codable, Sendable {
    case server
    case local
}
```

P1 约定：

- `server` 是默认值。
- `local` 只影响对话执行器，不影响登录身份。

### 5.2 本地最小 session 模型

P1 的本地 session 至少要保留这些字段：

| 字段 | 是否必需 | 说明 |
| --- | --- | --- |
| `id` | 是 | 本地会话 ID |
| `title` | 是 | 列表标题 |
| `status` | 是 | 运行状态 |
| `createdAt` | 建议 | 创建时间 |
| `updatedAt` | 建议 | 更新时间 |
| `lastMessageAt` | 建议 | 最近消息时间 |
| `messageCount` | 是 | 列表摘要 |
| `lastMessagePreview` | 是 | 列表预览 |
| `accountID` | 是 | 账号隔离 |
| `serverSessionID` | 否 | 未来兼容字段 |

### 5.3 本地与服务端的接口差异

| 能力 | `server` 模式 | `local` P1 模式 |
| --- | --- | --- |
| 新建会话 | REST / WebSocket 联动 | 本地内存建会话 |
| 发送消息 | `start_turn` | 本地 turn 启动 |
| 流式文本 | WebSocket 事件流 | 本地事件流 / stub 流 |
| 停止生成 | `cancel_turn` | 取消本地任务 |
| 会话列表 | `listSessions` REST | 本地 session store list |
| 会话详情 | `loadSession` REST | 本地 session store load |
| 重生成 | 已有 | 可先保持占位 |
| 问答补答 | 已有 | 可先保持占位 |

### 5.4 对 Web 语义的最小对齐

P1 本地模式要继续对齐 Web 的不是页面布局，而是这些语义：

- session 是实体，不是临时变量。
- turn 是一轮回答，不是一次 UI 更新。
- streaming 是增量过程，不是一次性文本。
- cancel 后保留上下文，不丢已经显示的内容。
- list / detail / reload 的语义要稳定。

## 8. 实施拆分与验收

### 8.1 P1 实施拆分

#### Step 1：保持 server 路径零回归

- `AIChatRepository` 不改语义。
- 现有 `server` 模式继续走 WebSocket + REST。
- 任何新增代码不能影响 `server` 的连接、发送、取消、恢复。

#### Step 2：把 local stub 收敛成最小闭环

- 保持 `LocalAIChatRepository` 的本地 session 入口。
- 保持本地流式事件输出。
- 让本地消息列表、停止按钮、会话切换都走同一套状态机。

#### Step 3：保证会话列表可用

- `localRepository.listSessions()` 返回本地缓存会话。
- `localRepository.loadSession(id)` 返回本地消息历史。
- `renameSession` / `deleteSession` 保持本地行为。

#### Step 4：保证停止生成真实生效

- `server` 模式走 `cancel_turn`。
- `local` 模式取消本地任务并收口当前 turn。

#### Step 5：保持 UI 不变

- `AIChatEntryView`、`AIChatRootView`、消息卡片不改整体结构。
- UI 只根据状态变化展示不同内容，不根据后端类型拆两套页面。

### 8.2 P1 验收标准

- [ ] 运行模式切到 `server`，现有 AI 对话行为不变。
- [ ] 运行模式切到 `local`，可以创建本地会话。
- [ ] `local` 模式可以发送消息，并看到流式文本。
- [ ] `local` 模式可以点击停止生成并立即中断。
- [ ] `local` 模式可看到本地会话列表。
- [ ] 切换账号后，本地会话不会串号。
- [ ] `server` 模式的会话列表、恢复、取消不受 `local` 改动影响。

### 8.3 手工验收场景

1. 登录账号 A，切到 `local`，发送一条消息，确认会话列表里出现新会话。
2. 在流式输出中点击停止，确认消息停在当前内容，不继续追加。
3. 切回 `server`，确认原有对话仍能正常连接和发送。
4. 登出账号 A 再登录账号 B，确认 A 的本地会话不会出现。
5. 在 `local` 模式下多次进入和退出对话页，确认本地 session 与消息不会丢失到当前会话缓存之外。

## 9. 风险与待确认项

### 9.1 风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| local 仍停留在 stub 流 | 目前已能出事件，但还没接真实 AI API | P1 先定义最小闭环，再把 stub 替换成真实执行器 |
| 账号切换污染 | 本地会话和运行模式如果不隔离，容易串号 | 始终按 accountID 隔离 `AIChatRuntimeModeStore` 和 `LocalAIChatSessionStore` |
| UI 过早分叉 | 如果页面里写 if local/server，会越来越乱 | 只允许仓储路由分叉，禁止页面分叉 |
| 模型配置重写 | 本地模式如果单独再造一套模型选择，会和 AISettings 冲突 | 继续复用 `AIConfigCenter` / `ScenarioPolicyResolver` |
| 停止语义不一致 | server 是 `cancel_turn`，local 是任务取消 | 需要统一到 ViewModel 状态机收口 |

### 9.2 待确认项

- `local` 模式的流式文本在 P1 里是继续用 stub，还是接一个最小真实模型调用。
- 本地 session 列表是否需要在 App 重启后保留。
- `server` / `local` 是否允许用户分别维护两套会话历史。
- `regenerate`、`resume_from`、`wait_for_input` 是否在 P1 完全占位。
- 本地模式的模型选择是否只取 `chat` 场景默认配置，还是允许显式 model picker。

### 9.3 最终判断

P1 不是为了“证明 local 可以跑”，而是为了“证明双链路切换之后，最小聊天闭环还能稳定工作”。

只要 P1 通过，就说明：

- 设置层能控制运行模式。
