# SupportClient｜AI 对话双后端切换 P0 方案与协议冻结

## 1. 对标范围与结论

补充实现细节见 [技术细节文档.md](./技术细节文档.md)。

本阶段只做两件事：

1. 把 AI 对话的运行模式从“单一路径”冻结成“`server` / `local` 双模式”。
2. 把对话协议里本地模式必须兼容的最小事件集冻结下来，避免后续实现时反复改口。

当前结论很明确：

- `server` 模式继续沿用现有 `DeepTutorSerevr` 对话链路，不能因为本地模式接入而被改掉。
- `local` 模式由 iOS 直接调用 AI API，UI 继续沿用现有 `AIChat` 页面与卡片编排。
- 这一次先不做正式本地数据库与多端同步，`local` 模式主要依赖本机内存缓存，但当前工程里的 resume snapshot 已经是 `UserDefaults` + memory cache 形态，需要在文档里按“轻量本地状态”理解，而不是纯 RAM 变量。
- `local` 模式下新建会话、发送消息、恢复续聊都只允许在本地缓存内完成，不能把 session、message、resume 请求发送到 `DeepTutorSerevr`。
- `local` 模式的模型消费必须接入项目内现有“分场景统一模型消费”链路，不能绕开 `AIConfigCenter` / `ScenarioPolicyResolver` 再单独维护一套 chat 模型选择。
- 这个阶段不改会话消息 UI 的信息架构，不改消息气泡，不改输入框，不改会话列表的主要交互，只改“从哪里取数据、往哪里发消息”的选择层。

### 1.2 P0 冻结结论

- 运行模式枚举先冻结为 `server` 和 `local` 两个值。
- 运行模式的持久化落点先放到 `AISettingsSnapshot` / `PreferencesPayload`，让它成为账号级偏好。
- `server` 模式的入口、协议、事件、鉴权、会话列表逻辑保持现状。
- `local` 模式先冻结协议兼容，不要求完整实现所有高级能力。
- 当前工程已经存在 `LocalAIChatRepository`、`LocalAIChatSessionStore`、`AIChatRoutingRepository` 和 `LocalAIChatRuntime`，所以 P0 的真实任务不是“发明 local 架构”，而是把这条骨架修成“最小双链路连通”的可验收实现。
- `local` 模式禁止调用 `DeepTutorSerevr` 的会话创建、消息提交、会话恢复、`resume_from`、session list 和 session detail 接口。
- `local` 模式的 chat 模型解析必须统一走 `AIConfigCenter.resolve(for: .chat, ...)` 或同等统一入口，不能直接从页面、仓储或本地 runtime 手填 endpoint/model/apiKey。

## 2. iOS 端目录设计

这个 P0 不新增 UI 页面，不拆掉现有功能模块，而是把新增内容限制在几个明确位置：

| 目录 / 文件 | 作用 | P0 变化 |
| --- | --- | --- |
| `SupportClient/SupportClient/Projects/Features/AISettings/Domain/AISettingsSnapshot.swift` | AI 设置账号级快照 | 增加 `AIChatRuntimeMode` 之类的运行模式字段 |
| `SupportClient/SupportClient/Projects/Features/AISettings/Presentation/Root/AISettingsViewModel.swift` | AI 设置页面的唯一状态入口 | 增加读取、修改、保存运行模式的逻辑 |
| `SupportClient/SupportClient/Projects/Features/AISettings/Presentation/Root/AISettingsView.swift` | AI 设置主页面 | 增加“AI 对话运行模式”开关所在的 section 或 row |
| `SupportClient/SupportClient/Projects/App/Sources/App/Architecture/AIChatAssembly.swift` | AIChat 装配点 | 按运行模式选择 `server` 仓储或 `local` 仓储 |
| `SupportClient/SupportClient/Projects/Features/AIChat/Infrastructure/AIChatRepository.swift` | 当前 `server` 仓储 | 保持现有实现不变，作为 `server` 基线 |
| `SupportClient/SupportClient/Projects/Features/AIChat/Domain/` | 协议和领域模型 | 新增或拆分出运行模式、后端选择、临时本地 session 模型 |
| `SupportClient/SupportClient/Projects/Features/AIChat/Infrastructure/` | 对话基础设施 | 为 `local` 模式预留仓储接口与本地事件适配层 |

### 2.1 推荐的开关落位

推荐把开关放在 `AISettingsView`，而不是 `SettingsView` 顶层：

- `SettingsView` 负责进入 AI 设置。
- `AISettingsView` 负责承载 AI Provider、模型、小任务和对话运行模式。
- 这样不会把“AI 对话运行模式”错误地当成全局系统设置，也不会和账号管理混在一起。

### 2.2 不建议的落位

- 不建议把运行模式塞进 `SupportAppEnvironment`，因为它是环境配置，不是账号偏好。
- 不建议把运行模式直接写成 `#if DEBUG` 的编译开关，因为用户要求的是可切换，而不是只在开发态可见。
- 不建议把切换逻辑放到 `AIChatView` 或 `AIChatViewModel` 里，否则后面每一个对话动作都会分叉。

## 3. 分层职责与请求链路

### 3.1 `server` 模式链路

```text
Settings / AISettingsView
  -> AISettingsViewModel
  -> AISettingsSnapshot 保存运行模式 = server
  -> AIChatAssembly 读取运行模式
  -> AIChatRepository
  -> DeepTutorTokenAPI
  -> DeepTutorSessionAPI / DeepTutorLLMOptionsAPI
  -> AIChatWebSocketClient
  -> AIChatEventReducer
  -> AIChatViewModel
  -> SwiftUI 消息列表 / 输入框 / 卡片
```

这个链路的原则是：P0 不动它的语义，只允许外层多一层“模式选择”。

### 3.2 `local` 模式链路

```text
Settings / AISettingsView
  -> AISettingsViewModel
  -> AISettingsSnapshot 保存运行模式 = local
  -> AIChatAssembly 读取运行模式
  -> LocalAIChatRepository / LocalAIChatRuntime
  -> 本地内存 session store 创建 / 读取会话
  -> iOS 直接调用 AI API
  -> 本地流式事件转换器
  -> AIChatEventReducer
  -> AIChatViewModel
  -> SwiftUI 消息列表 / 输入框 / 卡片
```

这个链路的关键点不是“重新做一套聊天页”，而是让本地响应也能被现有事件归约器吃进去。
同时要额外冻结一条红线：`local` 模式的会话创建、消息提交和恢复不能走 `DeepTutorSerevr`，只能走本地缓存与本地 runtime。

### 3.3 P0 的职责边界

| 层 | P0 负责什么 | P0 不负责什么 |
| --- | --- | --- |
| Settings / Presentation | 展示运行模式开关、保存用户选择 | 拼接后端请求 |
| AISettings / Application | 读写运行模式快照、刷新运行时缓存 | 解析流式事件 |
| AIChat / Assembly | 按模式选仓储实现 | 直接调用 UI |
| AIChat / Domain | 定义最小协议和状态语义 | 依赖具体网络栈 |
| AIChat / Infrastructure | `server` 仓储保持现状，`local` 仓储预留 | 把 UI 逻辑塞进网络层 |

## 4. 核心关键技术与实现方案

### 4.1 运行模式枚举

建议把运行模式冻结为：

```swift
enum AIChatRuntimeMode: String, Codable, Sendable {
    case server
    case local
}
```

冻结原则：

- `server` 是默认值。
- `local` 只表示 AI 对话的运行后端，不代表登录体系变化。
- 运行模式不应隐式影响账号身份、Keychain、Token 刷新或 App 启动状态。

### 4.2 运行模式的保存位置

推荐把字段放到 `AISettingsSnapshot`，并同步进入 `PreferencesPayload`，原因有三个：

1. 它是账号级设置，和 AI Provider、模型、小任务同属一个设置域。
2. `AISettingsViewModel` 已经有完整的加载、保存和运行时刷新链。
3. P0 需要的是可切换、可持久化、可回放，而不是临时内存变量。

建议字段语义如下：

| 字段 | 类型 | 作用 | 默认值 |
| --- | --- | --- | --- |
| `chatRuntimeMode` | `AIChatRuntimeMode` | 决定 AI 对话走 `server` 还是 `local` | `.server` |
| `chatRuntimeModeUpdatedAt` | `Date?` | 可选，便于调试与审计 | `nil` |
| `chatRuntimeModeOverride` | `AIChatRuntimeMode?` | 可选，仅用于调试覆盖 | `nil` |

说明：

- `chatRuntimeModeOverride` 不是 P0 必需字段，只是预留思路，避免后面调试开关和真实用户选择混在一起。
- 如果团队希望 P0 更简洁，可以只落 `chatRuntimeMode` 一个字段。

### 4.3 设置入口和开关交互

推荐交互：

- 进入 `AISettingsView`。
- 顶部新增一个 `Section`，标题可以是“AI 对话运行模式”。
- 使用 `Picker` 或 `Toggle` 显示当前值。
- 切换时直接写入 `AISettingsViewModel.snapshot`，由现有保存按钮或立即持久化策略决定何时落盘。

推荐文案：

- `DeepTutorSerevr 运行`
- `iOS 本地运行`

推荐解释文案：

- `DeepTutorSerevr 运行`：对话仍走服务端 WebSocket 和会话运行时。
- `iOS 本地运行`：对话由客户端直接调用 AI API，适合离线实验和本地调试。

### 4.4 装配层切换策略

`AIChatAssembly` 应从“固定创建一个仓储”升级为“根据运行模式创建对应仓储”：

| 运行模式 | 创建的对象 | 说明 |
| --- | --- | --- |
| `server` | 现有 `AIChatRepository` | 完全保留当前链路 |
| `local` | 新的 `LocalAIChatRepository` 或同级运行时实现 | 负责本地调用 AI API、流式事件转换和本地 session 缓存 |

关键原则：

- 切换逻辑要放在装配层，不要放在 `AIChatViewModel`。
- 同一个 `AIChatViewModel` 只依赖一个仓储协议，不感知后端类型。
- `AIChatEntryView`、`AIChatRootView`、消息列表和输入框都不应该因为模式不同而出现两套 UI。

### 4.5 本地模式的最小会话运行时

`local` 模式首期只需要内存级 session 管理，不要求持久化。

建议最小能力：

- 当前 session 的创建与切换。
- 当前 turn 的流式输出。
- 当前 turn 的取消。
- 当前 session 的消息列表。
- 本地临时会话列表。
- 基于本地缓存的当前会话恢复与续聊。

暂不要求：

- App 重启后恢复本地历史。
- 多设备同步。
- 本地与服务端会话合并。

强制约束：

- 新建会话时，只能在本地 session store 创建临时 session，不能向 `DeepTutorSerevr` 申请 session ID。
- 发送消息时，只能把消息写入本地缓存并直接驱动本地 AI runtime，不能调用 `DeepTutorSessionAPI` 或 WebSocket `start_turn`。
- 恢复续聊时，只能从本地缓存恢复当前会话与 turn 上下文，不能调用 `resume_from`、`subscribe_turn`、`subscribe_session` 或服务端 session detail 接口。

### 4.6 协议冻结的思路

P0 不是先实现所有能力，而是先冻结“哪些东西必须统一”：

- 统一消息发送入口。
- 统一流式事件类型。
- 统一 session / turn / seq 语义。
- 统一失败态与取消态。
- 统一 UI 驱动链路。
- 统一模型消费入口，尤其是 chat 场景的模型解析链。

## 5. 接口契约与数据模型

### 5.1 运行模式数据模型

建议最小数据结构如下：

```swift
nonisolated enum AIChatRuntimeMode: String, Codable, Sendable {
    case server
    case local
}
```

如果需要更清晰的设置隔离，可以在未来再补一个轻量封装：

```swift
nonisolated struct AIChatRuntimeConfiguration: Codable, Equatable, Sendable {
    var mode: AIChatRuntimeMode
    var updatedAt: Date?
}
```

### 5.2 运行模式字段落点

| 落点 | 字段 | 说明 | 备注 |
| --- | --- | --- | --- |
| `AISettingsSnapshot` | `chatRuntimeMode` | 当前账号选择的 AI 对话运行模式 | P0 必需 |
| `AISettingsSnapshot.PreferencesPayload` | `chatRuntimeMode` | 让设置能按账号持久化 | P0 必需 |
| `AISettingsViewModel` | `@Published` 绑定值 | 让 UI 能即时反映切换结果 | P0 必需 |
| `AIChatAssembly` | 读取后的运行模式 | 选择仓储实现 | P0 必需 |

### 5.2.1 模型消费字段与解析入口

`local` 模式虽然不再连接 `DeepTutorSerevr`，但模型消费不能脱离项目已有场景系统。P0 先冻结以下规则：

| 项 | 统一入口 | P0 规则 |
| --- | --- | --- |
| chat 场景解析 | `AIConfigCenter.resolve(for: .chat, preferredModelName:)` | 必须复用 |
| 场景默认模型 | `scenarioBindings` | 必须复用 |
| 场景模型来源 | `scenarioModelSources` | 必须复用 |
| runtime override | `AIRuntimeStore` / `AIConfigCenter.setRuntimeOverride` | 必须复用 |
| trial policy | `AITrialModelPolicyItem` / `trialPolicyConfig(for:)` | 必须复用 |

结论：

- `local` 模式只是把“最终执行器”改成本地，不是把“模型解析器”改成本地自定义。
- chat 模型选择必须仍然属于 `AISettings` 和 `AIConfigCenter` 的职责域。

### 5.3 最小客户端发送契约

`server` 模式仍然沿用当前 `AIStartTurnPayload`，其核心字段已经固定：

| 字段 | 说明 |
| --- | --- |
| `type = start_turn` | 发送一轮对话的命令类型 |
| `content` | 用户输入内容 |
| `session_id` | 会话 ID，可为空 |
| `capability` | 当前能力名，聊天默认 `chat` |
| `tools` | 工具列表 |
| `knowledge_bases` | 知识库列表 |
| `language` | 语言，当前默认 `zh` |
| `config` | 额外配置 |
| `persona` | 可选人格描述 |
| `llm_selection` | 模型选择 |
| `client_message_id` | 客户端消息 ID |

本地模式 P0 只需要保证：

- 发送入口仍然能表达同样的“用户输入 -> 一轮对话”的语义。
- 如果本地模型不支持某些字段，可以先忽略，但不能把字段结构改乱。
- 本地模式内部可以复用同样的领域模型，但这些字段不能被序列化后发送到 `DeepTutorSerevr`。
- 本地模式执行前的模型解析必须来自统一 chat 场景配置，而不是 `LocalAIChatRepository` 自己拼 endpoint/model/apiKey。

### 5.4 最小事件集

P0 冻结的最小事件集分两层：

#### 必须对齐

| 事件 | 为什么必须 | P0 本地处理要求 |
| --- | --- | --- |
| `session` | 会话标识和 turn 绑定的基础 | 必须能创建或更新本地 session |
| `content` | 流式正文的核心 | 必须逐段追加到当前回答 |
| `thinking` | 思考态与等待态的核心表现 | 必须能进入“思考中”状态 |
| `progress` | 进度与阶段中间态 | 必须能展示为活动状态 |
| `error` | 失败态与重试入口 | 必须能保留上下文并给出错误 |
| `done` | 一轮结束的收口事件 | 必须能固化消息并结束 streaming |

#### 可以占位

| 事件 | 占位原因 | P0 处理原则 |
| --- | --- | --- |
| `tool_call` | 本地模型未必先支持工具调用 | 可以先只记录日志或显示折叠占位 |
| `tool_result` | 与工具调用强绑定 | 可先延后实现 |
| `sources` | 需要检索与引用链路 | 可先只保留结构，不强制展示 |
| `wait_for_input` | 需要问答式中断恢复 | P0 可冻结协议，未实现时返回明确占位 |
| `stage_start` / `stage_end` | 主要用于过程可视化 | 可先作为活动态增强，不影响主链路 |
| `session_meta` | 多为会话标题与元数据 | 可先只读取标题，不强制消费全部字段 |
| `pong` / `active_turn_info` | 健康检查 / 活跃 turn 信息 | 可保留协议，不作为 P0 关键能力 |

### 5.5 本地模式 session 数据模型

由于本地模式先不做正式持久化，`local` session 可以先只保留内存字段：

| 字段 | 作用 | P0 是否必需 |
| --- | --- | --- |
| `id` | 本地 session 标识 | 必需 |
| `title` | 会话标题 | 必需 |
| `status` | 当前状态 | 必需 |
| `lastTurnID` | 最近一次 turn | 必需 |
| `lastEventSeq` | 最近一次 seq | 必需 |
| `messageCount` | 会话消息数量 | 必需 |
| `lastMessagePreview` | 列表预览 | 必需 |
| `createdAt` / `updatedAt` | 时间信息 | 建议保留 |
| `serverSessionID` | 如果未来要兼容服务端历史 | 预留 |

补充冻结：

- P0 的 `local` session ID 应由客户端本地生成。
- P0 的 `local` message 与 turn 只存在于本地缓存，不写入 `DeepTutorSerevr` session store。
- P0 的恢复语义仅指“在当前本地缓存中恢复”，不等于服务端断线续传。

## 6. iOS-Web 功能对照矩阵

这个矩阵的目标不是照搬 Web 的 UI，而是把“Web 已有的语义”与 iOS 两种后端模式对齐。

| 能力 | Web 语义基线 | iOS `server` 当前状态 | iOS `local` P0 状态 | 结论 |
| --- | --- | --- | --- | --- |
| 发送首条消息 | `start_turn` 发起一轮对话 | 已存在 | 必须对齐 | 必须 |
| 流式正文 | 内容按片段增量输出 | 已存在 | 必须对齐 | 必须 |
| 思考过程 | `thinking` / 中间态展示 | 已存在 | 必须对齐 | 必须 |
| 进度展示 | `progress` / 阶段中间态 | 已存在 | 必须对齐 | 必须 |
| 错误恢复 | 错误态保留上下文 | 已存在 | 必须对齐 | 必须 |
| 结束收口 | `done` 收尾并解除 loading | 已存在 | 必须对齐 | 必须 |
| 取消生成 | `cancel_turn` | 已存在 | 必须对齐 | 必须 |
| 会话列表 | session list 可浏览 | 已存在 | 可先内存实现 | P0 可做 |
| 会话加载 | 读取历史消息 | 已存在 | 先允许从本地缓存回看当前会话 | P0 可简化 |

| 工具调用 | `tool_call` / `tool_result` | 已存在 | 冻结协议，先占位 | P0 可占位 |
| 来源引用 | `sources` | 已存在 | 冻结协议，先占位 | P0 可占位 |

### 6.1 对齐规则

- Web 不是目标架构，后端契约才是事实源。
- iOS 本地模式不需要像 Web 一样使用浏览器状态，但事件类型和语义不能变形。
- 如果本地实现暂时缺少某个能力，要明确标注“占位”，不能偷偷改成“已完成”。

## 8. 实施拆分与验收

### 8.1 P0 实施拆分

#### Step 1：冻结运行模式枚举

- 新增 `AIChatRuntimeMode`。
- 默认值设为 `server`。
- 运行模式作为账号级偏好进入 `AISettingsSnapshot`。

#### Step 2：落位设置入口

- 在 `AISettingsView` 增加运行模式 section。
- 通过 `AISettingsViewModel` 读写并保存。
- 保证切换后不会影响 `SettingsView` 的其他条目。

#### Step 3：改造装配点

- `AIChatAssembly` 根据运行模式选择仓储实现。
- `server` 继续走现有 `AIChatRepository`。
- `local` 走新的本地实现骨架。
- `local` 骨架必须从 API 适配层就切断 `DeepTutorSerevr` 依赖，不能只是 UI 上切换标签。

#### Step 4：冻结最小协议

- 必须对齐：`session`、`content`、`thinking`、`progress`、`error`、`done`。
- 允许占位：`tool_call`、`tool_result`、`sources`、`wait_for_input`、`regenerate`、`resume_from`。

#### Step 5：保证 server 模式零回归

- `SupportAppEnvironment.deepTutorBaseURL` 不改语义。
- `DeepTutorSerevr` 端口不改。
- 现有 AI 对话 UI 不改入口和主链路。
- `local` 模式下不允许发出任何 `DeepTutorSerevr` 的建会话、发消息、恢复请求。

### 8.2 P0 验收标准

- [ ] 设置页可以看到 AI 对话运行模式开关。
- [ ] 切换到 `server` 后，现有 AI 对话链路行为不变。
- [ ] 切换到 `local` 后，iOS 端能够走新的本地仓储分支。
- [ ] 运行模式写入账号级设置快照。
- [ ] 本地模式的最小事件集已冻结，且占位能力有明确说明。
- [ ] `server` 模式的 WebSocket、session、cancel、done 语义没有被破坏。
- [ ] `local` 模式下新建会话、发送消息、恢复续聊不会触发任何 `DeepTutorSerevr` 会话或恢复接口。

### 8.3 手工验收场景

1. 登录账号 A，切到 `local`，重启应用，确认运行模式还能恢复。
2. 切回 `server`，确认 `AIChat` 仍然连接现有 `DeepTutorSerevr` 链路。
3. 在两种模式下都发送一条消息，确认 UI 结构没有变化。
4. 在 `local` 模式下触发错误，确认错误态仍保留上下文。
5. 切换账号后，确认前一个账号的运行模式和本地缓存不会串到当前账号。
6. `local` 模式下新建会话、发送消息、恢复当前会话时，确认没有任何 `DeepTutorSerevr` 网络请求。

## 9. 风险与待确认项

### 9.1 风险

| 风险 | 说明 | 建议 |
| --- | --- | --- |
| 本地模式和环境配置混淆 | 如果把本地地址塞进 `SupportAppEnvironment`，会污染 `server` 模式语义 | 本地地址应放在 AI 设置或本地 runtime 配置中 |
| 运行模式没有账号隔离 | 一个账号切换后影响另一个账号 | 必须和 `AISettingsSnapshot` 一起按账号保存 |
| UI 分叉过早 | 在 `AIChatView` 里直接写 `if local/server` | 只允许装配层分叉，不允许页面分叉 |
| 协议冻结不完整 | 本地模式做着做着又回头改事件类型 | P0 必须先冻结最小事件集 |
| 本地会话被误当正式存储 | 未来代码把内存缓存当数据库用 | 明确写“本地模式先不考虑持久化与同步” |
| Web 语义漂移 | iOS 本地模式如果另起字段名，会脱离已有协议 | 本地模式也要沿用统一事件与 session 语义 |
| 本地模式偷偷回落到服务端 | 看似是本地模式，实则仍调用 `DeepTutorSerevr` 建会话或恢复 | 通过仓储分层和日志校验确保 `local` 模式完全断开服务端会话接口 |
| 本地模式另起模型消费链 | 仓储或 runtime 自己维护 endpoint/model/apiKey，绕开场景系统 | 强制统一走 `AIConfigCenter.resolve(for: .chat)` |

### 9.2 待确认项

- `local` 模式是否需要独立的 API Key 或直接复用现有 AI Settings 里的 provider / model 选择。
- `local` 模式是否允许 `wait_for_input` 在 P0 先不支持。
- 本地 session 是否只在当前启动周期内存在，还是允许写入轻量缓存。
- 运行模式切换时，当前正在进行的 turn 是否立即中断。
- `server` 和 `local` 是否允许分别保留独立会话列表，还是共用一个列表但加来源标记。
- `regenerate`、`resume_from`、`subscribe_turn`、`subscribe_session` 在 P0 是否只冻结协议，不落本地实现。

### 9.3 最终判断

P0 的价值不是把本地 AI 完整做完，而是把后续工作拆成可执行、可回归、可验收的固定边界：

- 哪些东西必须和 `DeepTutorSerevr` 一致；
- 哪些东西可以先占位；
- 哪些东西必须放在设置和装配层；
- 哪些东西绝对不能写进页面里。
