# 设备登记需求

## 一、模块目标

设备登记负责在应用启动、进入未登录态、恢复已登录会话或登录成功后，向服务端 `POST /api/v1/device/register/` 上报当前终端信息。它的目标不是登录用户，而是让服务端能够识别同一安装设备、平台、App 版本、地区语言、系统环境和推送状态，为后续游客态、已登录态、通知、风控和诊断提供设备级基础数据。

当前 Android 工程 `SupportClientAndroid` 尚未实现设备登记链路。真实代码现状是：

- Android 工程类型：单模块 Android App，Kotlin + Jetpack Compose，入口为 `SupportClientAndroid/app/src/main/java/cn/zhaodk/SupportClient/MainActivity.kt`。
- 当前入口只展示 `Hello Android!`，没有 App 级容器、启动状态机、网络层、认证仓储、设备信息采集、设备登记 API 或本地设备 ID 存储。
- `SupportClientAndroid/需求文档/基础工程与运行环境/` 已有 HTTP、鉴权 Header、401 通知、网络状态监听等基础需求草稿，但尚未落到 Android 代码。
- iOS `SupportClient` 已有完整设备登记实现，可作为 Android 对齐基线。

本需求文档因此同时记录两类事实：

- iOS 当前实现事实：设备登记已经由生命周期协调器统一调度。
- Android 目标实现要求：在 Android 端补齐同等职责，但使用 Android/Kotlin 的平台实现。

## 二、注意区分

设备登记不是游客设备账号登录。

| 能力 | 后端接口 | 业务含义 | Android 目标入口 |
| --- | --- | --- | --- |
| 设备登记 | `POST /api/v1/device/register/` | 上报终端信息，可匿名或带 Token | `DeviceRegistrationCoordinator` |
| 游客设备账号登录 | 登录类接口，iOS 由 `signInWithDevice` 封装 | 用安装级设备凭证换取用户会话 | `SignInWithDeviceUseCase` |

设备登记可以在未登录态执行，且未登录登记不携带 Token；游客设备账号登录会产生会话，两者不能共用用例、不能互相替代。

## 三、对齐基线与关键代码

### iOS 已实现链路

```text

SupportClient/SupportClient/Projects/Core/Device/Application/DeviceRegistrationSubmittedSnapshot.swift
SupportClient/SupportClient/Projects/Core/Networking/Caching/DeviceCache.swift
```

iOS 的核心事实：

- `DeviceRegistrationCoordinator` 是设备登记主入口。
- `registerGuestDevice(reason:)` 走未登录登记，`authenticated = false`。
- `requestRegisterWithLimitedRetry(reason:session:maxAttempts:)` 走已登录登记，`authenticated = true`，最多 3 次，退避为 0ms、300ms、600ms。
- `lastRegisteredKey` 按 `authenticated-userID-installationDeviceID` 在同一次启动内去重。
- `suspendPendingSubmissions()` 在服务端鉴权失效处理中暂停后续提交。
- `SupportDeviceAPI.register(_:authenticated:)` 固定调用 `POST /api/v1/device/register/`，并通过 `requiresAuth` 控制是否注入 Token。
- `SupportSystemInfo` 负责安装级设备 ID、App 版本、系统版本、机型、屏幕、时区、语言、地区和模拟器标记等字段。
- `SparkKeychain.getOrCreateDeviceID()` 负责生成并持久化安装级设备 ID。

职责边界：

- `DeviceRegistrationCoordinator` 只负责组装请求、去重、暂停、有限重试和登记结果归类。
- `AppLifecycleCoordinator` 只负责决定何时登记，以及登记结果是否允许继续账号级 bootstrap。
- `DeviceAPI` 只负责接口路径、请求模型、响应模型和 `authenticated` 标记。
- `SupportSystemInfo` 只负责采集平台信息，不发起网络请求。
- `DeviceCredentialStore` 只负责安装级设备 ID 和游客设备登录密钥的持久化，不判断业务会话。
- `SignInWithDeviceUseCase` 只负责游客设备账号登录，不直接承担 `/device/register/`。

## 六、调用时机

设备登记不得由页面直接触发，必须由 App 生命周期统一调度。

| 场景 | 前置状态 | 调用 | 鉴权 | 结果处理 |
| --- | --- | --- | --- | --- |
| 冷启动恢复不到会话 | 网络已评估且可用，`signedOut` | `registerGuestDevice(guestColdLaunch)` | 不带 Token | 失败不阻塞登录页，只记录日志 |
| 进入未登录态清理后 | 登出或会话清理完成 | `reset()` 后 `registerGuestDevice(guestColdLaunch)` | 不带 Token | 同一未登录态防重复 |
| 冷启动恢复已登录会话 | `UserSession` 可用 | `requestRegisterWithLimitedRetry(signedInColdLaunch, session)` | 带 Token | 成功或同启动跳过后继续账号 bootstrap |
| 登录成功 | `.signedOut -> .signedIn` | `requestRegisterWithLimitedRetry(signedInColdLaunch, session)` | 带 Token | 成功或同启动跳过后进入主框架准备 |
| 前台补偿 | 已登录且需要刷新设备信息 | `requestRegisterWithLimitedRetry(signedInForeground, session)` | 带 Token | 前台场景允许绕过同启动冷启动去重 |
| 服务端鉴权失效 | 401 或业务码明确失效 | `suspendPendingSubmissions()` / `reset()` | 停止提交 | 中止账号级 bootstrap 并回到未登录态 |

整体调用链：

```text
AppLifecycleCoordinator
  ├── signedOut
  │     └── DeviceRegistrationCoordinator.registerGuestDevice(authenticated=false)
  └── signedIn
        └── DeviceRegistrationCoordinator.requestRegisterWithLimitedRetry(authenticated=true)
              └── DeviceRegistrationCoordinator.requestRegister
                    ├── SupportSystemInfo
                    └── DeviceAPI.register
                          └── POST /api/v1/device/register/
```

## 七、重试、去重与中止规则

### 有限重试

已登录设备登记参与账号级启动链路，因此需要有限重试：

- 默认最多 3 次。
- 第 1 次立即执行。
- 第 2 次前等待 300ms。
- 第 3 次前等待 600ms。
- 每次失败后记录 attempt、reason、accountID。
- 重试用尽返回 `failedRetryable`，并中止后续 AI、OSS 等账号级 bootstrap。

未登录游客登记不阻塞登录页，不需要在首屏链路里做同等级强制重试；失败时记录日志即可。

### 同启动去重

同一次 App 进程启动内，使用以下摘要避免重复提交：

```text
authenticated-userID-deviceID
```

规则：

- 上一次登记成功后保存 `lastRegisteredKey`。
- 新请求 key 相同且 reason 不是 `signedInForeground` 时，返回 `skippedSameLaunchSubmission`。
- `reset()` 清空同启动去重状态。
- 账号切换、登出、鉴权失效后必须调用 `reset()`。

### 鉴权失效中止

当设备登记阶段遇到明确鉴权失效：

- 返回 `authSessionInvalidated`。
- 调用 `suspendPendingSubmissions()`，暂停后续设备登记提交。
- `AppLifecycleCoordinator` 中止账号级 bootstrap。
- 清理会话和账号运行时后回到未登录态。
- 完成失效处理后再 `reset()`，允许后续游客登记重新开始。

## 八、数据与状态

| 状态类型 | Android 目标位置 | 生命周期 | 说明 |
| --- | --- | --- | --- |
| 安装级 `deviceId` | `DeviceCredentialStore` | App 安装级，卸载后可消失 | 敏感程度中等，不应每次启动变化 |
| 游客设备登录密钥 | `DeviceCredentialStore` | App 安装级 | 属于认证凭证，不能降级为内存态 |
| 同启动去重 key | `DeviceRegistrationCoordinator` | 进程内 | 不需要持久化 |
| 登记提交摘要 | `DeviceCache.lastDeviceRegistrationSnapshot` | 本地缓存 | 后续接入推送权限/Token 变化时用于跨启动去重 |
| 会话 Token | `AuthTokenProvider` / 会话存储 | 登录态 | 只在 `authenticated=true` 时读取 |
| 网络可用状态 | `NetworkPathMonitor` | 运行时 | 冷启动设备登记前置条件 |

设备登记请求中不应记录或打印完整 Token、设备登录密钥、推送 Token 原文。日志可以记录 `authenticated`、`reason`、`accountID`、`outcome`、接口 path 和 requestId。

## 九、异常与日志

设备登记需要输出可诊断但不泄露敏感信息的日志：

| 阶段 | 建议日志字段 |
| --- | --- |
| 开始 | `reason`、`accountID`、`authenticated` |
| 提交 | `path=/api/v1/device/register/`、`requestId`、`includesPushToken` |
| 成功 | `deviceId`、`registered`、`outcome=submitted` |
| 同启动跳过 | `outcome=skipped_same_launch_submission`、`reason` |
| 可重试失败 | `outcome=failed_retryable`、`attempt`、`errorType` |
| 鉴权失效 | `outcome=auth_session_invalidated`、`statusCode`、`backendCode` |
| 取消 | `cancelledBy`、`phase=signedInDeviceRegistration` |

401、401xx 业务码或明确 token 失效消息必须进入统一鉴权失效通知；403 不应自动视为会话失效。

## 十、验收标准

### 当前缺口验收

- `SupportClientAndroid` 中存在 Android 版 `DeviceRegistrationCoordinator`。
- `DeviceAPI.register(request, authenticated)` 能调用 `POST /api/v1/device/register/`。
- 未登录冷启动在网络可用后会执行一次游客设备登记。
- 已登录恢复或登录成功后，会先完成已登录设备登记，再进入账号级 bootstrap 和主框架。
- 已登录设备登记失败且重试用尽时，不继续预热 AI、OSS 或账号级运行时。
- 鉴权失效会中止设备登记和账号级启动链路，并回到未登录态。
- `SignInWithDeviceUseCase` 与 `DeviceRegistrationCoordinator` 职责分离。

### 请求字段验收

- Android 请求体包含 `deviceId`、`bundleId`、`platform=android`、版本、系统、机型、屏幕、时区、语言、地区和模拟器标记。
- 未登录登记不携带 Authorization Header。
- 已登录登记携带有效 Authorization Header。
- 推送未接入时 `pushToken=""`、`notificationsEnabled=false`，后续接入推送后再由通知模块提供真实值。

### 稳定性验收

- 重复 Compose 重组、Activity 重建或同一会话状态重复分发，不会在同一启动周期重复提交相同登记。
- 网络不可用时不会提前发起设备登记；网络恢复后可继续。
- 设备登记请求取消不会更新为成功状态。
- 日志能串起 requestId、operation name、reason 和 outcome。

## 十一、建议实施顺序

1. 先落 Android 网络基础：Base URL、HTTP 请求模型、JSON 编解码、错误解析、日志、鉴权 Header。
2. 实现 `DeviceCredentialStore` 和 `SupportSystemInfo`。
3. 增加 `DeviceRegistrationRequest`、`DeviceRegistrationResponse`、`DeviceAPI.register`。
4. 增加 `DeviceRegistrationRequestOutcome` 和 `DeviceRegistrationCoordinator`。
5. 建立 `AppContainer`、`AppSessionStore`、`AppLifecycleCoordinator`，把登记接入冷启动、未登录、已登录准备和鉴权失效回收。
6. 补充单元测试：请求模型字段、未登录不带 Token、已登录带 Token、同启动去重、3 次重试、鉴权失效中止。
7. 后续接入推送模块后，再将真实 Push Token、通知权限和跨启动 `DeviceRegistrationSubmittedSnapshot` 去重纳入设备登记。
