# 问题修复工单｜消息卡片与 Web 对齐 - 截图审计版

## 1. 工单目标

将 iOS 端 AI 对话里的“工具调用 + 向你提问 + 继续作答”整段体验，对齐 Web 端的问答卡片表达方式，重点修正：

- 视觉层级
- 卡片结构
- 选项样式
- 自定义输入区
- 提交区状态
- 工具调用提示语与状态流转

当前问题不是单纯的间距偏差，而是“同一业务状态在 iOS 和 Web 上被渲染成了不同的交互语言”。需要把 iOS 的问答卡片从“移动端简化版”提升为“与 Web 同语义的完整卡片版”。

---

## 2. 对比结论

### 2.1 iOS 当前表现

截图 1 中，iOS 端当前呈现为：

- 顶部仅保留简短标题“聊天”
- 工具调用阶段展示较为紧凑
- 问答卡片已经有基础结构，但整体偏窄、偏轻、偏弱
- 选项列表的层级感不够强
- 自定义输入和提交区被压缩在一个较小的卡片里
- 视觉上更像“聊天消息内嵌组件”，不像一个完整的任务卡

### 2.2 Web 当前表现

截图 2 中，Web 端当前呈现为：

- 更强的卡片边界与外框
- 更完整的引导标题
- 更明确的题目层级
- 选项块更大、更像独立选择卡
- 自定义输入区更清晰
- 提交按钮区域更稳定
- 整个问答流程更像“结构化交互面板”

### 2.3 结论

两端的差异已经超出字体和圆角层面，核心问题是：

- iOS 把“问答任务”渲染成了“普通聊天中的一段内容”
- Web 把“问答任务”渲染成了“独立任务卡”

这会导致用户对“正在执行什么动作”理解不一致，也会影响后续多端一致性。

## 3. 差异明细

### 3.1 问题标题与引导语

Web 端：

- 有明确的卡片级引导
- 标题层级更强
- 先说明“请作答以继续”，再进入具体问题

iOS 端：

- 标题和问题之间的关系更弱
- 更像把文本堆在一个消息里
- 缺少明显的“任务开始”感

### 3.2 问题正文层级

Web 端：

- 问题正文字号更大
- 行高更松
- 与选项区之间留白更充分
- 更容易识别当前要回答的核心问题

iOS 端：

- 正文更紧凑
- 问题感被弱化
- 视觉焦点容易落到外框而不是题目本身

### 3.3 选项呈现方式

Web 端：

- 每个选项是独立大卡
- A/B/C/D 字母区与文字区分离明确
- 选项更接近可点击任务项

iOS 端：

- 选项尺寸偏小
- 选项之间的结构感不够强
- 字母、标题、副标题的视觉权重没有完全拉开

### 3.4 自定义输入区

Web 端：

- 自定义输入是完整输入框
- 占位文案更明确
- 与提交按钮形成清晰的操作区

iOS 端：

- 自定义输入更像附加项
- 存在感不足
- 需要强化为“同等重要的回答方式”

### 3.5 提交按钮与底部说明

Web 端：

- 按钮位置稳定
- 灰态/可提交态切换更明显
- 整体更像表单提交

iOS 端：

- 按钮更轻
- 底部说明更贴近消息气泡风格
- 对“还没回答完”的状态表达不够强

### 3.6 工具调用状态

Web 端：

- 工具调用、等待回答、继续提交之间的状态切分更清楚
- 用户更容易理解系统正在做什么

iOS 端：

- 状态文案存在，但组合关系较弱
- 工具调用区与问答区衔接不够“连续”
- 需要把“调用工具中…”和“请作答以继续”串成同一条业务链

## 6. 优化建议

### 6.1 结构层建议

把 iOS 问答卡片拆成三个稳定区域：

1. 顶部任务引导区
2. 中部问题与选项区
3. 底部输入与提交区

这样可以让 iOS 的结构与 Web 保持同一语义分层。

### 6.2 视觉层建议

- 提高卡片边界存在感
- 增大题目字号与行高
- 选项块扩大为更明确的点击区域
- 自定义输入做成标准输入框，不要弱化成附加文本
- 提交按钮固定在操作区末尾，和输入区形成闭环

### 6.3 交互层建议

- 选中选项后要有清晰反馈
- 自定义输入获得焦点时，卡片应进入编辑态
- 未选择任何答案时，提交按钮应明确灰态
- 若存在“跳过提交”，要让文案和状态一致，不要只在底部提示里表达

### 6.4 状态机建议

统一以下状态：

- `tool_calling`
- `waiting_for_input`
- `collecting_answer`
- `ready_to_submit`
- `submitted`
- `skipped`

iOS 和 Web 都应使用同一套业务状态定义，只是渲染方式可针对平台微调。

### 6.5 文案建议

建议保持问答卡的核心文案一致：

- `请作答以继续。`
- `选择一个选项或输入自定义回复以继续。`
- `未回答的问题将作为「已跳过」提交。`

不要让 iOS 再出现与 Web 语义不一致的替代表达。

## 7. 验收标准

### 7.1 视觉验收

- iOS 问答卡片在层级上接近 Web
- 题目、选项、自定义输入、提交按钮的主次关系一致
- 工具调用区和问答区衔接自然

### 7.2 行为验收

- 选项可正常选中
- 自定义输入可正常输入
- 提交按钮状态与内容一致
- 跳过和提交逻辑与 Web 对齐

### 7.3 语义验收

- iOS 不再只是“消息里塞一个表单”
- iOS 能清晰表达“这是一个待回答的任务卡”
- 用户在 iOS 与 Web 上看到同一业务状态时，理解应一致

---

## 8. 结论

这次截图对比暴露出来的不是单一控件问题，而是“问答任务卡”的整体建模问题。

建议把 iOS 端的消息卡片升级为和 Web 同语义、同状态机、同结构的任务面板，再在平台层做有限度的尺寸适配。这样后续无论是工具提问、问答补全，还是多题流转，三端都能保持一致。

## 9. 新增问题｜iOS 点击提交后没有继续回答

### 9.1 现象

iOS 端在问答卡片里点击“提交”之后，页面没有像 Web 那样继续推进到后续回答流程。表现为：

- 提交动作有触发
- 但对话没有继续流转
- 没有进入下一段 assistant response
- 用户会感觉“答案提交了，但系统没接住”

### 9.2 与 Web 的对比

Web 端在提交后通常会完成完整的状态推进：

- 收集当前答案
- 触发提交事件
- 切换到下一轮对话状态
- 继续拉取或渲染后续 assistant 内容

iOS 端当前更像只完成了“表单提交”，没有完成“对话推进”。

### 9.3 重点怀疑方向

这个问题优先排查以下链路：

- 提交按钮是否只回调了局部状态，没有向上层透传“继续对话”事件
- 问答卡片是否只修改了本地选中态，没有触发 repository / view model 的下一步动作
- 当前 turn 是否停留在 `waiting_for_input` 或 `answering`，但没有切回可继续流转的状态
- iOS 是否缺少与 Web 等价的 `submit_user_reply` 事件
- 服务器返回后，客户端是否没有把结果重新喂回消息流

### 9.4 可能的根因

结合目前现象，比较大的概率是以下几类问题之一：

1. 提交按钮只做了 UI 层回调，没有真正触发后续对话请求
2. 问答结果已经收集，但没有附带当前 `session_id` / `turn_id` / `client_message_id`
3. 客户端状态机没有从“等待输入”切换到“继续发送”
4. Web 有“提交后继续”的二段流程，但 iOS 只实现了第一段

### 9.5 需要对齐的 Web 行为

Web 端的正确行为应包括：

- 点击提交后，立即结束当前问答收集
- 将用户答案包装成标准事件
- 触发下一轮 assistant 流程
- 如果服务端要求继续追问，应进入下一轮问答卡
- 如果服务端直接返回结果，应更新消息流并结束本轮

### 9.6 iOS 端排查重点

建议重点检查：

- `AIAskUserCard.swift`
- `AIChatViewModel` 或同类问答事件处理层
- `AIChatRepository`
- `AIChatMessageList.swift`
- `AIAssistantTurnView.swift`

需要确认提交后的调用链是否真的走到：

1. 收集答案
2. 构造提交事件
3. 发送到对话层
4. 收到后续消息
5. 更新列表状态

### 9.7 修复建议

建议把“提交”拆成两个明确动作：

- UI 动作：只负责收集答案、禁用重复提交、刷新按钮态
- 业务动作：负责把答案送入对话状态机，并触发下一轮 assistant 流程

如果 iOS 目前没有“提交后继续”的统一入口，建议补一个与 Web 对应的中间层事件，例如：

- `submit_user_reply`
- `continue_turn`
- `advance_after_answer`

### 9.8 验收标准

- 点击提交后，iOS 必须进入下一轮状态流转
- 对话不能停在问答卡片提交后原地不动
- 如果后端需要追问，iOS 应继续展示新的问答卡
- 如果后端返回完整答案，iOS 应继续渲染 assistant 消息
- 和 Web 的提交后行为保持一致
