# 会话相关数据模型对齐清单

> 目标：把 iOS 端 AI 对话相关的会话、回合、消息、事件、恢复态、日志态，和 Web 端保持同一套协议语义、同一套状态机、同一套回放逻辑。  
> 范围：仅覆盖 iOS 端当前 AI 对话链路，不展开 HarmonyOS / Android。  
> 原则：Web 是协议与行为的事实源，iOS 以 SwiftUI 呈现，但模型语义必须与 Web 对齐。

---

## 1. 文档目的

这份清单不是单纯的字段说明，而是一个“对齐审计清单”。

它要解决四类问题：

1. 现在 iOS 会话模型里到底有哪些数据类型。
2. 每个数据类型对应什么业务功能。
3. 哪些字段已经与 Web 对齐，哪些字段明显缺失或语义压缩。
4. 后续如果继续做“回答时间线、thinking、工具调用、恢复播放、日志审计”，应该优先补哪些字段。

---

## 2. 总体架构判断

### 2.1 当前 iOS 端可见的 AIChat 分层

从当前工程结构看，iOS 端已经不是“一个简单聊天页”，而是典型的分层 AI 对话架构：

1. `Domain` 层
   - 定义会话、回合、消息、事件、状态、错误、附件、协议模型。

2. `Application` 层
   - 负责事件 reducer、用例编排、视图状态组装、恢复流程、发送流程。

3. `Infrastructure` 层
   - 负责 WebSocket、接口 DTO、事件解码、恢复存储、Session API、Token API。

4. `Presentation` 层
   - 负责 SwiftUI 对话页、消息卡片、输入框、调试视图、来源视图、工具轨迹视图。

### 2.2 这个架构本身是否合理

结论：合理，而且方向接近 Web 的事件驱动模型。

但是，当前最大风险不是“有没有分层”，而是：

1. 模型字段是否已经足够表达 Web 的全部事件语义。
2. reducer 是否保留了足够多的中间态。
3. UI 层是否把“流式中间过程”当作最终文本去压缩展示。
4. 恢复逻辑是否把会话当成“状态快照”，而不是“事件时间线”。

如果这四点有任何一个不一致，就会出现你前面提到的那些现象：

- iOS 不能完整看到推理过程。
- iOS 在回复完成后把 thinking 区域隐藏掉。
- iOS 的“已完成 · 7s”和 Web 的“已完成 · 1m3s / 思考过程 / 时间线”不一致。
- iOS 的消息卡片、输入框、时间线、工具日志和 Web 看起来差异很大。

## 3. 当前会话相关数据模型总览

下面按“数据类型”而不是“文件名”来整理。

### 3.1 会话模型 `AIChatSession`

#### 业务职责

会话是一次完整对话上下文的容器，负责：

- 会话列表展示。
- 会话命名。
- 会话恢复。
- 会话状态切换。
- 账号隔离。
- 与服务器端 session 绑定。

#### 典型字段

- `sessionId`
- `title`
- `status`
- `createdAt`
- `updatedAt`
- `lastMessageAt`
- `accountId`
- `workspaceId`
- `resumeToken`
- `serverSessionId`
- `lastTurnId`
- `lastEventSeq`

#### 字段功能说明

- `sessionId`
  - 本地和远端对话会话的主标识。
  - 用于打开会话、恢复会话、切换会话。

- `title`
  - 用于会话列表标题。
  - 可能由第一轮用户输入自动生成，也可能由服务端返回。

- `status`
  - 表示当前会话生命周期。
  - 例如：活跃、空闲、已结束、异常。

- `createdAt` / `updatedAt`
  - 用于会话列表排序。
  - 用于本地缓存和恢复判断。

- `lastMessageAt`
  - 用于显示最近活跃时间。
  - 也常用于“排序到顶部”的逻辑。

- `accountId`
  - 账号隔离关键字段。
  - 防止不同账号读取到同一会话缓存。

- `workspaceId`
  - 如果产品存在工作区或知识库空间，这个字段用于隔离上下文。

- `resumeToken`
  - 断线重连或恢复流式事件时的凭证。
  - 很多 Web 端的恢复体验，实际上就是依赖这个字段。

- `serverSessionId`
  - 服务端真正承认的 session id。
  - 本地 `sessionId` 和服务端 `sessionId` 不一定完全相同，通常需要映射。

- `lastTurnId`
  - 最近一次回合的标识。
  - 用于恢复到正确的回合继续播放。

- `lastEventSeq`
  - 最近消费到的事件序号。
  - 这是重放、去重、断线续接的关键字段之一。

#### 与 Web 对齐检查

重点看三件事：

1. Web 是否支持多账号隔离。
2. Web 是否把恢复态绑定到 session + turn + seq。
3. Web 会话标题是不是服务端可回填、可重命名、可延迟生成。

如果 iOS 只保留 `sessionId/title/status`，那明显不够。

### 3.2 回合模型 `AIChatTurn`

#### 业务职责

回合是一次“用户发起 -> AI 处理 -> AI 返回”的完整链路容器。

它负责把以下内容绑定在一起：

- 用户输入。
- AI 生成过程。
- thinking 过程。
- 工具调用。
- 检索过程。
- 最终回复。
- 回合耗时。
- 回合是否失败。

#### 典型字段

- `turnId`
- `sessionId`
- `index`
- `role`
- `status`
- `startedAt`
- `finishedAt`
- `inputText`
- `outputText`
- `error`
- `eventCount`
- `thinkingCount`
- `toolCallCount`
- `sourceCount`
- `isRestored`

#### 字段功能说明

- `turnId`
  - 当前回合唯一标识。
  - 事件流、消息流、状态条都应绑定它。

- `sessionId`
  - 归属哪个会话。

- `index`
  - 回合序号。
  - 用于展示“第几轮”或列表排序。

- `role`
  - 当前回合的主角色。
  - 一般是 `user -> assistant` 的一问一答，但也可能包含系统事件。

- `status`
  - 回合级状态。
  - 例如：进行中、等待工具、等待输入、已完成、失败。

- `startedAt` / `finishedAt`
  - 用于显示已完成时长。
  - 也是 Web 端“已完成 · 7s”这类视觉信息的来源。

- `inputText`
  - 用户原始输入。
  - 在存在打字错误时，UI 可在本地按原文保留，不做改写。

- `outputText`
  - AI 最终输出。
  - 但注意不能只依赖它，否则 thinking、工具调用、引用来源都会丢失。

- `error`
  - 回合失败原因。
  - 用于恢复、重试、展示错误状态。

- `eventCount`
  - 该回合累计事件数。
  - 便于调试和日志核对。

- `thinkingCount`
  - thinking 事件数量。
  - 用于判断是否展示可折叠推理时间线。

- `toolCallCount`
  - 工具调用次数。
  - 用于展示“工具使用轨迹”。

- `sourceCount`
  - 引用源数量。
  - 用于来源卡片和知识库引用展示。

- `isRestored`
  - 是否来自恢复流程。
  - 用于区别实时生成和断点续播。

#### 与 Web 对齐检查

Web 端通常不是“一个回合只存一段最终文本”，而是：

- 回合是容器。
- 回合内部是事件序列。
- 消息是事件聚合后的结果。

如果 iOS 的 `AIChatTurn` 只做最终状态汇总，而没有保留事件粒度，那么会导致：

- 不能精确复现 Web 的时间线。
- 不能做展开/收起 thinking。
- 不能做恢复后继续补播。

### 3.3 消息模型 `AIChatMessage`

#### 业务职责

消息是最终渲染给用户看的最小业务单元之一。

它通常承载：

- 用户消息。
- AI 回复。
- 系统消息。
- 工具消息。
- 结果消息。
- 富文本消息。

#### 典型字段

- `messageId`
- `turnId`
- `role`
- `content`
- `parts`
- `attachments`
- `sources`
- `isStreaming`
- `isCollapsed`
- `timestamp`
- `displayMode`
- `messageType`

#### 字段功能说明

- `messageId`
  - 消息唯一标识。
  - 便于 diff、刷新、删除、重试。

- `turnId`
  - 所属回合。
  - 用于把消息和事件挂到同一上下文。

- `role`
  - 区分消息方向。
  - 一般至少包括 `user` / `assistant` / `tool` / `system`。

- `content`
  - 纯文本主体。
  - 可用于最基础的 UI 回退展示。

- `parts`
  - 消息被拆成多个片段。
  - 例如文本段、代码段、引用段、按钮段、卡片段。
  - 这是 Web 高一致性的关键字段之一。

- `attachments`
  - 附件列表。
  - 例如图片、文档、文件、音频、链接预览。

- `sources`
  - 引用来源。
  - 例如知识库文档、网页链接、工具返回数据。

- `isStreaming`
  - 是否正在流式输出。
  - 决定输入框、光标、尾部动画、滚动行为。

- `isCollapsed`
  - 是否折叠。
  - 常用于 thinking、日志、工具调用卡片。

- `timestamp`
  - 消息时间。
  - 可用于消息头部、调试日志、会话回放。

- `displayMode`
  - 渲染模式。
  - 例如普通文本、工具卡片、思考卡片、引用卡片、系统卡片。

- `messageType`
  - 更高层语义分类。
  - 用于 SwiftUI 选择不同组件树。

#### 与 Web 对齐检查

Web 端通常会把消息渲染拆成多个组件层：

- 用户输入气泡。
- 回答头部状态。
- 思考过程区。
- 工具调用区。
- 来源引用区。
- 最终正文区。

如果 iOS 的 `AIChatMessage` 只有 `content`，没有 `parts/displayMode/messageType`，就很难完全对齐 Web。

### 3.4 流式事件模型 `AIStreamEvent`

#### 业务职责

这是整个 AI 对话对齐里最关键的数据模型之一。

Web 的很多“看起来很高级”的交互，其实都来自事件流模型是否完整。

它负责：

- 接收 WebSocket 流。
- 记录每个阶段的中间状态。
- 支持恢复后补播。
- 支持时间线回放。
- 支持 tools / thinking / sources / progress 的独立展示。

#### 典型字段

- `eventId`
- `turnId`
- `seq`
- `type`
- `payload`
- `timestamp`
- `source`
- `done`
- `error`
- `checkpoint`
- `requestId`

#### 字段功能说明

- `eventId`
  - 单个事件的唯一标识。
  - 用于去重和调试。

- `turnId`
  - 事件属于哪一轮。

- `seq`
  - 事件顺序号。
  - 恢复、重放、排序、断点续播都依赖它。

- `type`
  - 事件类型。
  - 例如 `thinking`、`tool_call`、`tool_result`、`progress`、`sources`、`result`、`done`。

- `payload`
  - 真正的内容。
  - 可以是文本、结构体、数组、对象。

- `timestamp`
  - 事件时间戳。
  - 用于状态条和时长展示。

- `source`
  - 来源标识。
  - 例如 websocket、resume、replay、local-cache。

- `done`
  - 当前事件流段是否结束。

- `error`
  - 当前事件是否携带错误。

- `checkpoint`
  - 恢复点。
  - 这是 Web 端和 iOS 端恢复一致性的关键能力。

- `requestId`
  - 请求链路标识。
  - 用于把一次请求的所有事件串起来。

#### 与 Web 对齐检查

这个模型最容易发生“iOS 简化”的问题。

常见偏差包括：

1. iOS 只保留最终 `result`，没有完整中间事件。
2. iOS 没有 `seq`，导致重连后顺序不可控。
3. iOS 没有 `checkpoint`，断线恢复只能重发不能补播。
4. iOS 把 `thinking` / `tool_call` / `progress` 合并成一个字符串，丢失 UI 结构。

如果你要做“与 Web 完全一致”，`AIStreamEvent` 是必须补齐的核心模型。

### 3.5 页面状态模型 `AIChatState`

#### 业务职责

页面状态不是业务实体，但它决定 UI 如何表现业务实体。

它负责：

- 当前会话展示。
- 当前回合展示。
- 输入框内容。
- 连接状态。
- 发送状态。
- 恢复状态。
- 错误状态。
- 流式加载状态。

#### 典型字段

- `currentSessionId`
- `selectedTurnId`
- `draftText`
- `connectionStatus`
- `sendStatus`
- `loadingState`
- `pendingEvents`
- `scrollAnchor`
- `composerMode`
- `keyboardState`
- `timelineExpanded`

#### 字段功能说明

- `currentSessionId`
  - 当前页面正在看的会话。

- `selectedTurnId`
  - 当前展开或高亮的回合。

- `draftText`
  - 输入框草稿。
  - 需要支持草稿恢复。

- `connectionStatus`
  - 连接状态。
  - 例如连接中、已连接、重连中、已断开。

- `sendStatus`
  - 发送状态。
  - 例如空闲、发送中、排队中、失败。

- `loadingState`
  - 页面加载状态。
  - 包括初始加载、补播加载、历史消息加载。

- `pendingEvents`
  - 尚未落盘或尚未消费的事件。
  - 用于断线恢复和流式补齐。

- `scrollAnchor`
  - 滚动锚点。
  - 用于回到底部、定位某条回答。

- `composerMode`
  - 输入框模式。
  - 例如聊天、提问、工具、语音。

- `keyboardState`
  - 键盘弹起/收起状态。
  - 直接影响底部输入框和安全区。

- `timelineExpanded`
  - 思考时间线是否展开。
  - 这是 Web 与 iOS 最容易不一致的点之一。

#### 与 Web 对齐检查

如果 Web 的状态机里有：

- `responding`
- `thinking`
- `tooling`
- `waiting_for_input`
- `completed`

而 iOS 只保留：

- `loading`
- `done`
- `error`

那么视觉和交互就一定会偏。

### 3.6 恢复模型 `AIChatResumeStore`

#### 业务职责

恢复模型负责把“中断的流式回答”恢复成可继续显示的状态。

它支撑：

- App 退出后继续看回答过程。
- 网络断开后续播。
- 回答完成后保留过程日志。
- 回退到某个 checkpoint。

#### 典型字段

- `sessionId`
- `turnId`
- `cursor`
- `checkpoint`
- `lastEventSeq`
- `serverToken`
- `localSnapshotVersion`
- `restoredAt`

#### 字段功能说明

- `cursor`
  - 当前消费到哪里。
  - 用于继续补播。

- `checkpoint`
  - 可恢复节点。
  - 通常是服务端确认过的稳定状态。

- `lastEventSeq`
  - 最后成功接收的事件序号。

- `serverToken`
  - 服务端恢复凭证。

- `localSnapshotVersion`
  - 本地快照版本。
  - 用于判断缓存是否过期。

- `restoredAt`
  - 最近一次恢复时间。

#### 与 Web 对齐检查

如果 Web 已经支持“恢复后继续播放事件时间线”，那 iOS 也必须保留：

- 恢复序号。
- checkpoint。
- 最后事件序号。
- 服务端恢复凭证。

否则 iOS 只能做到“恢复最终结果”，不能做到“恢复过程”。

## 4. 关键业务能力与对应模型映射

下面把业务功能直接映射到模型，方便后面拆工单。

### 4.1 会话列表

依赖字段：

- `AIChatSession.sessionId`
- `title`
- `status`
- `updatedAt`
- `lastMessageAt`
- `accountId`

核心要求：

- 账号隔离。
- 排序正确。
- 会话标题准确。
- 删除/隐藏/恢复状态明确。

### 4.2 继续对话

依赖字段：

- `sessionId`
- `turnId`
- `lastEventSeq`
- `resumeToken`
- `checkpoint`

核心要求：

- 继续对话时不能丢上下文。
- 不能把新消息和旧回合混在一起。

### 4.3 事件时间线

依赖字段：

- `AIStreamEvent.seq`
- `AIStreamEvent.type`
- `AIStreamEvent.payload`
- `AIStreamEvent.timestamp`

核心要求：

- 顺序稳定。
- 事件可回放。
- 事件可折叠/展开。

### 4.4 thinking 推理区

依赖字段：

- `type == thinking`
- `payload`
- `seq`
- `timestamp`
- `isCollapsed`

核心要求：

- 不是纯文本拼接。
- 要保留独立条目。
- 完成后也不能直接销毁。

### 4.5 工具调用区

依赖字段：

- `type == tool_call`
- `type == tool_result`
- `payload`
- `requestId`
- `seq`

核心要求：

- 工具发起、执行、返回要分层。
- 工具结果不能只显示在最终答案里。

### 4.6 来源引用区

依赖字段：

- `sources`
- `messageType`
- `parts`

核心要求：

- 引用来源可见。
- 来源内容可展开。
- 来源和正文分离渲染。

## 5. iOS 端当前最可能不对齐的部分

结合你前面描述的现象，当前重点怀疑这些不对齐点：

### 5.1 thinking 被当成临时态，而不是持久事件

表现：

- iOS 回复完成后，推理过程隐藏。
- Web 仍可看到完整时间线。

原因：

- iOS 可能只把 thinking 放在 `loadingState` 里，而没有落到 `AIStreamEvent` 或 `AIChatMessage.parts`。

应对：

- thinking 必须有独立模型。
- thinking 必须能持久化。
- thinking 必须能在完成后继续折叠/展开。

### 5.2 回答头部状态与时长展示不一致

表现：

- Web 展示“已完成 · 1m3s”“回答中 · 1m3s”。
- iOS 可能只展示“完成/加载中”。

原因：

- 缺少 `startedAt`、`finishedAt`、`statusStartedAt` 或等价字段。

应对：

- 给回合和状态条增加稳定的时间源。

### 5.3 时间线事件粒度不够

表现：

- Web 的时间线里有很多步骤。
- iOS 只看到少量合并后的文案。

原因：

- `type` 或 `parts` 不够细。
- reducer 合并过度。

应对：

- 保留原始事件。
- 事件层与渲染层解耦。

### 5.4 恢复态丢失

表现：

- iOS 重启后只能看到最终答案。
- 不能看到完整中间过程。

原因：

- 只有快照，没有事件游标。

应对：

- 补齐 `checkpoint`、`lastEventSeq`、`cursor`。

### 5.5 多账号隔离不充分

表现：

- 切换账号后历史对话混乱。

原因：

- 会话存储没有严格绑定 `accountId`。

应对：

- 会话、回合、草稿、恢复存储都要绑定账号维度。

## 10. 工程落地建议

### 10.1 不要先改 UI，先补模型语义

原因很简单：

- UI 只是表现层。
- 语义不一致，UI 永远对不齐。

### 10.2 事件优先于最终文本

Web 对齐的根本不是“最终回答长得像不像”，而是：

- 事件有没有被完整接住。
- 事件有没有被正确排序。
- 事件有没有被正确分层。

### 10.3 thinking 必须可持久化

不要把 thinking 当成临时 loading 文案。

应该把它看成：

- 一个事件。
- 一个可回放时间线。
- 一个可折叠的结构化区块。

### 10.4 恢复逻辑必须依赖序列号

没有 `seq`，恢复就只能“猜顺序”。

一旦猜顺序，Web 和 iOS 必然漂移。

## 11. 建议验收标准

### 11.1 数据模型验收

必须能回答以下问题：

1. 一条回答的 thinking 在哪里存？
2. 工具调用在什么字段里存？
3. 事件顺序靠什么字段保证？
4. 断点恢复靠什么字段继续？
5. 多账号怎么隔离？
6. 一个回合的起止时间怎么计算？

### 11.2 UI 对齐验收

必须能在 iOS 上看到：

- 回答中状态条。
- 已完成耗时。
- 可展开的 thinking。
- 工具调用轨迹。
- 来源引用。
- 完整消息内容。

### 11.3 恢复验收

必须验证：

- App 重启后仍可继续看已生成事件。
- 网络中断后可继续补播。
- 成功后不会把思考过程直接丢掉。

## 12. 当前结论

当前 iOS 端会话相关模型的基础架构方向是对的，但是否“与 Web 完全对齐”，关键不在于有没有会话、消息、回合这些概念，而在于：

1. 有没有把事件流当一等公民。
2. 有没有把 thinking / tool / source / progress 结构化。
3. 有没有把恢复状态做成可回放。
4. 有没有把账号和工作区维度纳入会话存储。

如果某一层只是“最终结果”，而不是“事件过程”，那就一定会出现你现在看到的 iOS 和 Web 差距。
