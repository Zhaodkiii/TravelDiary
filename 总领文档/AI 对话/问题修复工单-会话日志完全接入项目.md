# 问题修复工单 - 会话内日志完全接入项目

## 1. 工单目标

将 AI 对话会话内的日志能力从“局部调试信息”提升为“项目级完整可观测链路”，覆盖接口请求、WebSocket 连接、事件流处理、消息状态变化、工具调用、恢复重连、错误处理和 UI 操作。

本工单只做文档方案，不修改业务代码，不改动后端协议，不涉及 HarmonyOS、Android。

## 2. 问题描述

当前会话内日志存在典型缺口：

- 日志内容分散在不同层，无法串成完整会话链路
- 接口请求、WS 事件、UI 状态和用户操作之间没有统一关联
- 恢复、重连、失败、重试等关键步骤缺少可追踪日志
- 只有部分调试页能看到局部输出，正式会话页缺少稳定日志入口
- 日志粒度不足，无法定位“哪一步开始、哪一步结束、哪一步失败”

结果是：

- 出问题时难以复盘
- 事件流难以对齐
- 会话恢复行为难以验证
- 前端与后端排查成本高

## 3. 对齐目标

日志系统应满足以下目标：

1. 任何一轮会话都能回放关键步骤。
2. 接口操作必须可追踪到具体 turn、session 和用户动作。
3. WebSocket 连接、消息发送、事件消费、恢复重连都要有对应日志。
4. 日志展示应服务于排障和验收，而不是只做开发调试。
5. 所有日志要与当前会话上下文绑定，避免变成无法关联的独立文本。

## 4. 日志范围

需要接入日志的对象包括：

- 页面进入与退出
- 会话列表切换
- 新建会话
- 恢复会话
- 发送消息
- 停止生成
- 重新生成
- 继续追问
- 用户补充输入
- 接口请求与响应
- WebSocket 连接、断开、重连、心跳
- 事件接收、去重、排序、归档
- tool call / tool result
- sources / wait_for_input / error / done
- 键盘聚焦与输入框交互
- 展开 / 折叠 `thinking`

## 5. 日志设计原则

### 5.1 链路化

每一条日志都必须能归属到：

- `session_id`
- `turn_id`
- `client_message_id`
- `event_seq`
- `request_id` 或服务端回包标识

### 5.2 分层化

日志至少分为以下层级：

- 页面层：用户点击、页面切换、状态展示
- 业务层：新建会话、发送消息、恢复、重试、停止
- 协议层：HTTP、WebSocket、事件流、去重、心跳
- 数据层：持久化、缓存、恢复加载、归档

### 5.3 可读性

日志内容要能回答这些问题：

- 谁触发的
- 在哪一步触发的
- 输入是什么
- 结果是什么
- 成功还是失败
- 下一步发生了什么

### 5.4 安全性

日志禁止直接输出：

- Token
- 密码
- 认证头完整值
- 私密会话内容的明文原样
- 个人隐私数据

必要时应做脱敏处理。

## 6. 日志体系建议

### 6.1 日志类型

建议将会话日志拆成以下几类：

- `session.lifecycle`
- `session.ui`
- `session.network`
- `session.websocket`
- `session.event`
- `session.reducer`
- `session.persistence`
- `session.error`
- `session.recovery`
- `session.tool`

### 6.2 推荐字段

每条日志至少包含：

- 时间戳
- 日志级别
- 模块名
- 操作名
- session_id
- turn_id
- client_message_id
- 事件 seq
- 简要描述
- 结果状态
- 错误码或错误类型

## 7. 会话日志接入点

### 7.1 页面进入

需要记录：

- 当前页面
- 当前账号
- 当前会话是否存在
- 是否进入恢复流程
- 是否命中缓存

### 7.2 新建会话

需要记录：

- 点击新建会话时间
- 新会话初始参数
- 是否成功创建 session
- session_id 生成结果
- 是否同步到状态仓库

### 7.3 发送消息

需要记录：

- 输入框内容长度
- 发送按钮状态
- client_message_id
- 绑定的 session_id / turn_id
- 请求参数摘要
- 请求发出结果
- 服务端响应摘要

### 7.4 WebSocket 连接

需要记录：

- 连接 URL 类型
- 认证方式
- 连接建立结果
- 首个订阅 turn
- 心跳发送与 pong 接收
- 重连次数
- 断开原因

### 7.5 事件处理

需要记录：

- 收到事件类型
- seq
- 去重结果
- reducer 处理结果
- UI 状态变化
- 是否追加到 thinking / answer / tools / sources

### 7.6 恢复与重连

需要记录：

- 恢复触发原因
- 恢复前最后 seq
- 恢复请求参数
- 恢复结果
- 恢复后首个事件
- 恢复后 UI 是否完全重建

### 7.7 停止、重试、追问

需要记录：

- 用户点击动作
- 当前 turn 状态
- 服务端操作结果
- UI 是否切换为停止态或等待态
- 是否进入新的 turn

## 8. 日志与界面联动

日志不能只存后台，它必须和 iOS 界面中的“会话内日志视图”联动。

建议联动规则：

- 页面顶部显示当前 turn 摘要
- 日志区域显示关键步骤时间线
- 点击一条日志可定位到对应消息卡片或事件卡片
- 发生错误时，日志区域自动跳到错误前后事件
- 恢复成功后，日志区域应保留本轮链路，不自动清空

## 9. 关键步骤清单

每一轮会话建议至少记录以下步骤：

1. 页面进入
2. 会话选择 / 新建
3. 输入框聚焦
4. 用户输入
5. 发送消息
6. 请求签发 / 认证准备
7. WebSocket 建连
8. start_turn / subscribe_turn
9. 收到 thinking
10. 收到 tool_call
11. 收到 tool_result
12. 收到 sources
13. 收到 wait_for_input
14. 收到 error
15. 收到 done
16. 会话恢复
17. 用户重试 / 停止 / 继续

## 11. 实施建议

### 11.1 接入顺序

建议按以下顺序接入：

1. 先统一日志字段和上下文
2. 再接入页面操作日志
3. 再接入接口请求/响应日志
4. 再接入 WebSocket 与事件流日志
5. 最后补恢复、错误和追问链路

### 11.2 日志输出位置

建议至少有三处输出：

- 控制台/开发日志
- 会话内日志面板
- 调试页完整时间线

其中会话内日志面板应面向正式排障，而不是只在 DEBUG 存在。

## 12. 验收标准

以下内容必须通过验收：

- 每次发送消息都能看到完整日志链路
- 每次接口请求都能定位到对应 turn
- 每次 WS 建连 / 重连都能看到原因和结果
- 每次事件消费都能看到 seq 和处理结果
- 每次恢复都能看到恢复前后状态变化
- 每次失败都能看到失败点与后续动作
- 日志不泄露 Token 和敏感内容
- 会话内日志可以帮助复盘一轮完整对话

## 13. 风险点

- 如果日志只分散在网络层，无法复盘 UI 问题
- 如果日志只分散在 UI 层，无法复盘协议问题
- 如果没有 session / turn 绑定，日志会失去价值
- 如果恢复流程不写日志，线上问题很难定位
- 如果敏感字段未脱敏，日志会带来安全风险

## 14. 待确认项

1. 会话内日志是否只对开发态可见，还是正式版也保留入口。
2. 日志面板是否需要支持复制、筛选、折叠和搜索。
3. 是否需要把日志与 `thinking` 面板合并显示。
4. 是否需要为每个 turn 提供独立日志导出。

## 15. 建议标题规范

后续同类工单建议统一命名为：

- `问题修复工单-<问题点>-对齐Web.md`
- `问题修复工单-<问题点>-日志接入.md`
- `问题修复工单-<问题点>-恢复与重建.md`

这样可以和当前 `AI 对话` 目录下的输入框、状态条、`thinking` 对齐工单保持一致。

## 16. 会话列表日志接入补充

会话列表也必须接入项目日志，不能只记录单条会话页面的行为。

### 16.1 需要记录的列表行为

- 列表页进入
- 列表数据请求
- 列表刷新
- 列表分页或游标加载
- 列表切换会话
- 列表搜索或筛选
- 列表空态
- 列表失败态
- 会话删除、归档、置顶、恢复（如有）

### 16.2 需要绑定的上下文字段

- account_id
- session_id
- 当前筛选条件
- 页码或游标
- 命中缓存与否
- 请求耗时
- 返回条数
- 当前选中项

### 16.3 目标

会话列表日志要能回答：

- 用户是如何进入某个会话的
- 为什么列表刷新后内容发生变化
- 为什么某个会话被选中或切换
- 为什么列表为空或失败

## 17. 异常报错统一接入项目通知系统

当前不应继续使用“会话头部错误”作为唯一错误出口。

### 17.1 调整原则

- 会话头部只保留 turn 级摘要和局部状态
- 异常报错统一进入项目通知系统
- 通知系统承担错误、警告、成功和必要动作
- 不在会话页内维护多套不同的错误展示

### 17.2 适用异常

- 接口请求失败
- WebSocket 断开或重连失败
- 事件解析失败
- 恢复失败
- 认证失效
- 权限不足
- 空数据或协议不一致
- 用户非法操作

### 17.3 通知系统接入目标

通知系统应成为异常的统一出口，页面只负责触发和订阅，不负责重新发明错误展示。

建议对齐的项目级通知宿主为：

- `SupportClient/SupportClient/Projects/App/Sources/App/Notification/NotificationHostView.swift`

### 17.4 验收标准

- 同一类错误只从通知系统展示
- 会话头部不再承担全局错误提示职责
- 通知能够区分错误等级和操作能力
- 日志、会话页、通知系统三者可以互相定位同一错误
