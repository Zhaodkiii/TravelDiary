# 问题排查工单 - 会话列表成功响应后仍提示加载失败

## 1. 工单目标

排查并修复“会话列表接口已成功返回，但 iOS 端仍提示会话加载失败”的问题，确保项目日志、会话列表状态和通知系统三者一致。

本工单只做问题分析与排查方案，不实现业务代码，不修改后端协议，不涉及 HarmonyOS、Android。

## 2. 现象描述

从会话日志可以看到以下链路：

```text
AIChatSessionLog step=24 category=session.ui action=session_list_refresh ai_trace_id=AIC-20260801-075458-44AEEE16 account_id=860 message=开始加载会话列表
AIChatSessionLog step=25 category=session.network action=list_sessions_start ai_trace_id=AIC-20260801-075458-44AEEE16 request_id=REQ-84B1176D result=inProgress message=GET /api/v1/sessions limit=50 offset=0
AIChatSessionLog step=26 category=session.network action=list_sessions_response ai_trace_id=AIC-20260801-075458-44AEEE16 request_id=REQ-84B1176D result=success message=status=200 cost=0.032s bytes=21299 limit=50 offset=0
AIChatSessionLog step=27 category=session.error action=user_notification ai_trace_id=AIC-20260801-075458-44AEEE16 account_id=860 result=failure message=会话列表加载失败: 会话加载失败，请稍后重试。
Notification enqueued: 875B76B1-945F-4E5D-8EF1-E68A1B71F3FC
```

关键信号是：

- 网络请求已经成功返回 `200`
- 响应体大小正常，说明不是空响应
- 失败发生在网络层之后
- 最终错误被送入通知系统

## 3. 初步判断

这不是“请求失败”，而是“响应成功后，在业务解析、列表组装、状态落盘或 UI 显示阶段被误判为失败”。

因此问题重点应放在以下几层：

1. 接口响应解析是否失败。
2. 列表数据映射是否失败。
3. 空列表或部分字段缺失是否被当成失败。
4. 状态仓库是否在写入前后抛错。
5. UI 是否把“空数据”“局部字段缺失”“恢复中”错误映射成“加载失败”。
6. 通知系统是否被过早触发，导致成功响应后仍弹错。

## 4. 可能根因

### 4.1 解析层错误

服务端返回成功，但客户端对响应体的解析失败，例如：

- 字段名不匹配
- 分页结构不匹配
- 某个可选字段被错误地当成必填
- 时间戳、枚举、嵌套对象解析失败

如果这种情况存在，日志里通常会出现：

- HTTP 成功
- 业务解析抛错
- 最终进入统一错误通知

### 4.2 业务层误判

列表数据可能已经成功返回，但客户端在组装列表时做了错误判断，例如：

- 列表为空就直接判失败
- 缺少某些非关键字段就判失败
- 只要有一条数据格式异常就整批失败

### 4.3 状态写入异常

网络数据已取回，但写入 session store、view model、缓存或分页游标时失败。

这类问题常见于：

- 空指针或越界
- account scope 不匹配
- 数据合并逻辑冲突
- 列表排序后状态丢失

### 4.4 通知触发过早

`user_notification` 可能在以下时机被触发：

- 还没确认业务层是否成功
- 只要某个中间步骤异常就触发
- 错误被二次包装，导致成功响应也走失败分支

这会让“成功响应”和“错误通知”同时出现。

## 5. 需要排查的链路

建议按以下顺序排查：

### 5.1 网络层

确认：

- `GET /api/v1/sessions` 是否返回完整 JSON
- `bytes=21299` 对应的 body 是否结构正确
- 是否存在隐藏的后端业务码失败
- 是否响应头或包裹层异常

### 5.2 解析层

确认：

- 响应 DTO 是否与后端一致
- 列表项字段是否全部可解析
- 是否存在未处理的空值或新增字段
- 是否某个字段导致整包 decode fail

### 5.3 组装层

确认：

- 列表是否成功映射到 domain model
- 是否有分页合并逻辑错误
- 是否有去重、排序、过滤导致的异常
- 是否 account scope 导致数据被过滤为空

### 5.4 状态层

确认：

- refresh 状态是否在成功后正确归位
- loading / empty / error 是否互相覆盖
- 是否成功后又被其他异步任务写回 error

### 5.5 通知层

确认：

- `user_notification` 是否只应在真正失败时触发
- 成功响应后是否还有后续校验失败
- 通知消息是否来自统一错误入口
- 会话头部和通知系统是否同时发错

## 6. 排查重点

结合当前日志，最值得优先检查的是：

1. `list_sessions_response` 成功后，是否还有后续 decode / map / merge 步骤报错。
2. `session_list_refresh` 完成后，状态是否被错误地设置为 failure。
3. `user_notification` 的触发条件是否过宽。
4. 通知系统是否把“空列表/局部异常”统一包装成“会话加载失败”。
5. 会话列表的日志链路是否缺少一个明确的“列表成功完成”事件。

## 7. 建议修复方向

### 7.1 增加明确的成功完成日志

在列表成功解析、成功落盘、成功渲染后增加明确日志，例如：

- `list_sessions_decode_success`
- `list_sessions_store_success`
- `list_sessions_render_success`

这样可以定位失败发生在哪一层之后。

### 7.2 区分三种状态

必须严格区分：

- 网络请求成功
- 业务列表成功
- UI 完成渲染

不能把这三者混成一个“成功/失败”开关。

### 7.3 收窄通知触发条件

通知系统只在以下情况触发：

- 网络失败
- 解析失败
- 状态写入失败
- 真正业务失败

不能因为空列表、局部字段缺失、加载中间态就直接弹“加载失败”。

### 7.4 保留原始失败原因

通知消息不应只显示：

- `会话加载失败，请稍后重试`

还应保留内部原因分类，例如：

- `decode_failed`
- `store_failed`
- `merge_failed`
- `empty_result`
- `unauthorized`

这样项目日志才能真正用于排查。

## 8. Plain Text 排查链路

```text
用户点击刷新
  ↓
session_list_refresh
  ↓
list_sessions_start
  ↓
list_sessions_response 200 OK
  ↓
decode / map / merge / store
  ↓
如果这里失败 → user_notification
  ↓
如果这里成功 → 列表渲染成功
```

当前问题大概率出在 `list_sessions_response` 之后的某个阶段。

## 9. 验收标准

修复后应满足：

- 接口成功返回时，不再误弹加载失败
- 失败通知只在真正失败时出现
- 会话列表有明确的成功完成日志
- 成功与失败状态不会互相覆盖
- 通知系统、会话列表、日志三者一致

## 10. 风险点

- 如果只改通知展示，不改业务状态判断，问题会反复出现
- 如果只看 HTTP 200，不看 decode 与 store，排查会继续失真
- 如果日志不补成功分支，后续问题仍难定位

## 11. 待确认项

1. `/api/v1/sessions` 的实际响应结构是否发生了字段漂移。
2. `AIChatSessionLog` 中是否存在 decode/store 失败的更详细日志。
3. `user_notification` 触发点是否由 session store、view model 或 reducer 发出。
4. 会话列表为空时，产品期望是显示空态还是显示失败。
