# 问题修复工单 - 顶部状态条与 Thinking 可展开区域对齐 Web

## 1. 工单目标

将 iOS 对话页中的顶部状态条、`thinking` 推理区域、事件时间线和最终回复的展示关系，调整为与 Web 端一致的可回溯、可展开、可恢复结构。

本工单只描述 iOS SwiftUI 的对齐方案，不实现业务代码，不涉及 HarmonyOS、Android，也不改动后端协议。

## 2. 问题描述

当前 iOS 端存在两个明显偏差：

1. 顶部状态条只表现“流式中的短暂状态”，在 AI 回复完成或页面恢复后，状态可见性不稳定，用户无法持续看到“已完成 · 7s”这类摘要信息。
2. `thinking` 推理区域缺少稳定的可展开承载层，AI 恢复完成后，推理过程容易被隐藏，导致用户无法回看本轮推理链路。

这会让 iOS 端从“可回溯的对话卡片”退化为“仅展示最终答案”，与 Web 端的体验不一致。

## 3. 现象对比

### 3.1 Web 端预期行为

Web 端的对话卡片应具备以下特征：

- 顶部有明确的轮次状态摘要
- `thinking` 区域可展开、可收起
- 完成后仍保留推理入口
- 恢复或刷新后仍能看到已完成事件链路
- 事件时间线与最终回答处于同一 turn 语义下

### 3.2 iOS 当前行为

当前 iOS 端更像是：

- 只在流式阶段短暂展示状态
- 完成后将推理过程从当前卡片中移除
- 恢复后仅保留最终答案
- 推理时间线更像调试信息，而不是正式能力

### 3.3 用户感知

用户会产生以下感受：

- “我知道 AI 答完了，但不知道它怎么想的”
- “刚刚还能看到的推理过程，恢复后就没了”
- “iOS 和 Web 不是同一个产品体验”

## 4. 对齐基准

对齐目标不是“把 Web 样式搬过来”，而是保持以下语义一致：

- 同一轮对话的状态摘要一致
- 同一轮对话的 `thinking` 是否可展开一致
- 完成态是否仍可回看一致
- 恢复后的可见内容一致
- 工具调用、来源、追问、进度事件是否进入同一事件面板一致

## 5. 根因判断

结合当前 iOS 端表现，问题大概率来自以下几类设计偏差：

### 5.1 `thinking` 被当成瞬时状态

`thinking` 在 iOS 里更像“流式中间态”，而不是“turn 级持久数据”。

结果是：

- `done` 后被清理
- 恢复后没有重新挂回 UI
- 用户无法从最终答案回到过程

### 5.2 状态条只绑定网络状态，没有绑定 turn 状态

顶部状态条如果只跟连接、流式中断、页面 active 等短期状态关联，就会出现：

- 完成后消失
- 重连后回到默认态
- 无法表达“本轮已完成但仍可展开查看”

### 5.3 展示层级不统一

iOS 当前把事件时间线、推理内容、最终回答分散在不同层级，导致：

- 用户不知道哪里才是“本轮完整语义”
- 推理信息缺少稳定入口
- 恢复后组件重建顺序可能丢失推理区

## 6. 优化方案

### 6.1 重新定义 turn 级展示结构

建议将每一轮对话的展示结构固定为：

1. 顶部状态条
2. 最终回答
3. 可展开的 `thinking` 推理区
4. 工具调用与结果
5. 来源与引用
6. 追问卡片或补充输入

这样完成后只改变状态，不改变结构。

### 6.2 顶部状态条改成摘要态

顶部状态条应保留轮次摘要，而不是仅显示流式过程。

建议状态语义：

- `思考中 · 7s`
- `已完成 · 7s`
- `已中断 · 7s`
- `恢复中 · 7s`
- `等待输入 · 7s`

要求：

- 完成后仍显示摘要
- 允许点击进入该 turn 的事件面板
- 不因页面恢复而消失

### 6.3 Thinking 改成可展开面板

`thinking` 不再是短暂的一段文本，而是一个完整面板。

面板应支持：

- 默认展开或默认折叠由产品策略控制
- 展开后可查看事件时间线
- 收起后仍保留入口
- 完成态和恢复态都可展开
- 内容不足时显示简化态，而不是整块消失

### 6.4 事件时间线必须保留 turn 语义

`thinking` 面板内应保留：

- `thinking`
- `tool_call`
- `tool_result`
- `progress`
- `stage_start`
- `stage_end`
- `sources`
- `wait_for_input`
- `error`

这意味着：

- 完成后仍能回看推理链路
- 恢复后仍能重建相同层级
- 工具和来源不会游离到别的区域

## 7. SwiftUI 落地建议

### 7.1 组件结构

建议将当前 assistant 卡片拆成以下语义层：

- `AIChatTurnCard`
- `AIChatTurnStatusBar`
- `AIChatTurnAnswerBody`
- `AIChatTurnThinkingPanel`
- `AIChatTurnEventTimeline`
- `AIToolTraceCard`
- `AISourceReferencesView`
- `AIAskUserCard`

### 7.2 状态模型

每个 turn 至少需要以下状态字段：

- 当前状态：`thinking` / `streaming` / `completed` / `interrupted` / `waiting_input`
- 已耗时：用于顶部状态条
- `thinking` 是否可展开
- 当前是否默认展开
- 是否存在工具调用
- 是否存在来源引用
- 是否存在追问卡片

### 7.3 恢复策略

恢复后不能只恢复最终消息，必须恢复整个 turn 结构：

- 状态条
- 最终回答
- 推理区展开状态
- 事件时间线
- 工具结果
- 来源引用

## 9. 验收标准

以下情况必须通过验收：

- AI 完成后，顶部状态条仍保留摘要
- `thinking` 面板在完成后仍可展开
- 页面恢复后，推理过程不丢失
- 工具调用、来源、追问在同一 turn 内可追溯
- Web 和 iOS 的可见语义一致
- 进入下一轮对话时，不会污染上一轮的展开状态

## 10. 风险点

- 如果状态条与网络连接状态耦合过深，完成态会被错误清空
- 如果 `thinking` 仍以临时文本存储，恢复后必然丢失
- 如果事件时间线只在调试模式出现，正式体验就无法和 Web 对齐
- 如果折叠/展开状态不按 turn 保存，页面刷新后会产生体验漂移

## 11. 待确认项

1. Web 端顶部状态条完成态是否固定显示“已完成 · 耗时”。
2. Web 端 `thinking` 面板默认是展开还是折叠。
3. 完成后是否允许继续看到全部事件时间线，还是只显示摘要。
4. 恢复后的默认展开策略是否与首次进入一致。

## 12. 建议落地顺序

1. 先把 turn 状态提升为持久结构。
2. 再让顶部状态条绑定 turn 生命周期。
3. 然后把 `thinking` 改成可展开面板。
4. 最后统一恢复逻辑和展开状态记忆。

这样可以先保证“看得见、找得到、恢复得回”，再处理更细的视觉和动画一致性。
