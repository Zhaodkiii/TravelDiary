# P3 事件完整渲染

> 本文档只补充 P3 阶段的 iOS 事件完整渲染方案，不实现任何 Swift、Python、TypeScript 或配置代码。

## 1. 阶段定位

P3 的目标是把 P2 已具备的基础聊天入口，升级为“能够完整消费 DeepTutorSerevr 流式事件”的 SwiftUI 渲染层。

P3 关注的不是“能不能发消息”，而是“收到什么事件、如何稳定落到页面上”。也就是说，P3 解决的是：

```text
StreamEvent
    ↓
事件分类 / 去重 / 聚合
    ↓
AIChatState
    ↓
消息气泡 / 草稿 / 工具卡 / 来源卡 / AskUser 卡 / 状态条 / 事件时间线
    ↓
SwiftUI 页面
```

P3 不是 P4 的会话恢复，也不是 P5 的完整产品化。P3 只聚焦事件完整渲染和事件语义稳定化。

P3 的关键价值：

- 让 `thinking`、`stage_start`、`tool_call`、`tool_result`、`sources`、`wait_for_input`、`error`、`done` 等事件在 iOS 上有明确视觉落点。
- 让 assistant draft、工具调用轨迹、来源引用、等待用户输入卡片形成可解释的中间态。
- 固定 event reducer 和 UI 组件的职责边界，避免继续把所有事件揉成一条文本。
- 为 P4 会话恢复、P5 产品化和后续多端一致性提供稳定事件语义。

P3 的完成标准不是“所有事件都做成漂亮卡片”，而是：

- 每类事件都有明确 UI 策略。
- 同一轮 turn 中事件展示不乱序、不重复、不丢关键状态。
- `done` 前的中间态可解释，`done` 后结果可沉淀。
- `error` 是终态或中间态时，UI 行为不同但语义清楚。
- `wait_for_input` 不再只是调试字符串，而是有完整卡片或基础交互。

### 4.3 当前 reducer 的关键特征

当前 reducer 有几个对 P3 很重要的事实：

| 特征 | 现状 | P3 影响 |
| --- | --- | --- |
| 去重 | 使用 `turn_id + seq` 作为 eventKey | P3 要继续依赖，避免重复渲染 |
| session 更新 | 通过 `session` / `session_meta` 建立会话标题 | P3 可继续使用 |
| content 聚合 | `assistantDraft += event.content` | P3 把多段回复合并成一个草稿 |
| tool 追踪 | 通过 `call_id` / `tool_name` 建 traceGroups | P3 可以正式化为工具卡 |
| sources 追踪 | 通过 `metadata["sources"]` 解析引用 | P3 把 sources 纳入结果结构 |
| ask_user | 通过 `metadata["questions"]` 解析问题列表 | P3 把等待输入变成 UI 卡片 |
| error 处理 | terminal error 进入 failed | P3 需要区分终态错误和可恢复错误 |
| done 处理 | 将草稿固化为 assistant message | P3 要确认最终文本、trace 和 sources 的收口时机 |

### 4.4 当前代码的一个现实偏差

当前 `appendEventToDraft` 在 reducer 中是空实现，这意味着：

- 事件文本的核心承载仍集中在 `content` 和 `result`。
- `thinking`、`observation`、`progress`、`stage_start`、`stage_end`、`unrecognized` 目前更多是状态或调试语义，而不是文本拼接语义。
- P3 需要明确这些事件是“单独卡片”“状态条”“调试事件条”，还是“附加到 draft 下方的辅助信息”。

这不是 bug 文档，而是 P3 的设计输入。

## 6. 目标渲染架构

### 6.1 渲染总图

```text
StreamEvent
    ↓
AIChatEventDecoder
    ↓
AIChatEventReducer
    ↓
AIChatState
    ├── messages
    ├── assistantDraft
    ├── traceGroups
    ├── sourceReferences
    ├── pendingAskUserCard
    ├── connectionState
    └── userFacingError
    ↓
AIChatRootView
    ├── AIChatErrorBanner
    ├── AIChatEmptyStateView
    ├── AIChatMessageList
    │   ├── AIChatMessageBubble
    │   ├── AIToolTraceCard
    │   └── AISourceReferencesView
    ├── AIAskUserCardView
    └── AIChatComposer
```

### 6.2 P3 核心原则

1. 一个事件至少有一个明确落点。
2. 同一事件不在多个位置重复造成“假信息”。
3. terminal 与 non-terminal 错误要区分。
4. 事件顺序以 `seq` 为准，显示可以做聚合，但不能乱序。
5. 用户能理解“AI 正在思考”“AI 正在调用工具”“AI 要求补充信息”“AI 给出来源”“AI 已完成”。

### 6.3 组件职责边界

| 层 | P3 职责 | 不承担 |
| --- | --- | --- |
| `AIChatRootView` | 页面级事件容器、状态切换、入口维护 | 不决定事件语义 |
| `AIChatMessageList` | 消息区主渲染与滚动 | 不解析原始 JSON |
| `AIChatMessageBubble` | 单条消息展示、assistant markdown、插槽 | 不做事件聚合 |
| `AIToolTraceCard` | tool call/result 展开与收起 | 不决定 tool 何时出现 |
| `AISourceReferencesView` | 来源列表、链接和摘要 | 不解析 sources JSON |
| `AIAskUserCardView` | 问题、选项、自定义输入 | 不决定 waitingForUser 的语义 |
| `AIChatEventReducer` | 事件语义到状态的转换 | 不直接做视图层样式 |

### 6.4 Web → SwiftUI 组件一一对应原则

P3 的“完全对齐”不是把 Web DOM 结构照搬到 SwiftUI，而是把每个视觉/交互组件的职责、出现条件、状态切换、动画和刷新语义保持一致。也就是说：

- 组件名称可以平台化。
- 组件职责不能变。
- 同一事件在 Web 和 SwiftUI 的可见层级必须一致。
- Web 端的“列表 / 卡片 / 折叠 / loading / 跟随滚动 / 暂存草稿 / 交互确认”都要在 SwiftUI 找到等价物。

| Web 参考组件/语义 | SwiftUI 对应组件 | 对齐目标 |
| --- | --- | --- |
| `ChatMessages` | `AIChatMessageList` | 消息流主容器、自动滚动、草稿插入 |
| `AssistantResponse` | `AIChatMessageBubble` 内的 assistant 分支 | Markdown 正文、流式追加、完成收口 |
| `AskUserOptions` | `AIAskUserCardView` | 问题、选项、自定义输入、提交 |
| `AssistantActivity` / `TracePanels` | `AIToolTraceCard` + 轻量事件时间线 | 工具调用与中间态可视化 |
| `ContextReferenceTree` / sources 区 | `AISourceReferencesView` | 来源标题、摘要、链接 |
| `SessionLoadingView` | `AIChatEmptyStateView` + loading overlay | 会话加载、取消、慢加载提示 |
| `ChatComposer` | `AIChatComposer` | 输入、能力/上下文选择、发送、停止 |
| `FilePreviewDrawer` / side panel | P3 可暂不完整实现，只保留“打开附件”接口 | 不把附件预览混进主消息区 |
| `Conversation row / session sheet` | `AIChatSessionListView` | 历史会话入口、刷新、选择、重命名、删除 |

P3 的原则是：

1. Web 有明显独立组件的，SwiftUI 也必须有独立组件。
2. Web 上“折叠/展开”的东西，SwiftUI 也必须折叠/展开，而不是一股脑展开。
3. Web 上“事件附着在消息下方”的，SwiftUI 也必须附着在同一层级。
4. Web 上“loading 与慢加载提示”的，SwiftUI 也必须保留等价状态。
5. Web 上“草稿和最终消息分离”的，SwiftUI 也必须分离。

### 6.5 组件级完全对齐范围

P3 要求对齐到每一个可见组件，而不是只对齐页面标题。

| 组件级元素 | 对齐要求 |
| --- | --- |
| 顶部导航标题 | 会话名 / `AI 对话` 规则一致 |
| 错误条 | 固定顶部出现、可见、不会盖住内容 |
| 空态图标和文案 | 对应“开始/连接失败/加载中”三态 |
| 消息气泡左右布局 | user 右，assistant 左 |
| assistant Markdown 容器 | 文本块、代码块、列表、引用的基本排版一致 |
| 草稿 loading | streaming 时出现小 loading / 处理中的视觉反馈 |
| tool trace 卡 | 默认折叠，点开查看调用与结果 |
| source references 卡 | 列表型、可点击、摘要型 |
| AskUser 卡 | 问题、选项、自定义输入、提交按钮 |
| 会话列表 sheet | 刷新、选择、重命名、删除 |
| 新对话按钮 | 清空当前会话并回到起始状态 |
| 停止按钮 | streaming 中可见，结束后消失 |

## 8. 渲染样式与动画

### 8.1 样式转换总原则

Web 端的视觉很大一部分来自类名、变量和小范围动效，SwiftUI 端要做的是把这些语义翻译成可维护的样式系统，而不是复制 CSS 选择器。

| Web 样式语义 | SwiftUI 落点 | 说明 |
| --- | --- | --- |
| `bg-[var(--card)]` / `bg-[var(--background)]` | `Color(.secondarySystemBackground)` / `Color(.systemBackground)` | 区分卡片与页面底色 |
| `border-[var(--border)]` | 细边框 / stroke | 不追求每个像素完全一致，但层级一致 |
| `muted-foreground` | 次级文案颜色 | 来源、时间、辅助说明使用 |
| `primary` / accent | 主操作色 | 发送、确认、选中状态 |
| `rounded-xl` / `rounded-lg` | 圆角卡片 | 卡片和气泡都要有统一圆角系统 |
| `shadow-sm` | 轻阴影或材质层次 | 只用于需要“浮起”感觉的卡片 |
| `animate-fade-in` | `transition` / `withAnimation` / `opacity` | 空态、加载、卡片出现要有轻量过渡 |
| `framer-motion` 的 collapse/expand | SwiftUI `withAnimation(.easeInOut)` | tool card、会话 sheet、卡片展开收起 |
| `scrollIntoView` | `ScrollViewReader.scrollTo` | 新消息和草稿持续跟随底部 |

### 8.2 视觉节奏

Web 端的节奏是“轻、快、逐步显现”，SwiftUI 要保持同样节奏：

- 新 user message 先出现，assistant draft 再跟随。
- tool/source/ask_user 不是一次性同时爆出来，而是按事件顺序逐步浮现。
- 展开卡片要有短时动画，不要硬切换。
- 空态到有内容应有柔和过渡。
- loading 到内容出现要是渐进，而不是闪屏。

### 8.3 动画清单

P3 应对齐的动画，不是炫技，而是信息结构的一部分。

| 动画场景 | Web 语义 | SwiftUI 方案 | 目标 |
| --- | --- | --- | --- |
| 空态进入 | `fade-in` | `opacity` + `transition(.opacity)` | 页面柔和出现 |
| assistant draft 更新 | 流式追加 | 文本内容变化 + `withAnimation` | 让用户感知“正在生成” |
| tool 卡展开/收起 | `animatePresence` / collapse | `withAnimation(.easeInOut(duration: 0.2))` | 保持折叠/展开一致 |
| AskUser 卡出现 | streaming stop & ask | `transition(.move(edge: .bottom).combined(with: .opacity))` | 突出“需要你补充” |
| 来源卡出现 | 附加块显现 | 淡入 / 下滑 | 与正文区分但不突兀 |
| 会话列表 sheet | drawer / overlay | `.sheet` 默认过渡 | 与 Web 的侧边/弹层语义一致 |
| 停止按钮切换 | sending → stop | `contentTransition` / 轻量动画 | 让状态切换可见 |
| 错误条出现 | top banner | 顶部插入动画 | 立即但不过度抢占 |

### 8.4 动画硬约束

- 不做高频、晃眼、抢注意力的动画。
- 动画时长统一短促，保持“像聊天产品”的连贯性。
- 卡片的出现优先于炫酷过渡。
- 列表滚动动画只负责跟随，不做夸张弹性。
- 错误状态不做复杂动画，避免影响理解。

### 8.5 刷新与重绘节奏

P3 需要特别强调“刷新”不是网络刷新，而是页面状态与事件流的更新节奏。

| 场景 | Web 行为 | SwiftUI 行为 | 对齐点 |
| --- | --- | --- | --- |
| 新事件到达 | React state 更新、局部重渲染 | `@Published` / `@StateObject` 更新 | 只刷新相关区块 |
| 草稿追加 | 文本流式变化 | `assistantDraft` 变化 | 自动滚动 + 文本增量 |
| trace/source 追加 | 列表局部插入 | `traceGroups` / `sourceReferences` 变化 | 列表尾部轻量增量 |
| 卡片展开 | 局部 state 切换 | `@State isExpanded` | 不触发全页重绘 |
| 会话列表刷新 | 拉取列表 | `loadSessions()` | sheet 内独立刷新 |
| 下拉/取消加载 | loading view 切换 | `session list` / `root` 视图切换 | loading 与内容切换清楚 |

P3 要确保：

- 大多数更新是局部更新。
- 不因为一个事件把整个页面重建一遍。
- `assistantDraft` 更新只刷新 message 区，不影响输入区和 toolbar。
- `trace/source` 更新只刷新对应卡片区域。

### 8.6 键盘与输入法

P3 的键盘不是纯输入工具，而是聊天体验的一部分。SwiftUI 里最容易翻车的，不是消息流，而是键盘把 Composer 顶没、输入法组合态导致误发送、以及“完成”按钮无法稳定收起键盘。

P3 要对齐的键盘行为：

| 场景 | 目标行为 | 说明 |
| --- | --- | --- |
| 键盘弹出 | Composer 始终可见 | 消息列表随着键盘上移留出底部安全区 |
| 发送中 | 输入可清空、键盘可保留 | 用户可继续补充或等待结果 |
| streaming | 允许停留键盘或自动收起 | 以产品策略为准，但必须稳定 |
| wait_for_input | 键盘优先服务 AskUser | 在 AskUser 卡上回答时不应遮挡问题 |
| 手动收起 | 键盘完成按钮可用 | `SparkKeyboardDoneToolbar` 提供统一入口 |
| IME 组合态 | 回车不误发 | 需要配合输入法状态判断 |

#### 输入法对齐原则

- 单行输入和多行输入都要保留一致的发送键行为。
- 中文输入法的组合态结束前，不应把回车当作发送。
- 如果 `TextEditor` 或多行 `TextField` 进入编辑，顶部导航和消息列表不能跳动太剧烈。
- 键盘关闭后，Composer 不能因为底部 inset 变化突然“抖一下”。

#### SwiftUI 落地建议


#### 键盘与 AskUser 的协同

- 当 `wait_for_input` 出现时，AskUser 卡与键盘要共享焦点策略。

### 8.7 消息卡片解剖

P3 要把“消息卡片”拆成可维护的层，而不是一个大气泡里塞所有内容。

#### 8.7.1 user 卡片

| 元素 | 目标 |
| --- | --- |
| 气泡位置 | 右侧 |
| 背景 | accentColor |
| 文本颜色 | 白色 |
| 边距 | 比 assistant 略紧凑 |
| 状态 | optimistic / confirmed |

#### 8.7.2 assistant 卡片

| 元素 | 目标 |
| --- | --- |
| 气泡位置 | 左侧 |
| 背景 | secondarySystemBackground |
| 文本 | Markdown 正文 |
| 附加层 | tool trace、source refs、AskUser、调试条 |
| loading | draft 右下或正文下方的小型 ProgressView |

#### 8.7.3 tool 卡片

| 元素 | 目标 |
| --- | --- |
| 默认状态 | 折叠 |
| 标题 | 工具名 + 状态 |
| 展开内容 | callContent / resultContent |
| 状态颜色 | pending / completed / failed 分层 |
| 动作 | 点击整行展开/收起 |

#### 8.7.4 source 卡片

| 元素 | 目标 |
| --- | --- |
| 标题 | 来源标题 |
| 摘要 | snippet，默认最多 3 行 |
| 链接 | 有 url 时可点击 |
| 排列 | 助手消息下方垂直列表 |

#### 8.7.5 AskUser 卡片

| 元素 | 目标 |
| --- | --- |
| 标题 | “需要你的补充” 类语义 |
| 问题 | 一条或多条 |
| 选项 | 可选 chip / button 列表 |
| 输入 | 可自定义文本 |
| 提交 | 单一提交按钮 |

#### 8.7.6 Loading 卡片

| 元素 | 目标 |
| --- | --- |
| 空态 | 页面级 loading / 会话加载 |
| 草稿 loading | assistant bubble 内的小型 loading |
| 慢加载提示 | 超时后给“仍在加载”提示 |

### 8.8 加载方式

P3 要把 loading 分成三种，而不是一种模糊的“转圈圈”：

| 加载类型 | 位置 | 触发时机 | 关闭时机 |
| --- | --- | --- | --- |
| 会话加载 | 页面级 | 打开历史会话、切换 session | session load 完成或取消 |
| 连接加载 | 页面级/顶部 | WebSocket connect 中 | ready / failed |
| 生成加载 | 消息级 | start_turn 后、done 前 | done / error / cancel |

#### 会话加载

- 使用独立 loading view，而不是欢迎页冒充加载页。
- 如果加载时间过长，给出“仍在加载”的提示。
- 取消时回到当前页面，而不是清空上下文。

#### 生成加载

- user message 先落地。
- assistant draft 作为生成中载体。
- loading 不应该遮住已有正文。

#### 连接加载

- 连接失败要有明确错误。
- 不要把连接中和加载中混成一团。

### 8.9 刷新方式

P3 里“刷新”不是手动下拉刷新的唯一形态，而是页面的多层刷新策略：

| 刷新层 | 触发 | 目标 |
| --- | --- | --- |
| 消息刷新 | 新事件到达 | 更新 assistantDraft / messages |
| 卡片刷新 | tool/source/ask_user 事件到达 | 更新对应卡片内容 |
| 状态刷新 | connectionState 变化 | 切换空态/错误条/加载态 |
| 会话刷新 | sheet 内刷新按钮 | 更新会话列表 |

#### 刷新粒度原则

- 不因为一个 tool_result 导致整页重绘。
- 不因为一个 content 片段把 toolbar 重建。
- 不因为 AskUser 卡出现把消息列表滚回顶部。
- 不因为 session meta 更新让 composer 失焦。

### 8.10 消息卡片与 loading 的排版节奏

P3 的排版节奏建议与 Web 保持一致：

- 先消息，后卡片。
- 卡片通常挂在 assistant 消息之下。
- loading 是局部的，不是全页遮罩。
- 只有会话加载才可用页面级占位。
- 生成中要让用户看到“正在发生什么”，不是只看到一坨灰块。

### 8.11 键盘/加载/卡片的通用对齐公式

```text
Web 交互语义
    ↓
状态归类
    ↓
SwiftUI 组件拆分
    ↓
焦点 / 动画 / 列表滚动 / 视觉层级
    ↓
可验收的页面表现
```

## 9. 事件完整渲染矩阵

### 7.1 事件矩阵总表

| 事件 | 语义 | 当前代码状态 | P3 UI 渲染 | 是否进主消息流 | 是否影响状态机 |
| --- | --- | --- | --- | --- | --- |
| `session` | 新会话或 session 识别 | 已处理 | 会话标题/上下文更新 | 否 | 是 |
| `session_meta` | 会话元数据更新 | 已处理 | 标题、元信息轻量更新 | 否 | 是 |
| `content` | assistant 流式正文 | 已处理 | 追加到 `assistantDraft` | 是 | 是 |
| `result` | 最终结果或总结 | 已处理 | 追加到 `assistantDraft`，必要时补充结果卡 | 是 | 是 |
| `thinking` | 思考中/推理中 | 已处理但弱展示 | 状态 chip / 灰色辅助行 | 否 | 轻度 |
| `observation` | 观察/中间结果 | 已处理但弱展示 | 状态 chip / 调试行 | 否 | 轻度 |
| `progress` | 进度更新 | 已处理但弱展示 | 进度条/百分比/状态文案 | 否 | 轻度 |
| `stage_start` | 阶段开始 | 已处理但弱展示 | 状态分段标题/调试行 | 否 | 轻度 |
| `stage_end` | 阶段结束 | 已处理但弱展示 | 状态分段标题/调试行 | 否 | 轻度 |
| `tool_call` | 工具调用 | 已处理 | `AIToolTraceCard` pending | 否 | 是 |
| `tool_result` | 工具结果 | 已处理 | `AIToolTraceCard` completed/failed | 否 | 是 |
| `sources` | 参考来源 | 已处理 | `AISourceReferencesView` | 否 | 是 |
| `wait_for_input` | 等待用户补充信息 | 已处理 | `AIAskUserCardView` | 否 | 是 |
| `error` | 错误 | 已处理 | 顶部错误条 / inline 错误卡 | 否 | 是 |
| `done` | 本轮结束 | 已处理 | 固化 assistant 消息、收口 trace/source | 是 | 是 |
| `pong` | 心跳回包 | 已处理 | 不显示在主界面 | 否 | 否 |
| `active_turn_info` | 运行中 turn 状态 | 已处理 | 可用于调试或恢复提示 | 否 | 轻度 |
| `unrecognized` | 未识别事件 | 已处理 | 调试事件条 / 原始事件展示 | 否 | 轻度 |

### 7.2 事件与可见区域

P3 需要把事件映射到以下可见区域：

| 可见区域 | 事件类型 |
| --- | --- |
| 用户消息气泡 | `user` 消息对象，不直接来自 StreamEvent |
| assistant 草稿 | `content`、`result`、部分 `thinking` / `observation` / `progress` |
| 工具卡 | `tool_call`、`tool_result` |
| 来源卡 | `sources` |
| AskUser 卡 | `wait_for_input` |
| 顶部错误条 | `error` |
| 生成中状态 | `thinking`、`progress`、`stage_start`、`stage_end` |
| 调试/时间线 | `unrecognized`、`active_turn_info`、`session_meta` |
| 完成收口 | `done` |

### 7.3 事件渲染规则

#### `content`

- 追加到 `assistantDraft`。
- 触发 scroll to bottom。
- 保持对用户可见。

#### `result`

- 如果携带正文，追加到 `assistantDraft`。
- 如果仅为结果摘要，可作为 final answer 的一部分或摘要卡片。
- 结束时由 `done` 收口。

#### `thinking`

- 不强制作为主文本。
- 可以显示为“AI 正在思考”状态 chip。
- 不应污染最终 assistant 文本。

#### `observation`

- 可以作为调试行或辅助状态。
- 如果内容有价值，可放进折叠 detail。
- 默认不作为主消息。

#### `progress`

- 可以显示短进度文案，如“检索知识库中”“正在生成答案”。
- 不要把所有 progress 都拼进正文。

#### `stage_start` / `stage_end`

- 可作为段落标题或 timeline marker。
- P3 更适合放入事件时间线或折叠调试面板。

#### `tool_call`

- 进入 `AIToolTraceGroup(status: .pending)`。
- 展示 tool 名称、调用内容、折叠状态。
- 不应直接塞入 assistant 正文。

#### `tool_result`

- 更新对应 `AIToolTraceGroup(status: .completed)`。
- 如果 `call_id` 找不到，创建补偿 trace。
- 可在展开状态中展示结果。

#### `sources`

- 解析 `metadata["sources"]`。
- 进入 `AISourceReference` 列表。
- 作为来源卡展示。

#### `wait_for_input`

- 解析 `metadata["questions"]`。
- 进入 `pendingAskUserCard`。
- UI 直接展示问答卡，而不是只显示一句“请补充信息”。

#### `error`

- 若 `turn_terminal=true`，进入失败态和错误条。
- 若是非终态，可作为辅助状态或草稿的一部分。
- 不把 error 直接吞掉。

#### `done`

- 把 `assistantDraft` 固化为 assistant 消息。
- 清空 `pendingAskUserCard`。
- 清理临时 trace/source 聚合，或保留在 message 附件区。
- 把 connectionState 从 done 转回 ready 的 UI 逻辑留在 ViewModel 层。

#### `pong`

- 只更新连接活跃时间。
- 不显示在主聊天流。

#### `active_turn_info`

- 可用于恢复状态提示。
- P3 不做完整恢复，但可将其记录在调试信息中。

#### `unrecognized`

- 以原始事件或调试行显示。
- 不允许 crash。

## 10. 数据模型与聚合规则

### 8.1 `AIChatState` 的 P3 使用重点

| 字段 | P3 作用 |
| --- | --- |
| `messages` | 已完成消息列表 |
| `assistantDraft` | 流式生成中的正文 |
| `pendingAskUserCard` | 等待补充输入卡 |
| `traceGroups` | 工具调用轨迹 |
| `sourceReferences` | 参考来源 |
| `userFacingError` | 顶部错误条 |
| `consumedEventKeys` | 去重 |
| `activeSession` | 会话标题和上下文 |
| `activeTurn` | 当前 turn id / seq / status |

### 8.2 `AIChatMessage`

P3 中消息对象的角色语义：

| role | P3 渲染 |
| --- | --- |
| `user` | 右侧气泡 |
| `assistant` | 左侧气泡，支持 markdown |
| `system` | P3 可暂不渲染或放入调试层 |
| `tool` | 不作为主消息，优先进入 trace |

P3 对消息的要求：

- user message 需要乐观展示。
- assistant message 只在 `done` 后收口。
- tool/source/ask_user 不要伪装成普通 assistant 文本。

### 8.3 `AIChatTurn`

| 字段 | P3 用途 |
| --- | --- |
| `id` | 当前 turn 标识 |
| `sessionID` | 当前会话标识 |
| `status` | running / waitingForUser / done / failed 等 |
| `lastSeq` | 去重和调试 |

P3 不做完整恢复，但需要让 `status` 在 UI 中能解释：

- running：显示生成中。
- waitingForUser：显示等待补充信息。
- done：显示完成。
- failed：显示失败。

### 8.4 `AIToolTraceGroup`

| 字段 | P3 用途 |
| --- | --- |
| `id` | call_id 或补偿 id |
| `toolName` | 工具名 |
| `status` | pending / completed / failed |
| `callContent` | 调用内容 |
| `resultContent` | 返回结果 |

P3 的工具 trace 规则：

- 一个 tool_call 对应一个 trace group。
- 一个 tool_result 优先回填同 id 的 group。
- 多次 tool_call/tool_result 按顺序可展开显示。
- Trace 默认折叠，避免压住正文。

### 8.5 `AISourceReference`

| 字段 | P3 用途 |
| --- | --- |
| `id` | 来源唯一标识 |
| `title` | 来源标题 |
| `snippet` | 摘要 |
| `url` | 可点击链接 |

P3 的来源规则：

- sources 不应混入 assistant 正文。
- 来源卡可以放在 assistant message 下方。
- 如果没有 url，也要可读 title/snippet。

### 8.6 `AIAskUserCard`

| 字段 | P3 用途 |
| --- | --- |
| `turnID` | 绑定当前 turn |
| `questions` | 问题数组 |

| 问题字段 | P3 用途 |
| --- | --- |
| `id` | 问题 id |
| `text` | 问题文本 |
| `options` | 可选项 |
| `allowsCustomInput` | 是否允许自定义回答 |

P3 目标：

- `wait_for_input` 不只是占位文案，而是可真正提交答案的卡片。
- 若 question 有 options，则先展示 options 再允许自定义输入。
- 若没有 questions，至少展示默认“请补充信息”的输入卡。

## 11. 关键技术方案

### 9.1 事件去重

当前去重键：

```text
turn_id + seq
```

P3 继续沿用该策略，保证：

- 重连后不会重复渲染。
- 同 seq 的重复 frame 不会把内容叠加两次。
- assistantDraft 不会因为重复事件无限增长。

P3 风险：

- 如果某些事件没有 seq，就只能作为临时调试事件处理。
- 对于无 seq 事件，P3 需要避免把其内容误加入主消息流。

### 9.2 草稿聚合

当前草稿聚合策略：

```text
content / result
    ↓
assistantDraft
    ↓
done
    ↓
assistant message
```

P3 要明确：

- content 是主正文。
- result 可作为正文尾部或摘要补充。
- thinking/observation/progress/stage_start/stage_end 不默认进入正文。
- 如果后端把某些非正文事件内容放进 content 字段，P3 应通过 event type 和 metadata 决定是否展示在正文、状态 chip、还是调试面板。

### 9.3 工具卡聚合

P3 的工具卡目标行为：

```text
tool_call
    ↓
创建 pending group
    ↓
tool_result
    ↓
更新同 id group
    ↓
assistant message 下方折叠展示
```

建议规则：

- 默认折叠。
- 展开后显示 callContent 与 resultContent。
- 状态 icon 区分 pending/completed/failed。
- 多个 tool group 按序排列。

### 9.4 来源卡聚合

P3 的来源卡目标行为：

```text
sources.metadata
    ↓
解析 title/snippet/url
    ↓
AISourceReference[]
    ↓
assistant message 下方展示
```

建议规则：

- 来源卡与正文分区。
- 链接可点击则可点。
- snippet 不超过三行。
- 过多来源可以折叠。

### 11.5 AskUser 交互

P3 的 AskUser 卡目标行为：

```text
wait_for_input
    ↓
questions
    ↓
AIAskUserCardView
    ↓
选项或输入
    ↓
submit_user_reply
```

建议规则：

- 每题至少能给一个答案。
- 支持 option 选择。
- 支持自定义文本。
- 提交后卡片消失或进入 waiting/streaming。

### 11.6 错误渲染

P3 要区分三类错误：

| 错误类型 | UI 策略 |
| --- | --- |
| terminal error | 顶部错误条，状态 failed，允许重试 |
| 非终态错误 | 作为辅助状态或草稿附注，不打断主流 |
| 解析错误 / 未识别事件 | 调试信息或事件时间线，不进入用户主流 |

P3 不能让 error 与 done 混淆。

### 11.7 调试事件时间线

P3 建议保留一个轻量的“事件时间线”或“原始事件”视图，尤其在开发期：

- 方便核对 seq 顺序。
- 方便对照 reducer 行为。
- 方便排查 sources / tool / ask_user 的 metadata 解析。

但这个时间线不应成为正式用户主界面默认焦点。

| --- | --- |
| idle | 空态、输入栏 |
| ready | 消息列表、输入栏、工具栏 |
| streaming | assistant draft、trace/source 卡、停止按钮 |
| waitingForUser | AskUser 卡、消息列表、输入栏按策略处理 |
| failed | 错误条、已有消息、重试入口 |
| done | 已完成消息、输入栏可继续 |

### 10.3 Assistant message 下的附加渲染

P3 允许 assistant bubble 下方附加：

- ToolTraceCard。
- SourceReferencesView。
- 状态辅助 chip。
- 可选的事件摘要。

但这些附加信息不能替代正文文本本身。

### 10.4 长消息策略

P3 需要考虑：

- assistantDraft 可能非常长。
- tool result 可能很大。
- sources 可能很多。

建议：

- 长文本默认折叠或限制行数。
- 详情展开后再看完整内容。
- 消息列表保持可滚动。

## 13. P3 事件完成矩阵

### 11.1 逐事件完成定义

| 事件 | P3 完成定义 |
| --- | --- |
| `session` | 能建立或更新 active session，并影响标题或上下文 |
| `session_meta` | 能更新 session 标题或元数据展示 |
| `content` | 能作为 assistant draft 基础文本连续追加 |
| `result` | 能作为最终结果的一部分，且不会丢失 |
| `thinking` | 能以状态 chip / 辅助行呈现 |
| `observation` | 能以状态 chip / 辅助行呈现 |
| `progress` | 能以进度状态或辅助文案呈现 |
| `stage_start` | 能作为阶段标记或调试辅助信息呈现 |
| `stage_end` | 能作为阶段标记或调试辅助信息呈现 |
| `tool_call` | 能生成 pending trace card |
| `tool_result` | 能回填 trace card 的结果并改变状态 |
| `sources` | 能生成来源卡并可点击或阅读 |
| `wait_for_input` | 能生成 AskUser 卡并提交答案 |
| `error` | 能进入 failed 或非终态辅助错误状态 |
| `done` | 能收口为 assistant message 并清理草稿 |
| `pong` | 不在用户主界面显示，但要维护连接活性 |
| `active_turn_info` | 能用于调试/恢复提示，不打断主流 |
| `unrecognized` | 能作为调试事件展示，不 crash |

### 11.2 事件完成判定规则

P3 只有在以下规则同时满足时才算“完整渲染”：

1. 每个后端事件类型有明确的 UI 策略。
2. 不会因为未知事件导致页面崩溃。
3. 主消息流和辅助信息层分离。
4. 同一事件不会被重复渲染成多个互相矛盾的 UI。
5. 终态错误和非终态错误处理不同。
6. AskUser / Tool / Sources 不再只是调试日志。

## 14. 与 P2 的关系

P2 的核心是“有入口、有输入、有基础聊天壳”。P3 的核心是“事件完整、语义清晰、卡片分层”。

| P2 能力 | P3 提升 |
| --- | --- |
| 基础聊天入口 | 事件完整渲染入口 |
| user/assistant 基础气泡 | assistant + tool + sources + ask user 的组合渲染 |
| 空态、错误条、Composer | 继续保留，并加上事件辅助层 |
| stop 按钮 | 继续保留，并和 waiting/error/done 状态精确联动 |
| Debug 入口 | 保持排障用途 |

P3 不应回头重新设计入口，而应在 P2 的 UI 骨架上扩展事件层。

## 15. 与 P4/P5 的关系

| 能力 | P3 处理 | 后续阶段 |
| --- | --- | --- |
| 历史恢复 | 可保留事件状态，但不完整闭环 | P4 |
| 账号切换恢复 | 不作为 P3 验收重点 | P4 |
| 产品化视觉 | 基础可用 | P5 |
| 附件 / 图片 / 文件 | 不纳入 P3 | P5 |
| 长会话性能优化 | 可先做基本滚动 | P5 |
| 多端同构事件矩阵 | 先沉淀 iOS 语义 | P6 |

## 16. 风险与处理

| 风险 | 表现 | 处理方式 |
| --- | --- | --- |
| 非正文事件被拼进正文 | trace/source/ask_user 污染 assistantDraft | 严格按事件类型区分正文和辅助层 |
| 重复事件重复展示 | 同一 turn 多次渲染相同内容 | 继续依赖 `turn_id + seq` 去重 |
| `done` 过早收口 | 后续 tool/source 事件丢失 | 必须确认后端 turn 完结顺序，必要时保留尾部缓冲 |
| `wait_for_input` 解析失败 | 用户只看到一段文字 | 以 `questions` metadata 为主，失败时降级为默认输入卡 |
| `sources` 数量过多 | 来源卡占据过多高度 | 折叠、限制条数或进入详情页 |
| markdown 复杂内容 | 表格/代码块/引用展示不完整 | P3 只保证基本可读，高保真进入 P5 |
| 非终态 error 误判成终态 | 生成中被错误打断 | 依赖 `turn_terminal` / 后端约定区分 |
| timeline 过重 | 调试条影响正式体验 | 默认折叠或仅 Debug 可见 |
| `appendEventToDraft` 空实现导致辅助事件无感 | 辅助事件缺少视觉反馈 | P3 明确辅助事件的独立 UI 层，不依赖正文拼接 |

## 17. P3 实施拆分

### 15.1 P3-A 事件语义冻结

目标：

- 给所有 StreamEvent 类型制定明确 UI 策略。
- 决定哪些进入正文，哪些进入辅助卡，哪些进入调试条。

验收：

- 矩阵完整。
- 没有含混不清的“差不多显示一下”。

### 15.2 P3-B reducer 与 state 细化

目标：

- 明确 `AIChatState` 对 tool/source/ask_user/status 的组织方式。
- 保证去重和顺序稳定。

验收：

- 同一事件不重复。
- 辅助信息不会丢。

### 15.3 P3-C 组件分层

目标：

- 让消息、工具、来源、AskUser 各自有稳定组件。

验收：

- 组件职责清楚。
- 组合方式清楚。

### 15.4 P3-D 错误与终态收口

目标：

- 区分终态错误与非终态错误。
- 确保 done / failed / waitingForUser 的 UI 语义不混淆。

验收：

- 错误条不污染正文。
- done 之后草稿正确收口。

### 15.5 P3-E 调试可观测性

目标：

- 保留事件时间线或原始事件辅助视图。
- 方便排查 reducer 和后端事件样本。

验收：

- 能看到 seq 顺序。
- 能核对 event type。

## 18. 手工测试脚本

### 16.1 基础文本流

```text
1. 进入 AI 对话。
2. 输入一段普通文本。
3. 发送 start_turn。
4. 确认 user message 立即出现。
5. 确认 content 连续追加到 assistant draft。
6. 收到 done 后，确认草稿固化为 assistant message。
```

### 16.2 工具调用流

```text
1. 发送一个会触发工具调用的请求。
2. 确认出现 pending ToolTraceCard。
3. 确认 tool_result 后状态转为完成。
4. 确认工具内容不直接污染正文。
```

### 16.3 来源流

```text
1. 发送一个会返回 sources 的请求。
2. 确认 assistant message 下方出现来源卡。
3. 确认 title/snippet/url 正常展示。
```

### 16.4 AskUser 流

```text
1. 发送一个会触发 wait_for_input 的请求。
2. 确认出现 AskUser 卡。
3. 选择选项或输入自定义文本。
4. 提交后确认卡片消失或进入继续生成状态。
```

### 16.5 错误流

```text
1. 触发终态 error。
2. 确认顶部错误条出现。
3. 确认已有消息保留。
4. 确认不会退出登录。
```

### 16.6 调试流

```text
1. 通过 Debug 入口发起同样的请求。
2. 核对 event timeline 中的 seq 和 type。
3. 对照 reducer 的状态变化。
4. 确认主界面与调试界面的表现一致或有意差异清楚。
```

## 20. P3 完成定义

P3 可标记完成，需要同时满足：

- 每类 StreamEvent 都有明确渲染策略。
- `content` / `result` / `done` 形成稳定正文流。
- `tool_call` / `tool_result` 形成稳定工具卡。
- `sources` 形成稳定来源卡。
- `wait_for_input` 形成稳定 AskUser 卡。
- `error` 形成稳定错误展示。
- `pong` / `active_turn_info` / `unrecognized` 不会破坏主流。
- 去重、顺序、收口规则清楚。
- P3 的辅助层不会污染正文层。
- P3 之后可以顺势进入 P4 会话恢复与账号隔离。
