# 应用内通知需求

## 一、模块目标

应用内通知模块负责把业务流程中的成功、失败、警告、提示、深链信息和可点击横幅，统一转换为用户可见的 toast、banner 或 alert，并记录通知收件箱与展示指标。

当前实现范围：

- `NotificationClient` 为业务侧提供 `success`、`error`、`warning`、`info` 和自定义 `publish` 入口。
- `NotificationIntent` 描述通知级别、展示形式、来源、去重键、自动消失时间和可选点击动作。
- `NotificationQueue` 负责去重、队列容量限制、入队、丢弃记录和点击动作旁路保存。
- `NotificationDeliveryCoordinator` 串行消费队列，更新 inbox、metrics，并驱动 `NotificationStore` 展示。
- `NotificationHostView` 作为全局 SwiftUI Host，承载 toast、banner 和 alert 展示。
- `NotificationInboxStore` 将通知历史写入 Application Support 下的 `notification_inbox.json`。
- `NotificationMetricsStore` 记录入队、展示、重复丢弃、溢出丢弃和平均展示延迟。

本模块不负责 iOS 系统推送注册、远端推送 payload 解析、后台通知点击路由、具体业务错误文案生成，也不负责认证失效状态机；这些分别由 Push、业务 ViewModel、路由与生命周期模块处理。

## 三、通知发布入口与业务接入

### 需求说明

业务代码需要一个统一、轻量的通知发布入口，避免每个页面单独写 toast、alert 或 banner 状态。登录、深链、网络失败、账号升级等业务都应通过同一套 `NotificationClient` 发出用户反馈。

### 基础要求与业务规则

- 业务侧优先依赖 `NotificationClient` 协议，而不是直接持有 `NotificationQueue` 或 `NotificationStore`。
- `success` 和 `info` 默认发布为 toast。
- `error` 和 `warning` 默认发布为 banner。
- 自定义通知使用 `NotificationIntent`，可以指定 `title`、`message`、`level`、`presentation`、`dedupeKey`、`source`、`autoDismissAfter` 和 `onTap`。
- `source` 用于诊断通知来源，例如登录流程使用 `auth.login`，深链入口使用 `deeplink`。
- `DefaultNotificationClient.publish` 内部创建 Task 调用 `PublishNotificationUseCase.execute`，业务调用方不需要等待展示完成。

### 验收标准

- 登录成功、登录失败、验证码发送、Apple 登录取消等路径能通过统一通知客户端给出反馈。
- 深链打开时可以通过 `notificationClient.info(url.absoluteString, source: "deeplink")` 展示调试/提示信息。
- 页面不会直接修改 `currentToast`、`currentBanner` 或 `currentAlert`。
- 新增业务通知时只需要注入 `NotificationClient` 或复用已有依赖，不需要新增全局 overlay。

### 技术细节与设计代码位置

- 发布协议：`SupportClient/Projects/Core/Notification/Application/NotificationClient.swift`。
- 发布用例：`SupportClient/Projects/Core/Notification/Application/PublishNotificationUseCase.swift`。
- 通知模型：`SupportClient/Projects/Core/Notification/Domain/NotificationModels.swift`。
- 根依赖注入：`SupportClient/Projects/App/Sources/App/AppContainer.swift`。
- 登录业务接入：`SupportClient/Projects/Features/Auth/Presentation/LoginViewModel.swift`。
- 深链接入：`SupportClient/Projects/App/Sources/ContentView.swift`。

## 四、队列去重、容量限制与丢弃记录

### 需求说明

通知可能在短时间内由多个业务状态同时触发。模块需要串行队列、重复消息抑制和容量保护，避免用户被相同通知刷屏，也避免队列无限增长。

### 基础要求与业务规则

- `NotificationQueue` 是 actor，负责串行化入队、出队和点击动作消费。
- `dedupeWindow` 默认 2 秒；同一 `dedupeKey` 在窗口内重复出现时丢弃。
- 未提供 `dedupeKey` 时，使用 `level|presentation|message.lowercased()` 生成 fallback key。
- `maxQueueDepth` 默认 128；超过容量时丢弃新消息。
- 丢弃原因使用 `NotificationDropReason.duplicate` 或 `NotificationDropReason.queueOverflow`。
- 入队成功要写入 inbox 并记录 enqueued 指标。
- 丢弃也要写入 inbox，并记录对应 dropped 指标。
- `onTap` 闭包不进入 `NotificationMessage`，而是按 message id 保存到 `pendingTapActions`，保持消息结构可编码。

### 验收标准

- 2 秒内重复发送同一 dedupe key 只展示一次。
- 队列达到 128 条后，新通知不会继续入队，但会记录溢出丢弃。
- inbox 中能看到被丢弃消息及其丢弃原因。
- 通知消息结构仍可 Codable，不会因为点击闭包导致持久化失败。

### 技术细节与设计代码位置

- 队列实现：`SupportClient/Projects/Core/Notification/Infrastructure/NotificationQueue.swift`。
- 丢弃原因模型：`SupportClient/Projects/Core/Notification/Domain/NotificationModels.swift`。
- 收件箱记录：`SupportClient/Projects/Core/Notification/Infrastructure/NotificationInboxStore.swift`。
- 指标记录：`SupportClient/Projects/Core/Notification/Infrastructure/NotificationMetricsStore.swift`。
- 日志模块：`SupportClient/Foundation/Logger.swift`。

## 五、投递协调、自动消失与点击动作

### 需求说明

通知展示需要稳定串行消费：每次从队列取一条，标记展示，更新指标，展示给用户，并在 toast/banner 自动消失或 alert 被用户确认后继续下一条。

### 基础要求与业务规则

- `NotificationDeliveryCoordinator.startIfNeeded()` 使用 `isConsuming` 防止重复消费循环。
- 消费前调用 `inboxStore.markPresented`，并计算从 `enqueuedAt` 到展示时刻的延迟。
- 展示前从队列消费 `onTap`，注册到 `NotificationStore`。
- toast 默认 2 秒后自动消失，最短 0.4 秒。
- banner 默认 2.8 秒后自动消失，最短 0.6 秒。
- alert 不自动消失，等待 `NotificationStore.waitForAlertDismissal(id:)`。
- banner 点击时先 dismiss，再执行 `onTap`；关闭按钮只 dismiss。
- 每条消息展示结束后调用 `inboxStore.markDismissed` 并刷新 dashboard。

### 验收标准

- 同一时刻只消费一个通知循环。
- toast 和 banner 能按默认或自定义时长消失。
- alert 会阻塞后续通知，直到用户确认关闭。
- banner 点击动作只在 message id 匹配时触发，dismiss 后会移除 tap action。
- 展示前后 inbox 和 metrics 能刷新到 `NotificationStore`。

### 技术细节与设计代码位置

- 投递协调器：`SupportClient/Projects/Core/Notification/Application/NotificationDeliveryCoordinator.swift`。
- 展示状态：`SupportClient/Projects/Core/Notification/Application/NotificationStore.swift`。
- 全局 Host：`SupportClient/Projects/App/Sources/App/Notification/NotificationHostView.swift`。
- 点击动作旁路：`SupportClient/Projects/Core/Notification/Infrastructure/NotificationQueue.swift`。
- 自定义全屏弹层扩展：`SupportClient/Projects/App/Sources/App/Notification/NotificationFullScreenCover.swift`。

## 六、全局展示 Host 与弹层覆盖

### 需求说明

通知展示必须覆盖整棵 App，避免某个页面切换后通知丢失。普通页面和 fullScreenCover 场景都需要可以套入同一个通知 Host。

### 基础要求与业务规则

- `ContentView` 使用 `NotificationHostView(store:)` 包住 `AppCoordinatorView`。
- `NotificationHostView` 使用 top overlay 展示 banner 和 toast。
- banner 与 toast 共同放在顶部 `VStack`，间距 8，顶部内边距 8，水平内边距 12。
- `currentAlert` 使用 SwiftUI `.alert` 展示，关闭时调用 `dismissAlert`。
- `notificationFullScreenCover` 扩展在全屏弹层内容外再套一层 `NotificationHostView`，让弹层内通知也能显示。
- 展示图标和颜色由 `NotificationLevel` 映射，不由业务调用方传 UI 细节。

### 验收标准

- App 根视图中的通知可以覆盖登录页、启动页和主 Tab。
- fullScreenCover 内部业务也可以使用同一套通知 Host。
- toast、banner、alert 都从 `NotificationStore` 当前状态渲染，不依赖局部页面状态。
- success、error、warning、info 四类通知有稳定的系统图标和颜色。

### 技术细节与设计代码位置

- 根 Host 接入：`SupportClient/Projects/App/Sources/ContentView.swift`。
- Host 展示：`SupportClient/Projects/App/Sources/App/Notification/NotificationHostView.swift`。
- fullScreenCover 扩展：`SupportClient/Projects/App/Sources/App/Notification/NotificationFullScreenCover.swift`。
- Store 状态：`SupportClient/Projects/Core/Notification/Application/NotificationStore.swift`。

## 七、收件箱、指标与诊断

### 需求说明

应用内通知不仅要展示即时反馈，还要保留最近通知历史和基础指标，便于调试重复消息、丢弃、展示延迟和来源问题。

### 基础要求与业务规则

- `NotificationInboxStore` 默认最多保留 500 条 `NotificationInboxItem`。
- inbox 默认文件位于 Application Support 的 `SupportClient/notification_inbox.json`。
- 入队、展示、关闭和丢弃都要更新 inbox。
- inbox 持久化使用 `AtomicFileWriter.write`，失败时记录 warning 日志，不中断通知展示。
- `NotificationMetricsStore` 记录 enqueued、displayed、duplicate drop、overflow drop 和平均展示延迟。
- `NotificationDeliveryCoordinator.refreshDashboard()` 将 inbox 和 metrics 刷新到 `NotificationStore`。
- `ContentView.task` 首次进入时调用 `refreshDashboard()`，用于加载已有 inbox 和 metrics 快照。

### 验收标准

- App 启动后 `NotificationStore.inboxItems` 能获得磁盘上已保存的通知历史。
- 通知入队、展示、关闭、丢弃后 dashboard 状态会更新。
- 持久化失败不会让通知展示失败。
- 指标可区分重复丢弃和队列溢出丢弃。

### 技术细节与设计代码位置

- 收件箱存储：`SupportClient/Projects/Core/Notification/Infrastructure/NotificationInboxStore.swift`。
- 指标存储：`SupportClient/Projects/Core/Notification/Infrastructure/NotificationMetricsStore.swift`。
- Dashboard 刷新：`SupportClient/Projects/Core/Notification/Application/NotificationDeliveryCoordinator.swift`。
- 原子写文件：`SupportClient/Projects/Foundation/Utilities/AtomicFileWriter.swift`。
- 根刷新入口：`SupportClient/Projects/App/Sources/ContentView.swift`。

## 八、整体业务流程

```text
业务动作 / 深链 / 登录状态变化
  ↓
业务模块构造 NotificationIntent 或调用 NotificationClient.success/error/warning/info
  ↓
DefaultNotificationClient.publish 创建异步任务
  ↓
PublishNotificationUseCase.execute
  ↓
NotificationQueue.enqueue
  ├── dedupe 命中 → markDropped + recordDropped + refreshDashboard
  ├── queue overflow → markDropped + recordDropped + refreshDashboard
  └── enqueued → appendQueued + recordEnqueued
        ↓
NotificationDeliveryCoordinator.startIfNeeded
  ↓
consumeLoop 串行 dequeue
  ↓
markPresented + recordDisplayed + refreshDashboard
  ↓
NotificationStore.present
  ↓
NotificationHostView 渲染 toast / banner / alert
  ↓
自动消失、用户关闭或 alert 确认
  ↓
markDismissed + refreshDashboard
```

### 成功路径

1. 业务模块调用 `notificationClient.success(...)`、`error(...)`、`warning(...)`、`info(...)` 或 `publish(...)`。
2. `DefaultNotificationClient` 异步执行 `PublishNotificationUseCase`。
3. `NotificationQueue` 根据 dedupe key 和队列深度判断是否入队。
4. 入队成功后，`NotificationDeliveryCoordinator.startIfNeeded()` 启动消费循环。
5. 消费循环取出消息，更新 inbox 和 metrics，并设置 `NotificationStore.currentToast/currentBanner/currentAlert`。
6. `NotificationHostView` 观察 Store 状态并展示通知。
7. 通知结束后标记 dismissed，刷新 dashboard，继续消费下一条。

### 失败、重试和恢复

| 场景 | 当前处理 | 恢复方式 |
| --- | --- | --- |
| 重复通知 | 2 秒窗口内丢弃并记录 `duplicate` | 等窗口过后再次发布 |
| 队列溢出 | 新消息丢弃并记录 `queueOverflow` | 后续队列消费后可继续入队 |
| inbox 持久化失败 | 记录 warning 日志 | 当前展示不受影响；下次启动可能缺失历史 |
| alert 未关闭 | 消费循环等待 | 用户点击 OK 后继续后续消息 |
| toast/banner 自动消失 Task 被取消 | 当前代码忽略 sleep 抛错后继续 dismiss | 后续会标记 dismissed 并消费下一条 |
| onTap 缺失 | banner 点击只 dismiss，不执行业务动作 | 发布方需要提供 `NotificationIntent.onTap` |

### 取消、并发和幂等

- `NotificationQueue` 是 actor，入队、出队和点击动作消费天然串行。
- `NotificationDeliveryCoordinator.isConsuming` 保证消费循环不会重复启动。
- `NotificationStore.dismissToast/dismissBanner/dismissAlert` 都校验当前 id，避免旧通知误删新通知。
- `NotificationClient.publish` 是 fire-and-forget，当前没有取消句柄。
- inbox 按最新通知插入头部，超过 500 条裁剪尾部。

## 九、状态模型

| 状态 | 进入条件 | 用户可见结果 | 退出条件 |
| --- | --- | --- | --- |
| 未发布 | 没有业务调用通知入口 | 无通知 | 业务调用 `NotificationClient` |
| 已入队 | `NotificationQueue.enqueue` 成功 | 暂无，等待消费 | 被 `dequeue()` 取出 |
| 已丢弃 | dedupe 或 queue overflow | 当前不展示 | inbox 记录 droppedReason |
| 展示中 toast | `store.currentToast` 被设置 | 顶部 toast | 自动消失或主动 dismiss |
| 展示中 banner | `store.currentBanner` 被设置 | 顶部 banner，可关闭，可点击 | 自动消失、关闭或点击 |
| 展示中 alert | `store.currentAlert` 被设置 | 系统 alert | 用户点击 OK |
| 已关闭 | `markDismissed` 写入 | 不再可见 | 保留 inbox 历史 |
| Dashboard 已刷新 | `refreshDashboard()` 完成 | inbox/metrics 状态可被观察 | 下一次入队、展示、关闭或丢弃 |

## 十、数据与持久化

| 数据 | 所有者 | 存储位置 | 生命周期 | 清理时机 |
| --- | --- | --- | --- | --- |
| `NotificationIntent` | 业务调用方 | 内存，调用入参 | 单次发布 | 入队转换后释放 |
| `NotificationMessage` | `NotificationQueue` / `NotificationStore` | 队列内存、Store 内存、inbox JSON | 从入队到展示关闭；历史可跨启动 | 队列出队、Store dismiss、inbox 超过 500 条裁剪 |
| `onTap` 闭包 | `NotificationQueue` / `NotificationStore` | 内存字典，按 UUID | 当前消息展示期 | `consumeTapAction` 或 `dismissBanner` |
| `NotificationInboxItem` | `NotificationInboxStore` | Application Support `SupportClient/notification_inbox.json` | 跨启动保留 | 超过 `maxItems` 后裁剪 |
| `NotificationMetricsSnapshot` | `NotificationMetricsStore` | 内存 | App 进程生命周期 | 当前未发现持久化清理，重启后归零 |
| `currentToast/currentBanner/currentAlert` | `NotificationStore` | SwiftUI ObservableObject 内存 | 当前展示期 | 自动消失、用户关闭或 alert 确认 |

## 十一、错误模型

| 错误类别 | 触发条件 | 是否重试 | 用户反馈 | 清理动作 |
| --- | --- | --- | --- | --- |
| 重复通知 | dedupe key 在 2 秒窗口内再次出现 | 不重试 | 不展示 | 记录 duplicate drop |
| 队列溢出 | 队列深度达到 128 | 不重试当前消息 | 不展示 | 记录 overflow drop |
| inbox 写入失败 | JSON 编码或原子写文件失败 | 当前不重试 | 通知仍展示 | warning 日志 |
| inbox 读取失败 | 文件不存在或 JSON 解码失败 | 不重试 | dashboard 初始为空 | 当前无用户提示 |
| alert 等待过久 | 用户不关闭 alert | 不自动重试 | alert 停留 | 后续通知排队等待 |
| 点击动作不存在 | 未提供 onTap 或已被消费 | 不重试 | banner 只关闭 | 清理当前 banner |
| 系统推送权限未授权 | `PushAdapter` 返回 false | 当前应用内通知不依赖系统授权 | 不影响应用内 toast/banner/alert | 无 |

## 十二、与其他模块的接口边界

### 本模块负责

- 提供业务通知发布协议和默认客户端。
- 将通知意图转换为可展示、可持久化的消息。
- 执行队列去重、容量保护、串行投递和自动消失。
- 维护当前展示状态、通知历史和基础指标。
- 在根视图和 fullScreenCover 中提供统一通知 Host。

### 本模块不负责

- 生成具体业务错误文案。
- 决定登录、登出、账号切换或鉴权失效状态机。
- 远端推送注册、推送 payload 解析和系统通知展示。
- 后台收件箱同步或服务端通知列表。
- 用户级通知偏好、免打扰和通知中心页面。

### 上游调用方

- `LoginViewModel`：登录、验证码和账号升级反馈。
- `ContentView.onOpenURL`：深链信息提示。
- 未来业务 ViewModel 或 UseCase：可通过 `NotificationClient` 发布统一反馈。
- `NotificationFullScreenCover` 内业务内容：可复用同一 Store 展示弹层内通知。

### 下游依赖

- SwiftUI overlay、alert、transition 和 animation。
- `NotificationQueue`、`NotificationInboxStore`、`NotificationMetricsStore`。
- `AtomicFileWriter`。
- `Logger` / `SupportLogger`。
- iOS `UNUserNotificationCenter` 仅用于 `PushAdapter` 的系统推送授权，当前与应用内通知展示分离。

### 输入和输出契约

| 契约 | 输入 | 输出 |
| --- | --- | --- |
| 发布通知 | `NotificationIntent` 或快捷方法参数 | enqueued 或 dropped |
| 队列消息 | `NotificationMessage` | 当前展示状态、inbox、metrics |
| 点击横幅 | `NotificationMessage.id` 对应 onTap | dismiss 后执行主线程动作 |
| Dashboard 刷新 | inbox store 与 metrics store 当前值 | `NotificationStore.inboxItems`、`metricsSnapshot` |
| 系统推送授权 | 当前授权状态 | `Bool`，不影响应用内通知 |

## 十五、当前实现、缺口与演进

### 当前实现

- 当前实现已经具备业务发布入口、通知模型、队列去重、容量限制、串行投递、全局展示、收件箱持久化和基础指标。
- 当前实现已经把通知 Host 接到 `ContentView` 根部，并提供 `notificationFullScreenCover` 适配全屏弹层。
- 当前实现已经支持 banner 点击动作，但通过旁路字典保存，避免破坏 `NotificationMessage` 的 Codable。
- 当前实现已经在登录 ViewModel 和深链入口使用应用内通知。
- 当前实现有 `PushAdapter` 请求系统通知授权，但未发现它与应用内通知队列有直接衔接。

### 当前缺口

- 当前未发现应用内通知模块的单元测试或 UI 测试。
- 当前未发现用户可见的通知中心/历史页面，`inboxItems` 目前主要是可观察状态和诊断数据。
- `NotificationMetricsStore` 只保存在内存中，重启后指标归零。
- inbox JSON 不是账号隔离路径，当前实现更像设备级应用通知历史；若未来涉及账号敏感内容，需要补账号边界。
- `PushAdapter` 只处理系统授权请求，未发现远端推送 payload 转应用内通知的 adapter。
- 当前没有通知优先级、分组、手动清空历史、免打扰或用户偏好设置。

### 建议演进

- 优先补齐 `NotificationQueue`、`NotificationDeliveryCoordinator` 和 `NotificationInboxStore` 的单元测试，因为这些是去重、持久化和串行消费的风险点。
- 若通知内容可能包含账号敏感信息，应将 inbox 路径或数据字段按 accountID 隔离，并在登出或账号切换时明确清理策略。
- 增加通知历史页面或调试面板，让 `inboxItems` 和 `metricsSnapshot` 有明确用户或开发者入口。
- 将 `PushAdapter` 与业务路由/通知队列解耦接入，明确远端推送到应用内通知的映射规则。
- 增加通知优先级或类型策略，避免 alert 长时间阻塞低优先级 toast/banner。

## 十六、整体验收标准

- [ ] 业务模块通过 `NotificationClient` 发布通知，不直接操作展示 Store。
- [ ] toast、banner、alert 三种 presentation 都能展示和退出。
- [ ] success、info 默认 toast；warning、error 默认 banner。
- [ ] 2 秒内重复 dedupe key 会被丢弃并记录 duplicate。
- [ ] 队列超过 128 条会丢弃新消息并记录 queueOverflow。
- [ ] banner 点击动作能在 dismiss 后执行，关闭按钮不会触发业务动作。
- [ ] alert 未关闭时后续通知不会抢占展示。
- [ ] inbox 能记录 queued、presented、dismissed 和 dropped 状态。
- [ ] metrics 能统计入队、展示、重复丢弃、溢出丢弃和平均展示延迟。
- [ ] 根视图和 fullScreenCover 都能展示同一 Store 的应用内通知。
- [ ] 测试覆盖队列、投递、Store、inbox 和 Host 的核心风险路径。
