# 网络模块需求

## 一、模块目标

建立统一的客户端网络基础模块，为登录、设备注册、账号管理、AI 设置、文件管理、OSS 和 OCR 等业务功能提供一致的后台访问能力。

网络模块需要统一处理以下事项：

- API Base URL 和环境配置。
- 请求模型、URL 拼接、查询参数、请求体和响应体。
- HTTP 传输、超时、取消和网络异常。
- Token 读取、鉴权 Header 注入和 Token 刷新。
- 后台响应包裹格式和业务错误解析。
- 可重试请求、退避等待和 `Retry-After`。
- 同类请求串行执行和并发请求合并。
- ETag、`If-None-Match`、304 和本地响应缓存。
- 401 鉴权失效通知和会话清理。
- 网络请求日志、业务用途标识和敏感信息脱敏。

业务模块只负责接口参数、数据模型和业务结果处理，不重复实现网络基础逻辑。

## 三、API Base URL 与环境配置

### 需求说明

统一配置客户端访问同一个后台服务器的 API Base URL，并支持不同运行环境切换。

### 基础要求

- 支持开发、测试和生产环境配置。
- 所有业务接口只维护相对路径。
- Base URL 与业务接口路径由网络引擎统一拼接。
- 正确处理 Base URL 末尾斜杠和接口路径开头斜杠，避免路径重复或缺失。
- 运行时可以读取当前服务地址，供日志和诊断使用。
- 不允许业务页面硬编码完整服务器地址。

### 验收标准

- 客户端能够访问配置环境对应的后台服务。
- 切换 Base URL 后，业务接口无需逐个修改。
- Base URL 拼接后不会出现双斜杠、路径丢失或查询参数错误。

### 技术细节与设计代码位置

- 运行环境对象负责提供 `apiBaseURL`，由应用启动容器注入 `SupportBackend`。
- NetworkEngine 只接收完整的 Base URL 和相对 `path`，统一通过 URLComponents 拼接路径与 query。
- Base URL 不参与业务 API 的定义，API 只维护类似 `/api/v1/device/register/` 的相对路径。
- 关键代码位置：`SupportClient/SupportClient/App/SupportAppEnvironment.swift`、`SupportClient/SupportClient/Core/Networking/SupportBackend.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkEngine.swift`。

## 四、统一 Backend API 入口

### 需求说明

建立统一 Backend 组合入口，集中持有网络引擎和各业务 API，避免页面直接创建 HTTP 客户端。

### 基础要求

统一 Backend 至少提供以下 API：

| API | 主要职责 | 典型接口 |
| --- | --- | --- |
| AuthAPI | 登录、登出、会话恢复 | 登录、Token 刷新 |
| OTPAPI | 手机号验证码 | 发送验证码、校验验证码 |
| DeviceAPI | 设备登记 | `/api/v1/device/register/` |
| FileAPI | 文件元数据管理 | 注册、列表、业务绑定、删除 |
| OSSAPI | OSS 上传凭证 | `/api/v1/oss/sts/credentials/` |
| OCRAPI | OCR 服务凭证 | `/api/v1/oss/ocr/sts/credentials/` |
| AIConfigAPI | AI 配置同步 | 读取和更新 AI 配置 |
| AccountIdentityAPI | 账号身份管理 | 身份列表、绑定和修改 |
| DeactivationAPI | 账号注销 | 身份验证和注销提交 |

- API 对象统一依赖 BackendConfiguration 或 NetworkEngine。
- API 层负责定义路径、请求参数和响应模型。
- API 层不负责页面状态、路由跳转和本地业务缓存展示。
- API 层使用统一 Operation 执行请求。

### 验收标准

- 所有后台 API 都可以从统一 Backend 入口访问。
- 页面和业务用例不直接依赖底层 HTTP Transport。
- 新增后台接口时只需要增加对应 API 和数据模型。

### 技术细节与设计代码位置

- `SupportBackend` 负责组装 Engine、Configuration 和各领域 API，形成应用级单例依赖图。
- API 对象使用轻量结构体持有 `SupportBackendConfiguration`，不自行创建 Transport、TokenProvider 或缓存。
- `SupportBackendConfiguration.execute` 负责 Operation 调度，`executeDecoded` 负责统一解码。
- 关键代码位置：`SupportClient/SupportClient/Core/Networking/SupportBackend.swift`、`SupportClient/SupportClient/Core/Networking/SupportAPIs.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportBackendConfiguration.swift`、`SupportClient/SupportClient/App/AppContainer.swift`。

## 五、请求模型与 HTTP 封装

### 需求说明

将每次网络访问抽象为统一请求模型，由 NetworkEngine 完成构建和发送。

### 请求模型

请求至少包含：

- HTTP 方法：GET、POST、PUT、PATCH、DELETE。
- 相对路径。
- 查询参数。
- 自定义请求头。
- 请求体类型：无请求体、JSON、原始字节。
- 单次请求超时时间。
- 鉴权、缓存、重试、串行键和优先级等 NetworkStrategy。

### HTTP 封装要求

- JSON 请求自动设置 `Content-Type: application/json`。
- 原始字节请求必须支持自定义 `Content-Type`。
- 统一处理响应状态码、响应体和响应头。
- 每个出站请求生成唯一 `X-Request-ID`。
- 支持请求取消，并将取消状态转换为统一错误。
- 支持单请求覆盖默认超时时间。
- 网络传输层与业务 API 层解耦，便于单元测试替换 Transport。

### 验收标准

- 业务代码不重复拼接 URL、序列化 JSON 或设置基础请求头。
- 请求和响应能够通过 Request ID 关联日志。
- 请求取消后不会继续执行后续业务状态更新。

### 技术细节与设计代码位置

- `SupportNetworkRequest` 描述 method、path、queryItems、headers、body、timeoutInterval 和 strategy。
- `SupportBody.json` 使用统一 JSONEncoder，`SupportBody.raw` 用于文件或特殊 Content-Type 的字节数据。
- `SupportNetworkEngine.performAttempt` 负责把请求模型转换为平台 URLRequest，再交给 Transport。
- Transport 只负责真实发送，不负责业务解码和页面状态。
- 关键代码位置：`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkModels.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkEngine.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkTransport.swift`。

## 六、响应格式与数据解码

### 需求说明

兼容后台统一包裹响应和直接返回响应两种格式。

### 响应模式

#### 统一包裹响应

```json
{
  "code": 0,
  "msg": "",
  "data": {}
}
```

- `code == 0` 时返回 `data`。
- `code != 0` 时转换为业务错误。
- `msg` 用于错误提示和诊断日志。

#### 直接响应

部分接口，例如 Token 刷新接口，根对象直接就是目标数据，不经过 `data` 包裹，需要支持直接解码。

### 数据兼容要求

- 统一配置 JSON Decoder 的命名转换规则。
- 兼容服务端字段命名差异，例如 `access`、`access_token`、`fileUuid`、`file_uuid`。
- 兼容日期字符串、时间戳和空值等常见格式。
- 对后端错误中的字符串、对象和数组消息提供兼容解析。

### 验收标准

- 统一包裹接口和直接响应接口都能正确解析。
- 后台业务错误不会被误判为成功数据。
- 字段命名和日期格式差异不会导致正常响应整体解码失败。

### 技术细节与设计代码位置

- `backendWrapped` 先解码 `BackendWrappedResponse<T>`，检查 `code` 后返回 `data`。
- `direct` 直接将响应体解码为目标模型，适用于 Token 刷新等非包裹响应。
- 解码失败必须保留响应状态码、请求路径和脱敏后的 body 摘要，便于定位字段契约问题。
- 关键代码位置：`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkEngine.swift`、`SupportClient/SupportClient/Projects/Core/Networking/API/Common/SupportAPIResponseDecoder.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkModels.swift`。

## 七、Operation 与 BackendConfiguration

### 需求说明

将每个接口调用抽象为独立 Operation，通过统一配置容器执行。

### 基础要求

每个 Operation 至少包含：

- Operation 名称。
- API 名称。
- NetworkRequest。
- 可选的并发回调合并 Key。
- 统一执行方法。

BackendConfiguration 负责：

- 持有 NetworkEngine。
- 持有 DeviceCache 和 CallbackCache。
- 输出 API 和业务用途日志。
- 执行 Operation。
- 将响应解码为目标数据类型。

### 验收标准

- 网络调度、日志和解码逻辑集中在统一配置层。
- 业务 API 不直接管理请求执行生命周期。
- 单个 Operation 可以独立测试和替换请求 Transport。

### 技术细节与设计代码位置

- Operation 是网络调用的最小业务单元，包含 `name`、`apiName`、`request` 和可选 `callbackCacheKey`。
- Configuration 先记录业务用途，再执行回调合并或直接调用 Operation。
- Operation 不保存页面状态，不持有 ViewModel，不处理路由跳转。
- 关键代码位置：`SupportClient/SupportClient/Projects/Core/Networking/Operations/SupportNetworkOperation.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportBackendConfiguration.swift`、`SupportClient/SupportClient/Projects/Core/Networking/Logging/SupportNetworkOperationBusinessPurpose.swift`。

## 八、鉴权 Header 与 Token 管理

### 需求说明

统一管理 Access Token、Refresh Token 和鉴权 Header，为需要登录的 API 自动提供有效身份凭证。

### Token 数据

Token 管理至少包含：

- Access Token。
- Refresh Token。
- Token 类型，默认支持 `Bearer`。
- Access Token 到期时间。
- 内存中的当前 Token。
- 安全存储中的持久化 Token。

### 基础流程

1. 业务请求声明 `requiresAuth`。
2. NetworkEngine 向 AuthTokenProvider 获取有效 Token。
3. AuthTokenProvider 判断 Token 是否接近过期。
4. 未过期则生成 `Authorization: Bearer <token>`。
5. 即将过期则先调用刷新接口，再使用新 Token 请求。
6. Token 不存在时返回未登录错误。

### 安全要求

- Token 使用系统安全存储能力持久化。
- Token 不写入普通缓存、业务日志或错误提示。
- 退出登录、明确刷新失败和 401 失效时清理 Token。
- 公开接口不得被错误添加鉴权 Header。

### 验收标准

- 需要鉴权的 API 自动携带有效 Token。
- Token 临近过期时能够自动刷新。
- Token 不存在或已清理时请求能够明确返回未登录状态。

### 技术细节与设计代码位置

- API 通过 `NetworkStrategy.requiresAuth` 声明是否需要 Authorization，不由页面手动传 Header。
- Engine 在每次真实请求前异步读取最新 Token，避免并发请求使用旧 Token。
- Token 持久化与普通业务缓存隔离；Access Token、Refresh Token、过期时间和 tokenType 作为一个完整快照保存。
- 关键代码位置：`SupportClient/SupportClient/Projects/Core/Networking/AuthTokenProvider.swift`、`SupportClient/SupportClient/Projects/Foundation/Security/SparkKeychain.swift`、`SupportClient/SupportClient/App/AppSessionStore.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkModels.swift`。

## 九、Token 刷新与并发去重

### 需求说明

解决多个请求同时发现 Token 过期时重复刷新、互相覆盖或产生竞态的问题。

### 基础要求

- 同一时间只允许一个刷新任务实际访问刷新接口。
- 其他并发请求等待同一个刷新任务结果。
- 刷新成功后更新内存和安全存储中的完整 Token 信息。
- 兼容刷新接口返回 `access`/`refresh` 和 `access_token`/`refresh_token` 两种字段。
- 从 JWT `exp` 解析 Access Token 到期时间。
- 刷新请求携带设备 ID、Bundle ID 等后台需要的设备信息。
- 401 响应触发强制刷新，并在刷新成功后重试原始请求一次或按策略执行。

### 刷新失败分类

- `missingTokens`：本地没有刷新凭证，直接进入未登录状态。
- `refreshFailed`：后台明确判定 Refresh Token 无效，清理会话并通知失效。
- `refreshTemporarilyUnavailable`：网络或服务暂时不可用，保留本地凭证，允许后续重试。
- `invalidRefreshResponse`：刷新响应无法解析，返回刷新异常。

### 验收标准

- 并发请求不会同时发起多次 Token 刷新。
- 临时刷新失败不会误清理仍可能有效的本地登录态。
- 明确的刷新凭证失效能够清理 Token 并回到登录流程。

### 技术细节与设计代码位置

- `AuthTokenProvider` 使用 actor 隔离 `cachedTokens` 和 `refreshTask`，保证 Token 读写和刷新状态串行化。
- 第一个调用方创建刷新 Task，后续调用方直接等待同一个 Task 的结果。
- 刷新成功后解析 JWT `exp`，生成新的 `AuthTokens` 并同时更新内存和安全存储。
- 刷新失败需要区分明确鉴权失败、临时网络失败和无效响应，决定是否清理会话。
- 关键代码位置：`SupportClient/SupportClient/Projects/Core/Networking/AuthTokenProvider.swift`、`SupportClient/SupportClient/Foundation/JWTExpParser.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkEngine.swift`。

## 十、网络错误与后台错误解析

### 需求说明

将 HTTP、传输、取消、解码和后台业务错误转换为统一错误类型。

### 错误分类

- `transport`：DNS、连接失败、网络断开、超时等传输错误。
- `http`：服务器返回非成功 HTTP 状态码，并携带状态码、BackendError 和原始数据。
- `refreshFailed`：Token 刷新失败。
- `cancelled`：请求被主动取消或任务取消。
- `decoding`：响应无法解析为目标模型。
- `invalidResponse`：响应结构无效。

### 后台错误解析

- 解析 `{ code, msg, data }` 结构。
- `msg` 支持字符串。
- `msg` 为对象时，优先提取 `detail`、`code` 或可读字段。
- 记录状态码、业务码和脱敏后的错误消息。
- 通过错误本地化模块将后台错误转换为用户可理解的提示。

### 验收标准

- 业务层不需要识别底层 URLSession、ArkWeb 或系统网络错误细节。
- 网络异常和业务异常能够分别处理。
- 错误提示不会直接暴露 Token、API Key 或完整敏感响应体。

### 技术细节与设计代码位置

- `SupportNetworkError` 是跨网络层和业务层的统一错误边界。
- `BackendError` 解析服务端 `code`、`msg`、`data`，兼容 `msg` 为字符串或对象的情况。
- `BackendErrorLocalizer` 按业务码、消息关键字和 HTTP 状态码生成本地化文案。
- 原始错误作为诊断上下文保留在日志，不直接作为 UI 文案展示。
- 关键代码位置：`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkModels.swift`、`SupportClient/SupportClient/Projects/Core/Networking/BackendErrorLocalizer.swift`、`SupportClient/SupportClient/Projects/Core/Networking/API/Common/SupportAPIResponseDecoder.swift`。

## 十一、重试策略与退避

### 需求说明

仅对可恢复且允许重试的请求执行自动重试，避免重复提交业务操作。

### 默认重试规则

- 默认最多重试 2 次，不包含首次请求。
- 可重试 HTTP 状态码：429、500、502、503、504。
- 可重试网络错误：超时、找不到主机、无法连接主机、连接丢失、无网络、DNS 查询失败。
- 优先遵循服务端 `Retry-After` 响应头。
- 没有 `Retry-After` 时使用退避间隔，例如 `0`、`0.75`、`3` 秒。

### 幂等性规则

- GET 请求默认允许重试。
- POST、PATCH、DELETE 等非 GET 请求默认不自动重试。
- 非 GET 请求只有显式声明 `isIdempotent` 后才允许重试。
- 401 不走普通重试，而是优先执行 Token 刷新流程。
- 请求取消不得触发重试。

### 验收标准

- 临时网络故障和 5xx/429 能按规则退避重试。
- 非幂等操作不会被无条件重复提交。
- 达到次数上限后返回最终错误。
- 重试过程可以通过日志识别当前次数和等待原因。

### 技术细节与设计代码位置

- `RetryConfig` 是请求级策略，允许每个 API 覆盖最大次数、状态码、网络错误集合和退避间隔。
- `RetryPolicy` 先判断状态码或 URLError，再计算等待时间；`RetryAfterParser` 支持秒数和 HTTP 日期两种格式。
- Engine 将 401 刷新流程与普通 429/5xx 重试分开，避免鉴权失败被普通重试吞掉。
- 关键代码位置：`SupportClient/SupportClient/Projects/Core/Networking/RetryLayer.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkEngine.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkModels.swift`。

## 十二、串行请求门控与优先级

### 需求说明

对具有顺序要求的同类请求进行串行调度，避免并发更新造成数据覆盖或资源竞争。

### 基础要求

- 每个请求可以配置 `serialKey`。
- 相同 `serialKey` 的任务依次执行。
- 不同 `serialKey` 的任务可以并行执行。
- 请求按优先级调度：非常高、高、普通、低。
- 重试任务使用统一重试优先级，避免重试任务阻塞正常请求。
- 队列任务支持取消。
- 文件列表、OSS STS、OCR STS 等需要防重复的请求可以使用固定串行键。

### 验收标准

- 同一串行键下不会同时执行两个真实请求。
- 不同业务请求不会被不必要地全局串行化。
- 重试和正常请求的执行顺序符合优先级规则。

### 技术细节与设计代码位置

- `SerialRequestGate` 以 `serialKey` 保存多个独立队列，每个队列只允许一个任务运行。
- 队列排序先比较优先级，再比较入队序号，保证同优先级任务 FIFO。
- 首次请求使用业务配置的优先级，重试任务切换为 retry 优先级。
- 关键代码位置：`SupportClient/SupportClient/Projects/Core/Networking/SerialRequestGate.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkModels.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkEngine.swift`。

## 十三、同类请求回调合并

### 需求说明

当多个页面或用例同时读取同一 GET 资源时，只发送一次真实网络请求，其他调用方共享同一个请求结果。

### 基础要求

- GET 请求根据方法、路径和查询参数生成合并 Key。
- 首个请求创建并保存进行中的 Task。
- 后续相同 Key 的请求等待已有 Task。
- 请求成功或失败后移除进行中的 Task。
- 不同查询参数必须生成不同 Key。
- POST、PATCH、DELETE 等修改请求默认不进行回调合并。

### 验收标准

- 同一资源的并发读取只产生一次真实请求。
- 并发调用方可以获得相同结果或相同错误。
- 请求完成后不会残留失效 Task，后续请求可以重新发起。

### 技术细节与设计代码位置

- GET 请求使用 method、path 和 query 生成 callback cache key，查询参数顺序和内容必须稳定。
- `SupportCallbackCache` 只缓存进行中的 Task，不把成功响应永久当作业务数据缓存。
- Task 成功、失败或取消后都必须从 in-flight 字典移除。
- 关键代码位置：`SupportClient/SupportClient/Projects/Core/Networking/Caching/SupportCallbackCache.swift`、`SupportClient/SupportClient/Projects/Core/Networking/Operations/SupportNetworkOperation.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportBackendConfiguration.swift`。

## 十四、ETag 与 HTTP 响应缓存

### 需求说明

通过 ETag 条件请求减少重复传输，并在收到 304 时使用本地响应体恢复完整数据。

### 缓存流程

1. 业务请求声明 `allowETag`。
2. 根据 URL、查询参数和鉴权信息生成稳定缓存 Key。
3. 有未过期 ETag 时添加 `If-None-Match`。
4. 服务端返回 2xx 且带 ETag 时持久化 ETag、响应体和过期信息。
5. 服务端返回 304 时读取本地响应体，合并为可解码的完整响应。
6. 没有本地响应体时，304 不得被误判为成功。
7. 本地缓存过期时删除缓存，不再发送过期 ETag。

### 过期规则

缓存有效期优先级：

1. `Cache-Control: no-store`：立即过期，不继续复用。
2. `Cache-Control: max-age`：按服务端秒数计算。
3. `Expires`：按 HTTP 日期计算。
4. 请求声明的 `etagTTL`。
5. 网络模块默认 TTL，当前 SupportClient 默认约 300 秒。

### 安全和隔离

- 缓存 Key 必须包含鉴权指纹，避免不同用户共享响应。
- 缓存数据只能用于对应的 URL 和查询参数。
- Token 和 API Key 本身不进入响应缓存内容。
- 账号切换、退出登录和鉴权失效时清理账号相关缓存。

### 验收标准

- 首次成功响应可以保存 ETag 和响应体。
- 后续请求可以携带 `If-None-Match`。
- 304 能够正确合并本地响应并正常解码。
- 过期缓存不会继续被使用。
- 不同账号、不同查询条件之间不会串用缓存。

### 技术细节与设计代码位置

- ETag cache key 由 URL、query 和 Authorization 指纹生成，再通过 SHA256 得到稳定文件名。
- 元数据保存 ETag、最后更新时间和过期时间；body 单独保存，便于 304 合并。
- 开启 ETag 的请求使用 `reloadIgnoringLocalCacheData`，确保真实收到服务端 304，而不是被系统 URLCache 透明合并。
- `ETagHTTPInterceptor` 在 2xx 响应保存缓存，在 304 响应读取 body 并设置 `didMerge304`。
- 关键代码位置：`SupportClient/SupportClient/Projects/Core/Networking/ETagStore.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkEngine.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkModels.swift`。

## 十五、设备缓存与本地状态

### 需求说明

缓存网络相关的设备级状态，支持冷启动恢复和会话清理。

### 可缓存内容

- 当前用户 ID。
- 可信设备 ID。
- 上次登录账号 ID。
- 日志级别。
- 设备登记摘要。
- ETag 元数据和响应体索引。

### 清理要求

- 支持清理已认证设备状态。
- 支持清理设备元数据。
- 支持清理全部缓存。
- 支持单独清理 ETag 响应缓存。
- 退出登录和账号切换时清理账号相关状态。
- 设备登记失败时保留可安全复用的登记摘要，避免无意义重复登记。

### 验收标准

- 冷启动可以恢复允许持久化的设备状态。
- 账号切换后不会读取上一个账号的业务状态。

### 技术细节与设计代码位置

## 十六、网络状态监听

### 需求说明

监听设备网络状态，为应用启动、页面展示和请求调度提供网络可用性判断。

### 基础要求

- 识别网络可用、不可用和状态未知。
- 应用启动阶段先完成网络状态评估，再决定是否进入启动引导。
- 无网络时向页面提供统一网络异常状态。
- 网络恢复后更新状态，不自动重复触发多次启动流程。
- 网络状态变化不能绕过请求重试和取消规则。

### 验收标准

- 无网络时客户端能够显示网络不可用状态。
- 网络恢复后状态能够及时更新。
- 网络变化不会造成重复登录、重复设备登记或重复页面跳转。

### 技术细节与设计代码位置

- `NetworkPathMonitor` 发布 `hasEvaluatedPath` 和 `isSatisfied` 两类状态，区分“尚未评估”和“已确认无网络”。
- `AppCoordinatorView` 根据网络状态覆盖 `NetworkGateView`，启动任务等待网络评估完成。
- `AppLifecycleCoordinator` 只在网络状态满足条件后执行启动恢复，避免冷启动时连续失败。
- 关键代码位置：`SupportClient/SupportClient/Foundation/NetworkPathMonitor.swift`、`SupportClient/SupportClient/App/AppCoordinatorView.swift`、`SupportClient/SupportClient/App/Presentation/NetworkGateView.swift`、`SupportClient/SupportClient/App/AppLifecycleCoordinator.swift`。

## 十七、401 鉴权失效通知

### 需求说明

统一处理 HTTP 401 和后台业务层明确表示 Token 失效的情况。

### 失效识别

- HTTP 状态码为 401。
- 后台业务码处于鉴权失效范围，例如 40100-40199。
- 错误消息包含明确 Token 失效标识，例如 `token_not_valid`、`invalid_token`、`token_expired`。
- 不能仅凭网关错误页或无法解析的临时响应就清理本地登录态。

### 基础流程

1. NetworkEngine 收到需要鉴权请求的 401。
2. AuthTokenProvider 强制刷新 Token。
3. 刷新成功则更新 Token 并重试原请求。
4. 刷新失败时解析后台错误。
5. 明确 Refresh Token 失效则清理 Token、会话快照和账号缓存。
6. 发布全局会话失效事件。
7. 路由层统一切换到登录页。

### 防重复要求

- 相同会话失效期间只允许触发一次全局失效通知。
- 401 失败请求不得无限重试。
- 会话清理操作必须幂等。

### 验收标准

- Access Token 过期但 Refresh Token 有效时，用户无感完成刷新。
- Refresh Token 明确失效后能够回到登录页面。
- 失效后不再使用旧 Token 访问鉴权接口。

### 技术细节与设计代码位置

- `SupportAuthSessionInvalidation.shouldInvalidate` 综合 HTTP status、backend code 和错误消息判断是否失效。
- Engine 收到 401 后调用 `forceRefreshTokens`，刷新失败时才发布全局失效事件。
- `AppRouteCoordinator` 监听失效通知，`AppLifecycleCoordinator` 执行清理，`AppSessionStore` 更新内存会话状态。
- 401 请求必须设置重试上限，并且刷新失败后不得回到普通重试循环。
- 关键代码位置：`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkModels.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkEngine.swift`、`SupportClient/SupportClient/App/AppCoordinatorView.swift`、`SupportClient/SupportClient/App/AppLifecycleCoordinator.swift`。

## 十八、日志与诊断

### 需求说明

为每次网络操作提供可追踪、可脱敏的诊断信息。

### 日志内容

- API 名称和 Operation 名称。
- 业务用途，例如认证、设备、文件、OSS、OCR 或 AI 配置。
- HTTP 方法和相对路径。
- 查询参数摘要。
- Request ID。
- 是否需要鉴权、是否启用 ETag、是否启用重试。
- 串行 Key、队列优先级和重试次数。
- HTTP 状态码、响应字节数和请求耗时。
- 缓存命中、缓存过期、ETag 应用、304 合并和回调合并状态。

### 脱敏要求

- 不输出完整 Access Token、Refresh Token、API Key 和 STS Secret。
- URL 中的敏感查询参数必须脱敏。
- 请求体和响应体只输出安全摘要或截断内容。
- 错误日志不能包含完整凭证。

### 验收标准

- 可以通过 Request ID 定位完整请求链路。
- 可以区分真实请求、重试请求、缓存命中和请求合并。
- 诊断日志不泄露认证凭证和云服务密钥。

### 技术细节与设计代码位置

- Transport 记录 method、脱敏 URL、Request ID、请求/响应字节数、状态码和耗时。
- BackendConfiguration 记录 API、Operation、业务用途、鉴权开关、ETag、重试配置、串行 Key 和队列优先级。
- 日志分为 app、network、auth、cache、oss 等模块，便于按功能过滤。
- `NetworkLogSanitizer` 负责 Header、URL、请求体和响应体预览脱敏与截断。
- 关键代码位置：`SupportClient/SupportClient/Foundation/Logger.swift`、`SupportClient/SupportClient/Projects/Core/Networking/Logging/SupportNetworkingStrings.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkTransport.swift`、`SupportClient/SupportClient/Projects/Core/Networking/SupportBackendConfiguration.swift`。

## 二十一、整体验收标准

- 所有业务 API 通过统一 Backend 和 NetworkEngine 访问后台。
- 统一支持 JSON、错误解析、请求取消、超时和 Request ID。
- 需要鉴权的请求自动携带有效 Token，并支持并发刷新去重。
- 401 能够优先刷新 Token，明确失效后清理会话并通知路由。
- GET 请求支持回调合并和按需 ETag 缓存。
- 304 响应能够使用本地 body 恢复为可解码数据。
- 重试遵循状态码、网络错误、幂等性和 `Retry-After` 规则。
- 相同串行键的请求按队列顺序执行。
- 账号、设备、ETag 和文件缓存能够按范围安全清理。
- 网络日志可诊断，但不泄露 Token、API Key 和 STS 密钥。
- 接口路径、字段、错误码和 Token 规则与 `SupportClient` 使用同一后台契约。

## 16. 核心数据模型与参数约定

以下内容以当前 `SupportClient` 网络层实现为准，用于后续迁移或重构时保持字段、参数和行为一致。

### 16.1 HTTP 请求模型

代码位置：

```text
SupportClient/SupportClient/Projects/Core/Networking/SupportNetworkModels.swift
```

| 类型 | 核心字段 | 参数含义 |
| --- | --- | --- |
| `SupportHTTPMethod` | `get`、`post`、`put`、`patch`、`delete` | API 请求方法；GET 通常允许 ETag 和回调合并，写操作必须明确幂等性 |
| `SupportBody` | `none`、`json(AnyEncodable)`、`raw(Data, contentType)` | 请求体类型；JSON 请求必须通过 `AnyEncodable` 编码，原始数据必须显式声明 MIME 类型 |
| `SupportNetworkRequest` | `method`、`path`、`queryItems`、`headers`、`body`、`timeoutInterval`、`strategy` | 业务 API 只提供相对路径和业务参数，绝对 URL、鉴权 Header、重试和缓存由网络层补齐 |
| `SupportNetworkResponse` | `data`、`httpResponse`、`didMerge304` | 统一返回原始响应数据、HTTP 元数据和是否由 304 使用本地缓存体 |
| `AnyEncodable` | `wrapped` | 将不同的 `Encodable` 请求模型统一放入 `SupportBody.json` |

`SupportNetworkRequest.path` 必须是后端相对路径，例如 `/api/v1/files/`。禁止业务模块自行拼接环境域名、Authorization、User-Agent 或 Request ID。

### 16.2 网络策略模型

| 类型 | 核心字段 | 参数含义 |
| --- | --- | --- |
| `NetworkStrategy` | `requiresAuth` | 是否获取并注入 Bearer Token；登录、刷新 Token 等认证入口不能依赖当前用户 Token |
| `NetworkStrategy` | `allowETag` | 是否启用 ETag、`If-None-Match` 和 304 本地响应复用 |
| `NetworkStrategy` | `serialKey` | 同一业务资源的串行键，例如 `files.list`、`oss.sts.credentials` |
| `NetworkStrategy` | `retryConfig` | 当前请求的重试次数、状态码、网络错误和 Retry-After 策略 |
| `NetworkStrategy` | `isIdempotent` | 是否允许网络层在请求已发出但结果不确定时重试；POST 默认必须谨慎设置 |
| `NetworkStrategy` | `queuePriority` | 请求进入串行门控时的优先级，`veryHigh`、`high`、`normal`、`low` |
| `NetworkStrategy` | `etagTTL` | 本地 ETag 响应缓存的有效期；过期后仍可发送条件请求，但不能直接视为新鲜数据 |

默认重试配置：开启重试、最多重试 2 次、退避间隔约为 `0s`、`0.75s`、`3s`，可重试状态码包括 `429`、`500`、`502`、`503`、`504`，并识别超时、断网、连接失败和 DNS 失败等网络错误。

### 16.3 Operation 模型

代码位置：

```text
SupportClient/SupportClient/Projects/Core/Networking/Operations/SupportNetworkOperation.swift
```

```swift
protocol SupportNetworkOperation: Sendable {
    var name: String { get }
    var apiName: String { get }
    var request: SupportNetworkRequest { get }
    var callbackCacheKey: String? { get }

```

核心参数：

`CacheableSupportNetworkOperation` 适合 GET 或可安全合并的请求。非幂等写操作不能仅因为路径相同就自动合并。

| 类型 | 核心字段/参数 | 使用边界 |
| --- | --- | --- |

## 22. 重试、串行门控、回调合并与 ETag 的方法参数

### 22.1 RetryPolicy

代码位置：`SupportClient/SupportClient/Projects/Core/Networking/RetryLayer.swift`

```swift
init(config: RetryConfig, scheduler: RetryScheduler)
```

判定输入：请求的 HTTP 方法、`isIdempotent`、当前重试次数、`SupportNetworkError`、HTTP 状态码、`Retry-After` 值。只有满足幂等性、次数未超限且错误属于允许范围时才进入退避调度。

### 22.2 `SerialRequestGate`

代码位置：`SupportClient/SupportClient/Projects/Core/Networking/SerialRequestGate.swift`

门控键由 `serialKey` 决定；相同键的请求按 `RequestQueuePriority.gatePriority` 排序并串行执行，不同键默认允许并发。典型用途：Token 刷新、STS 获取、账号身份变更和文件列表刷新。

### 22.3 `SupportCallbackCache`

同类 GET 请求的合并键至少包含：HTTP 方法、规范化 path、排序后的 query 参数。合并结果是同一个 in-flight Task 的结果，不能把失败结果长期缓存，也不能合并带有不同鉴权账号或不同业务上下文的请求。

### 22.4 `ETagStore` 与 304

代码位置：`SupportClient/SupportClient/Projects/Core/Networking/ETagStore.swift`

```swift
func record(forKey key: String) -> ETagCacheRecord?
func cachedBody(forKey key: String) -> Data?
func store(record: ETagCacheRecord, body: Data, forKey key: String) throws
func removeCache(forKey key: String)
```

`ETagCacheRecord`：`etag`、`lastUpdated`、`expirationDate`。请求命中已有记录时发送 `If-None-Match`；服务端返回 304 时读取 `cachedBody`，构造 `SupportNetworkResponse(data:httpResponse:didMerge304: true)`；缓存体损坏或缺失时必须放弃 304 合并并重新请求。

## 23. 各模块统一实现模板

新增业务 API 必须按以下顺序落地：

1. 在对应 `API/<Domain>` 目录定义请求 DTO、响应 DTO 和业务错误需要的字段。
2. 为每个公开方法创建 `SupportNetworkOperation`，填充 `name`、`apiName`、HTTP 方法、相对路径、请求体和 `NetworkStrategy`。
3. 通过 `SupportBackendConfiguration.executeDecoded` 执行，不直接调用 `URLSession`。
4. 明确 `wrapped` 模式，确认后端响应是 `{ code, msg, data }` 还是直接对象/数组。
5. 为 GET 资源补充 `allowETag`、`etagTTL`、`serialKey` 和回调合并规则。
6. 为写操作明确 `isIdempotent`；没有服务端幂等键时禁止自动重试。
7. 在日志中记录 Operation、业务用途、状态、耗时、Request ID 和脱敏后的参数摘要。
8. 在测试中覆盖成功响应、业务失败、HTTP 401、HTTP 429、断网、解码失败、304 和并发合并。

## 24. 数据模型与方法参数验收标准

- 所有 API 请求模型的 JSON 键名与后端契约一致，特别是 `bundleId`、`deviceId`、`otpId`、`accessToken`、`refreshToken` 等兼容字段。
- 所有响应 DTO 明确必填字段、可选字段、空响应行为和后端字段兼容策略。
- 所有公开网络方法记录完整参数含义、默认值、是否鉴权、是否允许重试、是否进入串行门控和返回类型。
- Token、API Key、STS Secret、Authorization 和验证码不得进入普通日志、ETag 文件或非安全缓存。
- 账号级缓存、设备级缓存、游客缓存和临时凭证缓存具有明确命名空间，并在登出、账号切换、401 失效时按边界清理。
- 相同 Operation 在并发调用时不会重复刷新 Token、重复获取 STS 或重复执行同类 GET。
- 新增 API 不绕过 `SupportBackend`、`SupportBackendConfiguration`、`SupportNetworkEngine` 和统一 Transport。
