## 1. 功能目标

定义制作额度、邀请及分享奖励，并规划额度刷新、邀请与活动通知。

## 2. 制作额度与邀请／分享奖励

**原始诉求**：达到制作上限后，通过邀请、分享或分享生成视频获得额度。

**代理任务**：梳理额度展示、扣减、刷新、耗尽提示、奖励发放和到账记录；分别定义邀请、分享、视频生成／分享的奖励条件；设计重复请求与重复领取处理。

**待确认**：基础积分额度及用量换算参数见第 4 节；各类奖励数量与上限；邀请以注册还是首次制作为准；生成视频是否即可奖励，还是必须分享；如何验证有效分享。

**验收建议**：额度记录可追溯；重复回调不重复发奖；同一调用重复记账不重复扣减，实际新调用继续计费；奖励满足条件后到账。不能将“点击分享”未经定义就当成“有效传播”。

## 3. 消息通知

**原始诉求**：额度刷新通知、邀请通知，考虑活动通知。

**代理任务**：定义每类通知的触发事件、内容、频次、站内／系统推送渠道与点击目的页；复用既有通知能力，设计开关与去重。

**待确认**：额度刷新是否每次通知；邀请通知指邀请到达还是奖励到账；活动通知是否首期纳入；静默时段及通知偏好。

**验收建议**：触发与真实业务状态一致；同一事件不重复发送；关闭后按约定不再通知；点击进入正确页面；拒绝系统推送权限不影响核心制作。

## 4. 当前方案与决策状态

更新时间：2026-11-14。此版本替代此前按业务动作固定收取 1、5、10、15 积分的方案。

### 4.1 已确定的产品方向

- 计费分类简化为文本 AI 和图片 AI。
- 服务端将调用用量折算成积分，客户端展示制作额度剩余百分比。
- 保留 5 小时和 7 天两个恢复周期。
- 调用消耗额度，生成失败、超时、取消和用户未保存成果均不构成退款条件。
- 制作任务内部的每次实际模型调用分别记录用量，汇总为本轮消耗。

### 4.2 本文采用的落地建议

以下为待实现验证的设计建议，具体参数尚未定案。

- 文本同时计入输入和输出 token，分别配置系数。
- 图片优先使用供应商可返回的实际计费用量；模型支持图片 token 时按 token，按张计量的模型使用张数与规格折算。
- 两个周期同步累计相同积分，各自计算剩余比例。
- 延续首次使用起算方式。首次授权调用启动周期，查询不启动周期。
- 有用量按实际用量计费；调用失败且用量无法取得时使用模型配置的最低调用消耗，标记为估算。
- 初期每账号最多一笔待记账的模型调用，避免多设备并发透支；客户端内部并行模型调用需要排队执行。此项会影响现有制作速度，实施前评估。

### 4.3 待确定参数与依赖

发布前确定两个周期的积分上限、各模型输入输出系数、图片计量单位、最低调用消耗、最大输出预算、用量等待时限和小数精度。建议积分保留六位小数，使用 Decimal 或整数微积分存储。

核实当前文本及图片供应商能返回哪些 usage 字段、流式中断能否查询用量、是否有服务端查询凭据。上述能力未核实，本文不假定所有图片模型都有 token 用量。

## 5. 两类计量规则

| 计费分类 | 包含功能 | 用量依据 |
| --- | --- | --- |
| text_ai | 润色、文字生成、排版方案、背景提示词、文本审查 | 输入、输出 token 及供应商计费明细 |
| image_ai | 背景生成、图片编辑 | 图片 token 或生成张数与规格 |

业务功能名称只用于记录来源，不参与固定定价。排版加背景分别汇总实际文本调用和图片调用。

### 5.1 文本公式

文本积分 = 普通输入 token / 1000 × 输入系数 + 缓存输入 token / 1000 × 缓存系数 + 输出 token / 1000 × 输出系数。

- 单位统一为每千 token 对应的积分数，系数按模型和版本配置。
- 普通输入与缓存输入必须互斥。供应商 input_tokens 已含缓存时，应先扣除缓存部分再分别计算。
- 推理 token、图片理解 token 等是否已包含在输入输出字段中，由供应商适配器明确映射，禁止重复累加。
- 图片作为文本模型的理解输入仍归入 text_ai，根据该模型返回的 usage 计量。

### 5.2 图片公式

- token 模式按供应商返回的输入输出计量字段及对应系数计算。
- 按张模式按实际计费张数 × 模型及规格系数计算，规格包括供应商实际区分的分辨率、质量等参数。
- 每个模型版本明确一种计量方式，禁止同时按 token 和张数重复收费。
- 图片调用无有效计量数据时使用该模型的最低调用消耗，并标记 estimated。

### 5.3 调用、重试和失败

- 计费对象为一次供应商调用 call_id，制作任务 task_id 用于聚合。
- 一次排版中发生三次模型调用，就分别累计三次用量。一个调用的流式分片、轮询、下载和重复上报只形成一笔最终用量。
- 新模型请求，包括用户重试和 SDK 实际重试，创建新 call_id 并独立计费。传输重发若复用了供应商幂等键且未创建新执行，则复用原 call_id。
- 已有结果的应用、保存、导出、手动编辑不产生模型费用。
- 失败或取消但有可信 usage 时照常计费。已确认发起调用却没有 usage 时采用最低调用消耗，不以失败为由返还。
- 鉴权、参数或余额检查拒绝且尚未授权模型调用的请求不收费。

## 6. 扣费流程与双周期

实际 token 只有调用后才能确定。流程采用调用前准入、调用后按用量记账；计费不依赖作品是否生成成功。

1. 客户端为每次模型调用生成并持久化 call_id，向服务端申请调用。
2. 服务端校验账号、模型、场景、策略和当前待记账调用，锁定费率版本及两个窗口。
3. 根据输入量、最大输出量或图片规格确定本次调用的上界预算，两个窗口均能覆盖才授权。这里的预算用于准入，不写消费或积分预占流水。
4. 首期通过每账号一笔待记账调用防止预算被并发重复使用，返回一次调用许可。
5. 模型返回后取得 usage，服务端原子增加两个窗口已用积分，记录唯一 charge 流水并解除待记账状态。
6. 成功、失败、取消均走同一用量记账路径。没有 usage 的调用在等待时限后按最低消耗记账并解除阻塞。

准入上界需要供应商可执行的最大输出限制和明确的计量规则。无法给出可靠上界的模型需配置保守预算并标明限制。实际费用意外超过剩余额度时仍完整记录，剩余比例归零，阻止继续调用；后台记录超预算原因，禁止静默截断实际用量。

### 6.1 窗口规则

- 两个窗口分别为 5 小时、168 小时，从首次授权调用开始计时。
- 剩余积分 = max(0, 上限 - 已用积分)，剩余比例 = 剩余积分 / 上限。上限为 0 时比例为 0 并禁止新调用。
- 到期后恢复完整额度，下次授权建立新窗口。两个窗口独立恢复。
- 调用按授权时绑定的窗口记账，跨周期返回的用量写回原窗口，不能转扣新窗口。
- 修改费率不改变已授权调用，修改周期上限不改变活跃窗口。
- 迟到的可信用量替换估算总额，按差额修正原窗口和流水。减少部分属于计量纠错，不属于失败退款；重复纠错必须幂等。

仅作计算示例，短窗口上限 100、长窗口上限 500，一轮累计消耗 7.5 积分后，分别剩余 92.5% 和 98.5%。具体上限和换算系数待确定。

## 7. 客户端表现

- 设置页与 AI 工作区显示「5 小时制作额度」「7 天制作额度」、剩余百分比和恢复倒计时。
- 用户界面不显示积分、token 单价或业务操作次数。
- 消耗按实际用量确定，开始前显示「按 AI 用量消耗制作额度，失败或取消也会消耗」。可提供标明预计的范围，不展示固定价格承诺。
- 调用尚未记账时显示「用量更新中」，最终用量到达后刷新百分比。
- 无周期显示「剩余 100% · 首次制作后开始计时」；到期显示「额度已恢复」。
- 小于 1% 且大于 0 显示「不足 1%」。服务端保留精度，客户端按统一规则格式化。
- 正剩余比例不保证能覆盖下一次调用的预算，准入接口决定是否允许执行。
- 额度不足、调用进行中、服务维护、频控、权限不足分别提示原因。
- 使用服务器时间校准倒计时，回到前台、完成记账和到期时刷新。
- 用户主动重试明确提示再次消耗额度。账号切换清除缓存，未记账调用继续属于原账号。

## 8. 接口与用量可信性

统一使用 `/api/v1/ai-production/` 的全新接口契约。客户端、服务端和管理后台同步接入新逻辑，移除旧次数协议及兼容分支。策略版本仅用于追踪费率和额度配置。

### 8.1 接口建议

- `GET quota/` 返回 server_time、policy_version 和两个窗口的 remaining_ratio、status、starts_at、reset_at，以及 pending_usage 状态。
- `POST tasks/` 创建制作上下文，保存输入摘要和所需场景，本接口不固定扣费。
- `POST tasks/{id}/calls/` 接收 call_id、category、model、input_digest、请求参数及 client_capabilities，执行准入并返回锁定的费率、窗口和许可。
- `POST tasks/{id}/calls/{call_id}/usage/` 接收供应商请求 ID、执行状态、usage 及用量来源，验证后计算积分并返回最新额度快照。
- `GET tasks/{id}/calls/{call_id}/` 用于恢复调用和记账状态。
- complete、pause、cancel 更新执行状态，暂停取消后仍允许原调用上传用量。

### 8.2 校验与幂等

- category、模型和场景由服务端配置校验，客户端不能指定价格或最终扣款数。
- 同账号同 call_id 同参数返回原记录，不重复授权或扣费；参数改变返回冲突。
- 每次供应商执行关联唯一请求 ID，重复流式尾帧、回调、客户端重发不累加消费。
- 使用账号行锁、事务和唯一约束，原子写入两个窗口和流水。记账事务失败允许同键重试。
- 客户端在发起模型请求前保存 call_id；响应丢失先查询原请求，避免把未知执行状态直接当新调用重试。
- SDK 自动重试必须接入调用计量或关闭其透明重试，防止实际重复执行漏记。

### 8.3 当前直连架构的限制

当前客户端直接请求模型。客户端上报 usage 可以支撑初期统计，但无法独立保证上报真实、完整，也无法可靠证明用户在授权后是否真正发出了请求。

建议优先使用服务端可查询的供应商用量作为凭据；若供应商支持则按 request ID 对账。缺少该能力时，直连上报阶段必须标记 client_reported，明确其可被篡改或漏报的限制。生产环境需要强约束时，采用服务端代发或可核验的调用网关，具体接入方式在供应商能力核实后确定。

授权后长期无上报按最低消耗记账属于估算兜底，可能包含客户端退出而未实际请求模型的情况。客户端恢复后补报、服务端对账和原流水差额纠正构成恢复路径。

## 9. 数据与管理后台

- ProductionPolicy 保存两个周期积分上限、按模型版本的计量模式、系数、最低消耗及调用预算限制。
- ProductionWindow 保存积分上限与已用积分，使用定点数。清除旧次数、预占次数和旧计量版本字段。
- ProductionTask 作为制作聚合，执行结果不控制是否扣费。
- 新增调用记录，保存 call_id、任务、分类、供应商、模型、request ID、费率快照、两个窗口、原始 usage、标准化 usage、计费积分、来源和估算标记。
- ProductionLedger 支持 charge 和 measurement_adjustment，记录唯一事件键与积分变化，可追溯原调用。
- 后台展示分类及模型用量、真实与估算消耗、待记账调用、超预算异常、用户双周期百分比及恢复时间。
- 保留人工重置窗口的权限、原因、请求幂等和审计。重置后旧调用仍写回旧窗口。
- 移除任务退款接口、退款按钮、退款权限及其调用方。用量纠错使用 measurement_adjustment，并保留原因和审计。

## 10. 全量替换与实施范围

### 10.1 已确认的实施方式

用户明确要求全量清除旧客户端、服务端额度逻辑，并让后台管理系统接入全新逻辑。采用客户端、API 和后台同步更新方式。

- 移除旧次数计量、任务预占、保留期限、成功结算、取消释放和失败返还流程。
- 移除旧接口契约、旧计费版本分支、旧客户端适配、双轨运行和历史任务兼容逻辑。
- 历史次数、额度窗口和未完成预占任务不转换为新积分记录。
- 新体系使用新的周期配置、模型费率、调用记录及用量账本。
- 数据库结构变更仍通过项目正常的 schema migration 工具执行；此处的全量替换指业务体系替换，不取消数据库结构管理。

### 10.2 客户端清理与接入

1. 清除 DiaryProductionService 中旧次数响应模型及预占、结算、释放 API。
2. 清除 DiaryAIWorkspace 中以制作任务成功与否控制额度的逻辑、24 小时预占维护、旧任务恢复和旧额度兼容字段。
3. 本地草稿读取时忽略废弃的额度记录，保留作品内容。需要发起模型调用时创建新调用记录。
4. 在文本和图片供应商请求入口接入调用准入、用量采集、上报、幂等及恢复。
5. 替换设置页和工作区额度 UI，统一展示双周期剩余百分比与恢复时间。
6. 删除旧价格文案、成功扣次提示、退次提示及废弃测试，更新为新规则的测试。

### 10.3 服务端清理与接入

1. 清除 ai_production 的旧 reserve、release、settle、refund 及过期预占回收路径。
2. 清除旧次数字段、hold_hours、reservation_id 和旧账本事件依赖，以新周期积分、模型调用与用量流水建模。
3. 重写额度查询和调用准入接口，接入按模型用量计算积分及估算纠正流程。
4. ai_runtime 的配置授权改为校验新调用记录、场景和许可，移除对旧 reserved 状态的依赖。
5. 原制作任务如仍承担作品结果或页面关联，保留对应业务职责，解除其与旧额度结算的耦合。
6. 删除旧额度专用管理命令、后台接口和测试。代码搜索确认无旧入口仍能发起调用或修改额度。

## 15. API 详细契约

### 15.1 通用约定

沿用项目响应包装 `{code, msg, data}`。成功 code=0，HTTP 状态与失败类别一致。错误 data 包含稳定的 error_key、retryable、blocked_windows、next_eligible_at 等结构化信息。

UUID 使用标准字符串；时间使用 UTC ISO 8601；积分和费率使用十进制定点字符串；remaining_ratio 为 0～1 的 JSON 数字。服务端计算金额，客户端仅格式化展示。

所有用户接口按登录账号隔离。列表统一 page、page_size，默认 25、最大 100，返回 items 和 pagination。错误数字码按现有全局注册规则分配，下表的 error_key 作为客户端判断依据。

| HTTP | error_key | 处理 |
| --- | --- | --- |
| 400 | INVALID_REQUEST | 修正参数 |
| 401/403 | AUTH_REQUIRED / ACCESS_DENIED | 登录或权益提示 |
| 404 | CALL_NOT_FOUND | 终止对不存在调用的恢复 |
| 409 | IDEMPOTENCY_CONFLICT | 同键不同参数，禁止重放 |
| 409 | CALL_IN_PROGRESS | 显示当前账号调用处理中 |
| 409 | VERSION_CONFLICT | 刷新后重新操作 |
| 429 | QUOTA_INSUFFICIENT | 显示不足窗口和恢复时间 |
| 429 | RATE_LIMITED | 使用 retry_after_seconds |
| 503 | SERVICE_UNAVAILABLE / PRICING_UNCONFIGURED | 显示服务状态 |

### 15.2 查询额度

`GET /api/v1/ai-production/quota/` 的 data 示例，数值仅用于说明字段：

```json
{
  "server_time": "2026-11-14T06:00:00Z",
  "policy_version": 12,
  "service_status": "available",
  "entitled": true,
  "pending_usage": false,
  "windows": [
    {"kind": "short", "status": "active", "remaining_ratio": 0.8,
     "starts_at": "2026-11-14T04:00:00Z", "reset_at": "2026-11-14T09:00:00Z", "duration_seconds": 18000},
    {"kind": "weekly", "status": "active", "remaining_ratio": 0.94,
     "starts_at": "2026-11-13T04:00:00Z", "reset_at": "2026-11-20T04:00:00Z", "duration_seconds": 604800}
  ]
}
```

无活跃周期 starts_at 和 reset_at 为 null。status 使用 not_started、active、awaiting_first_use。额度查询提供展示信息，具体调用能否执行由准入接口判断。

### 15.3 创建制作任务

`POST /api/v1/ai-production/tasks/`

请求含 attempt_key、input_digest、required_scenes、client_capabilities；响应含 task_id、state、created_at。该接口仅创建聚合任务。相同账号和 attempt_key 同参数返回同一任务。

### 15.4 申请模型调用

`POST /api/v1/ai-production/tasks/{task_id}/calls/`

```json
{
  "call_id": "11111111-1111-4111-8111-111111111111",
  "category": "text_ai",
  "scene": "diary.layout",
  "model_binding_id": "layout-default",
  "input_digest": "64位SHA256摘要",
  "parameters": {"max_output_tokens": 2048},
  "input_usage_estimate": {"input_tokens": 3200},
  "retry_of": null
}
```

input_usage_estimate 是客户端估算，服务端必须采用经模型适配验证的上界或可信输入计量，不能直接信任该数值做强额度保证。图片 parameters 包含数量、尺寸和质量，由服务端白名单校验。

响应包含 call_id、execution_state、accounting_state、pricing_version、authorized_at、authorization_expires_at、allowed_parameters、调用配置或其获取地址。许可绑定账号、call_id、模型、场景、参数摘要和时限。配置接口再次验证绑定关系。

### 15.5 上报用量

`POST /api/v1/ai-production/tasks/{task_id}/calls/{call_id}/usage/`

```json
{
  "event_id": "22222222-2222-4222-8222-222222222222",
  "provider_request_id": "provider-request-id",
  "execution_state": "completed",
  "usage": {"input_tokens": 3200, "cached_input_tokens": 1000, "output_tokens": 800},
  "raw_usage": {},
  "finished_at": "2026-11-14T06:01:20Z"
}
```

- usage 可为空，表示尚未取得用量。该上报更新执行状态，用量等待截止后走估算流程。
- 普通客户端不能自行指定 trusted 来源、积分和费率。来源由服务端接收渠道与校验结果确定。
- 所有 token、张数字段非负并设置合理上限。raw_usage 只允许供应商计量字段，禁止附带密钥或完整请求正文。
- 同 event_id 同内容幂等，同 event_id 不同内容返回冲突。供应商对账修正通过独立可信入口写入。
- 响应包含 call_id、accounting_state、estimated、quota。精确积分在管理接口提供。

### 15.6 状态查询与后台处理

`GET /api/v1/ai-production/tasks/{task_id}/calls/{call_id}/` 返回执行状态、记账状态、截止时间和最近错误。模型是否可重新执行取决于调用状态，重复查询不会重新发放新的执行许可。

服务端定时任务扫描超过 usage_due_at 的 pending 调用，按最低消耗入账并解除账号阻塞。扫描需幂等，进程重启可继续处理。可信对账到达后计算新总额与已记总额的差值，写 measurement_adjustment。

## 16. 数据模型、约束与事务

以下为目标模型，类名可按项目命名规范微调，字段语义应保持一致。

| 模型 | 主要字段 | 约束与用途 |
| --- | --- | --- |
| ProductionPolicy | id、name、short_limit_points、weekly_limit_points、effective_at、enabled、publish_key、reason、actor、created_at | publish_key 唯一，发布后不可原地修改 |
| ModelRate | id、policy_id、provider、model、category、metering_mode、input_rate、cached_input_rate、output_rate、image_rates、minimum_charge、max_output_tokens、usage_timeout_seconds | 同策略模型和规格唯一，所有费率非负，单位明确 |
| ProductionWindow | id、account_id、kind、starts_at、ends_at、limit_points、used_points、policy_id | account/kind/starts_at 唯一，按 account/kind/ends_at 建索引 |
| ProductionTask | id、account_id、attempt_key、input_digest、state、created_at、updated_at | account/attempt_key 唯一，仅聚合制作 |
| ProductionCall | id、account_id、task_id、category、scene、model_rate_id、rate_snapshot、input_digest、parameters_digest、short_window_id、weekly_window_id、execution_state、accounting_state、authorized_at、authorization_expires_at、usage_due_at、provider_request_id、raw_usage、normalized_usage、charged_points、estimated、usage_source、retry_of | call_id 唯一，任务和调用账号必须一致 |
| ProductionLedger | id、call_id、event_id、event、delta_points、resulting_charge_points、short_window_id、weekly_window_id、reason、actor、created_at | event_id 唯一，每调用一笔 charge，调整可有多笔 |
| ProductionUsageEvent | id、call_id、event_id、payload_digest、source、received_at | event_id 唯一，用于拒绝内容变化和处理重发 |
| ProductionQuotaReset | id、account_id、scope、request_key、reason、actor、window_snapshot、created_at | request_key 唯一，记录重置前窗口 |
| ProductionControl | id、accepting、version、reason、updated_at | 全局控制，乐观锁 version |

积分建议 Decimal(24,6)，费率建议 Decimal(24,12)。单调用汇总计算后统一四舍五入至六位，禁止各 token 分项先按整数取整。measurement_adjustment 可为负数，窗口累计 used_points 保持非负。

调用执行状态使用 authorized、running、completed、failed、cancelled、unknown；记账状态使用 pending、estimated、actual。两组状态独立，例如 failed + actual 合法。客户端不能将 estimated 改成 actual，必须经过服务端校验。

### 16.1 事务边界

- 准入事务锁账号，校验无 pending 调用，再检查预算、创建窗口和调用记录。外部网络请求放在事务之外。
- 记账事务按账号、调用、窗口的固定顺序加锁，插入唯一事件、更新调用累计费用、两个窗口 used_points 和流水，整体提交。
- 估算纠正按「可信新累计费用减去当前累计费用」计算差额，纠正与首次记账竞争时使用同一套锁。
- reset 与准入、记账同样先锁账号，结束所选当前窗口，保留旧调用外键。
- 对账失败不能修改已确认费用；保留待处理状态及错误供后台重试。
- 数据库保护调用、策略和流水外键，业务记录不得通过后台删除以修改余额。

- 有供应商查询能力时提供「重新核对用量」。成功显示差额，失败保留原费用并显示原因。

### 17.5 用量纠错与审计

纠错页默认筛选估算或核对失败的调用。管理员通过供应商记录核对并提交原始用量及证据编号，系统计算差额，不允许直接输入任意余额。

提交前展示旧积分、新积分、差额、归属窗口、原因；过期窗口的更正明确标注「更新历史周期」。提交使用 request_key 和调用 version，冲突后要求刷新。所有纠错写审计。

审计页提供操作者、用户、动作和日期筛选，展示策略发布、控制开关、额度重置及计量更正的前后信息。沿用现有审计系统，避免重复存储完整敏感请求。

### 17.6 管理接口与权限

统一前缀 `/api/admin/v1/ai-production/`。

## 18. 三端联调验收场景

1. 后台发布模型费率和双周期上限，客户端查询百分比，首次文本调用建立窗口；调用使用的费率版本与后台一致。
2. 文本完成上报 usage，客户端比例下降，后台可见原始用量、计算结果和唯一消费流水。
3. 图片失败且返回用量，仍正确消费；无用量时到期估算，客户端显示更新后的比例。
4. 可信对账纠正估算，两个原窗口按差额更新，后台可追溯更正，重复核对不重复记账。
5. 两设备同时申请，只有一笔获准，另一设备收到明确的进行中状态；前一笔记账后可继续。
6. 后台重置窗口或发布新费率时仍有调用执行，旧调用按原窗口、原费率入账，新调用按新配置执行。
7. 客户端断网、取消、杀进程再启动，待上报事件可恢复，同一次供应商调用始终只形成一笔消费。
8. 后台发布、重置、更正的重复点击、响应丢失和版本冲突均可恢复，权限拒绝不产生部分变更。
9. 大字体、深色模式、小屏幕、VoiceOver 及后台空列表、错误、分页状态均可正常操作。

本次补充为需求与设计交付，供应商 usage 能力、具体费率、超时和预算参数仍需实施时核实，尚未修改业务实现。


## 19. 实施记录与启用条件

- 当前实现继续使用客户端直连火山方舟，账本标记客户端上报、超时估算和人工核对。供应商用量自动查询和可信调用网关仍待实现。
- 文本取 Responses 的输入、输出及缓存 token。Seedream 支持按生成张数计量，也可配置按响应的输出 token 计量。图像 API 缺少输入 token 时按零处理。参考 [Responses 缓存字段](https://console.volcengine.com/ark/region%3Acn-beijing/docs/context-cache) 与 [图片生成用量字段](https://docs.volcengine.com/docs/ark/image-generation-api?lang=en)。
- 同一工作区的模型请求在客户端排队，服务端每账号允许一笔待记账调用。收到明确失败且没有有效用量时立即按最低消耗记账，状态未知时由 Celery 定时处理。补报真实用量时通过差额修正。
- 额度字段和旧流水通过数据库结构变更全量清理。已经完成的印刷活动凭据只保留成果完成时间，不转换旧额度。
- 上线需同步发布 SparkService、Celery worker 和 beat、后台与 iOS。后台按运行配置中的模型标识发布费率和双周期积分上限，再验证四个制作场景。上限与费率由运营配置，代码无生产默认值。
