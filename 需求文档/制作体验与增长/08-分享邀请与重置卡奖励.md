# 分享邀请与重置卡奖励需求方案

日期：2026-11-15  
状态：设计方案，尚未实现；已确认 public-web + public_experience 统一架构，商业候选参数仍需确定。  
关联：[制作额度与奖励通知](./04-制作额度与奖励通知.md) · [Pro 会员与 AI 制作额度](./07-Pro会员与AI制作额度.md) · [实体装订与优惠活动](./05-实体装订与优惠活动.md)

## 1. 核心目标与范围

建立“客户端分享海报 → 好友扫码 → Web 登记联系方式 → App Store 下载 → App 验证登录或绑定 → 有效邀请 → 后台发奖 → 客户端使用奖励”的完整链路。

本方案的邀请成功条件取代之前讨论的“首次 AI 制作消耗”：不要求好友制作、付费或购买 Pro。

### 1.1 用户已明确的规则

1. 客户端生成包含二维码与分享内容的分享图片。
2. 扫码打开 Web，填写手机号或邮箱，提交成功后跳转苹果 App Store 下载。
3. 好友使用登记手机号在 App 登录或绑定成功，计为邀请成功；邮箱验证绑定成功同样有效。
4. 后台能够查看分享、邀请人数并发放奖励。
5. 引入有有效期的制作额度重置卡。Pro 使用时重置 5 小时和 7 天额度；免费用户使用时重置 7 天额度。
6. 邀请满 5 人奖励半价装订，满 10 人奖励免费装订；复用现有实体书优惠活动和印制优惠券体系。

### 1.2 本文推荐但尚未确定的商业规则

- 新用户拉新：登记前未关联正式 App 账号，最终转正后的账号未参加过邀请奖励。已有账号补绑另一联系方式默认不新增有效邀请。
- Web 增加手机号／邮箱验证码验证后再跳转，避免他人冒填抢占邀请归属。若坚持只填不验证，登记只能作为弱线索，不能据此永久占用联系方式或自动确定唯一邀请人。
- 邀请归属保留 7 天，活动结束前完成 App 验证才计入本期。
- 每有效邀请 1 人发 1 张重置卡、每活动最多 10 张、到账后 30 天到期。这是首期候选值，后台发布前必须明确。
- 5 人、10 人两个里程碑分别发一张券，每活动各一次；达到 10 人共得半价券 1 张和免费券 1 张，不自动作废已发半价券。
- 重置卡与装订奖励可同时获得；同一印制订单仅选一张优惠券，不叠加。
- 装订奖励限定标准规格、页数、数量及抵扣上限；建议运费、超页、升级规格单独支付，必须在宣传和下单前说明。

不将 12 月 13 日 06:09 写成固定有效期；这是展示样例，实际由每张卡 expires_at 决定。

本次不采用额外积分奖励池。奖励通过重置卡恢复现有周期额度；内部仍按积分计费，客户端继续显示百分比。

所有邀请页面、身份匹配和奖励 API 均接入 https://diary.dreamwhale.top，生产链路不转发到本地。

## 3. 整体流程与状态

```text
邀请人登录 → 进入邀请有礼 → 生成海报和分享文案
→ 好友扫码访问公开落地页
→ 填写手机号／邮箱 → 推荐完成验证码验证
→ 服务端保存邀请登记 → 跳转官方 App Store 产品页
→ 下载并打开 App → 用相同手机号验证登录／绑定，或验证绑定邮箱
→ 服务端匹配登记并核验唯一性 → 有效邀请 +1
→ 生成奖励资格 → 后台发放（可配置自动发放）
→ 重置卡进入“我的奖励”，印制券进入“我的印制优惠券”
→ 使用卡恢复额度／下单时选券抵扣
```

登记状态：待验证 → 待 App 激活 → 邀请成功；分支为已过期、无资格、重复账号、异常待核验。

奖励状态：已达标待发放 → 发放中 → 已到账；失败可重试，异常可暂停。资格与发奖分开，不因发奖失败回滚有效邀请人数。

分享按钮点击、调用系统分享、海报保存、扫码访问、填写表单均不能直接算邀请成功。

## 4. 客户端核心功能

### 4.1 邀请有礼页面

入口：个人中心、制作额度面板、额度不足弹窗、作品导出完成页。不会因额度不足自动弹起分享或强制分享。

```text
邀请好友，一起收藏旅途
已成功邀请 3 人

邀请 5 人：标准装订半价券     3 / 5
邀请 10 人：标准装订免费券    3 / 10
制作额度重置卡：查看本期规则

[生成邀请海报]  [复制邀请文案]
[邀请记录]      [我的奖励]
```

显示活动截止时间、有效邀请定义、装订适用范围、奖励期限、是否需要后台发放和剩余名额。活动暂停或名额用完时，不能继续展示无条件领券承诺。

### 4.2 海报与分享内容

海报包含品牌名称、邀请主题、可选作品封面、二维码、简短步骤、活动关键限制和活动标识。文案建议：“扫码登记并下载，使用同一手机号或邮箱完成登录／绑定，一起解锁邀请好礼。”

二维码内容为 HTTPS 落地页 `/invite/{opaque_token}`，不含手机号、邮箱、登录 token 或直接可枚举的用户 ID。服务端签发不可猜测的邀请标识，绑定邀请人及活动版本。

客户端本地合成海报，二维码由邀请 URL 生成；必要时提供服务端静态海报模板。不因分享自动上传整个手帐。使用作品封面前让用户预览、选择替换或关闭。

提供保存图片、系统分享和复制文案；二维码保留白边和高对比度，导出后通过实际扫码验收。分享取消不显示“邀请成功”。

### 4.3 登录／绑定与邀请结果

保持现有手机号登录、绑定手机号、绑定邮箱流程。邀请匹配由服务端在身份验证事务提交后触发，客户端不能提交“已邀请成功”布尔值。

Web 无需把 App 登录凭证传给客户端，依靠经验证的联系方式在服务端关联，所以无需依赖安装后保留深链参数。仅在 App 内已验证相同联系方式时完成归因。

邮箱登记用户用 Apple 登录但未绑定相同邮箱时，不算邀请成功；提示在账号设置验证绑定登记邮箱。Apple 隐藏邮箱不能自动等同登记邮箱。

好友可看到“邀请已确认／未找到有效邀请／登记已过期”。邀请人列表只展示昵称或脱敏联系方式及状态，不暴露完整联系方式。

### 4.4 我的奖励与重置卡 UI

奖励分为“制作重置卡”和“印制优惠券”，使用入口分别进入额度确认页、印制下单页。

Pro 卡片：

```text
制作额度重置卡
完全重置（7 天 + 5 小时）
使用后，两项制作额度恢复至 100%
将于 12 月 13 日 GMT+8 06:09 到期
[使用重置卡]
```

免费用户卡片：显示“重置 7 天制作额度”，不展示已获得 Pro 双周期权益。帮助说明该卡按使用时等级生效，升级不消耗卡、也不改变卡到期时间。

确认弹窗展示当前等级、两项或单项使用前／后百分比、卡片期限，明确“立即消耗 1 张，恢复后下次 AI 调用开始新周期”。点击确认后使用幂等请求，成功刷新额度与卡列表。

有未记账调用、会员状态未知、卡已过期时禁止使用；额度均为 100% 时不消耗卡。请求超时先查询使用结果，不立即用新请求号再扣一张。

## 5. Web 落地页

页面展示活动名称、品牌、邀请说明、手机号／邮箱切换、隐私说明、表单、验证码（推荐）和“确认并前往 App Store”按钮。

手机号做国家／地区与规范化处理，邮箱按账号模块规则规范化，不能随意移除邮箱中的点号或加号后缀。发送与验证验证码复用现有能力，增加公开接口限频和尝试次数限制。

在联系方式提交并验证成功后，先持久化登记，再跳转后台配置的官方 App Store 产品 URL。URL 必须是审核通过的 apps.apple.com 产品地址，不能接受访问者传入任意跳转地址。当前文档不臆造 App Store ID，上线前核对真实商品页。

自动跳转受阻时显示“登记成功”与“打开 App Store”按钮；明确要求后续使用同一联系方式登录／绑定。非 iOS 浏览器显示 iPhone 下载说明及链接，不跳到无关安装包。

活动失效、邀请人失效、名额不足时展示真实状态。登记数据仅用于邀请归因和通知，不默认勾选营销同意。配置数据保留期限，过期未激活记录按规则清理。

## 6. 有效邀请与防重复规则

唯一计数主体是最终 App 账号，不是手机号、邮箱或设备数量。同一人手机号和邮箱都验证，只计一人；同一好友重复登录、解绑再绑定、换设备、重复提交都不增加人数。

推荐每个受邀账号全局只能成为一次“新用户邀请”；邀请人可参加后续不同活动，但旧受邀人不能反复贡献人数。若要支持老用户召回，另建活动类型，不混入本期新用户奖励。

同一已验证联系方式多次登记，推荐采用仍在有效期内的首次已验证归属，不被后来的扫码静默覆盖。联系方式对应账号已存在、本人邀请本人、已参与过邀请奖励时，返回中性状态，不向匿名访问者泄漏账号详情。

多个联系方式最终合并到同一账号时，使用账号锁和唯一约束只确认一条；已重复确认的数据进入审计纠错，奖励已使用的情况不能直接扣成负余额或撤销已履约实体订单。

同 IP 作为异常信号而非唯一拒绝依据，避免家庭网络误伤。活动设账号发奖上限、总量／预算、验证码限频与异常审核；首期不做多级返利。

## 7. 重置卡服务端设计

### 7.1 资产与状态

新增 ProductionResetCard：id、owner、source_grant、grant_key（唯一）、issued_at、expires_at、status、used_at、used_reset_id、revoked_at、reason。

状态：可用、已使用、已过期、已撤销。过期判断以服务端时间为准，不依赖定时任务及时刷新状态。

重置卡不属于 RevenueCat 钱包，不发钻石，不直接改变会员等级，不能转赠或兑换现金。奖励拥有者绑定项目账号。

### 7.2 重置含义

采用现有 reset_quota 的语义：结束当前启用周期、保留原周期及消耗流水；下一次调用创建新的完整周期。使用卡后立即显示 100%，但不是把原调用记录删除或把所有历史 used_points 清零。

- 当前有效 Pro：结束当前 5 小时和 7 天周期。
- 当前免费：仅结束当前 7 天周期，停用的历史短周期不处理。
- 等级以使用时服务端验证结果为准。确认页到提交期间等级变化，返回冲突要求刷新，不悄悄改变重置范围。
- Pro 其中一项有消耗即可使用，效果是完整重置两个启用周期；全部无消耗则不使用。
- 有未结算调用先按原规则处理；仍 pending 时拒绝用卡，避免跨周期结算错账。

### 7.3 原子使用流程

验证登录 → 锁账号 → 查幂等使用记录 → 锁卡 → 验证所有权、有效期和状态 → 核实会员等级 → 核实待结算调用和可恢复额度 → 调用重置核心 → 标记卡已用并关联重置记录 → 同一数据库事务提交。

账户锁与授权调用保持一致顺序。任何步骤失败都不消耗卡；同一请求重试返回原成功结果；不同卡并发使用时，第一张恢复完成后第二张因已满额度拒绝。

现有 reset_quota 主要服务后台人工操作，需要提取共用重置核心／新增来源字段，将用户用卡与管理员重置明确区分。不要让客户端获得后台重置接口权限。重置卡用户权限、后台补发权限、撤销权限分别校验。

现有故障处理与计费规则保持不变：已经获得授权的调用按实际用量或既有估算计费，失败也扣；用卡不退还已消费金额。

## 8. 装订奖励与现有活动融合

### 8.1 邀请与实体书活动的分工

邀请活动负责海报、归因、有效邀请计数和里程碑资格；PrintCampaign 增加 invitation 来源，配置具体产品、页数、金额上限、名额和券有效期；PrintCoupon 承载用户实际可使用的券。

建立邀请活动与实体书活动的明确关联，并保存发布版本。制作达标活动、年费首购活动继续按原逻辑运行；在“实体书优惠活动”中并列展示来源，不把邀请人数转换成制作页数。

### 8.2 5 人／10 人奖励

推荐两个独立奖励规则：5 人 → percent=50；10 人 → percent=100。唯一发放键示例 `invite:{campaign_id}:{owner_id}:milestone:5` 和 `...:10`。

达到 10 人时检查并补齐所有已达标但未发放的里程碑。后台重复点发放、任务重跑不会重复生成优惠券。每条奖励发放记录关联实际 PrintCoupon ID。

如最终选择“5 人半价券升级为 10 人免费券”，需另行确定半价券已使用／已锁单时的补差权益；不能静默采用当前已用券不升级的行为。本方案默认推荐分别发券，前端明确两档可分别获得。

### 8.3 免费与半价的适用范围

复用 coupons.coupon_amount 的现有计算：对指定基础费用及包含页数按 50%／100% 抵扣，并受 cap_fen 上限约束。若上限不足覆盖标准规格，就只能叫“最高抵扣券”，不能叫“免费装订”。

活动发布必须指定标准产品、包含页数、单券册数、抵扣上限、运费承担、超页价、升级规格差额和有效期。建议一券一订单一册；以实际报价和券快照为准。

邀请券与现有制作达标券、年费券可以同时持有，同一订单不叠加。复用现有可用券筛选、订单锁券、支付、取消／退款和履约流程；实施时必须专项验证取消／支付超时释放、退款后的券处理及 0 元订单流程，不假定已有每个分支都符合新活动。

免费产品现有计算返回 0 优惠，不能再消耗一张邀请券；无实际优惠时提示并保留券。

## 9. 服务端核心数据与接口

### 9.1 数据模型

| 对象 | 核心字段与约束 |
| --- | --- |
| InvitationCampaign | 活动状态、期限、归因有效天数、规则版本、App Store URL、关联印制活动、名额与预算、自动／人工发放 |
| InvitationLink | 邀请人、活动、不可猜测 token、模板版本、状态 |
| InvitationRegistration | 方式、联系方式匹配摘要／受保护值、验证时间、邀请关系、过期时间、状态 |
| InvitationConversion | 受邀最终账号、邀请人、活动、验证身份来源、成功时间；受邀账号唯一约束 |
| RewardRule | 资格阈值、奖励类型、卡有效期／券模板、发放数量、发放上限、发布版本 |
| RewardGrant | 受益人、资格证据、规则快照、唯一 grant_key、状态、实际卡／券引用、审核人与原因 |
| ProductionResetCard | 见第 7 节，关联使用后的 ProductionQuotaReset |
| InvitationAudit | 规则发布、人工发奖、撤销、归因纠错、操作者、前后状态、时间 |

联系方式不得写入普通日志或二维码。用于跨端匹配的摘要采用带服务端密钥的 HMAC，而不是可被枚举的普通手机号哈希；展示和必要保留采用既有安全机制，后台默认脱敏。

### 9.2 API 建议

| 使用方 | 接口 | 用途 |
| --- | --- | --- |
| App | GET /api/v1/experience/invitations/me/ | 当前活动、邀请链接、有效人数、里程碑及奖励状态 |
| App | GET /api/v1/experience/invitations/records/ | 分页邀请记录，脱敏 |
| Web | GET /api/public/v1/invitations/{token}/ | 公开活动、有效性、下载入口 |
| Web | POST /api/public/v1/invitations/{token}/verification/ | 发送受限流的验证请求 |
| Web | POST /api/public/v1/invitations/{token}/registrations/ | 验证并登记，返回可信下载 URL |
| App | GET /api/v1/experience/rewards/ | 卡与券摘要、到账记录 |
| App | POST /api/v1/ai-production/reset-cards/{id}/preview/ | 当前等级、重置范围、前后额度及阻塞原因，不消耗 |
| App | POST /api/v1/ai-production/reset-cards/{id}/use/ | 幂等用卡，校验预期等级，返回卡与额度结果 |
| 后台 | 活动、统计、资格审核、发放、审计 API | 独立 RBAC，复用后台框架 |

邀请确认没有客户端开放的“成功”接口，由账号登录／绑定成功后的服务端业务事件触发。可靠事件或补偿任务保证事务提交后即使处理暂时失败也能补计。

预览不能作为最终权限依据；卡、会员状态、余额、活动名额在写事务重新校验。发奖先记录资格和唯一键，资产创建与到账状态同事务提交，通知通过提交后事件投递。

## 10. 后台管理系统

### 10.1 活动配置

入口建议“增长活动 → 分享邀请”。编辑草稿 → 预览海报与落地页 → 检查规则／规格／额度 → 发布。配置邀请成功条件、归因期限、重置卡数量和有效期、5/10 人印制奖励、总名额／预算、人工或自动发放。

规则发布保存版本。调整只影响新参与者或新发布活动，不追溯降低已承诺奖励。活动结束停止新登记，已达标未发放奖励仍可处理。

### 10.2 统计与记录

分别展示：海报生成用户数、分享操作次数、扫码访问／去重访客估计、登记人数、完成 App 验证的有效邀请人数、异常人数、奖励待发／已发数量、卡使用次数、券核销和实际补贴成本。

扫码独立访客不等于真实人数；浏览器 Cookie 只能估计去重。系统分享操作不宣称真实公开发布人数。

邀请人详情可查看漏斗、受邀人脱敏记录、有效人数、各里程碑状态、已发卡券、用卡及印制订单关联。搜索与导出受权限控制，敏感查看留审计。

### 10.3 发放交互

列表筛选“已达标待发放” → 勾选用户 → 显示预计卡／券数量、奖励模板和补贴范围 → 填写原因并确认 → 返回逐条结果。

服务端重新验证资格、库存和唯一键。资格不满足不能混在常规发放中绕过；运营特殊补赠使用单独权限及理由，不篡改有效邀请人数。

重试只补失败项；撤销仅针对未使用资产，已锁券／已用卡／已履约订单进入人工处理。暂停活动不自动没收已发资产。

配置人工发放时，客户端明确显示“已达标，待发放”，不能展示“已到账”。可后续启用自动发放，复用同一发奖服务。

名额控制不能等用户邀请到 10 人才临时告知无奖。推荐活动参与时锁定对应里程碑名额，设参与截止／达标截止并释放未达标名额；后台发布时按两档累计成本预留预算。规则确定前不对外发布无限量承诺。

## 11. 通知与异常处理

- 有效邀请成功：更新邀请人进度，站内可查看；与到账通知可合并，减少重复推送。
- 卡／券真实到账后发送奖励通知，点开对应资产。
- 到期提醒可选，默认站内展示，推送遵循现有通知偏好。
- 通知失败可重试，不能触发重复发奖。
- 登记成功但下载失败：允许再次打开可信下载链接，不新增一条邀请。
- App 验证已成功但计数暂时失败：可靠事件补偿；用户看到处理中，后台可重试。
- 会员验证异常：保留卡，重试确认，不能降级按免费额度强行使用。
- 活动和重置卡时间由服务端 UTC 保存，客户端本地化；样例按 GMT+8 展示，可包含年份避免跨年歧义。

## 12. 核心验收

1. 海报二维码在实际导出图片、聊天压缩后可扫描，链接不含隐私和认证凭证。
2. 手机和邮箱各完成一次扫码、登记、下载、登录／绑定闭环；只登记不计成功。
3. 同账号绑定手机和邮箱、重试、换设备、账号合并均不重复计人或发奖。
4. 第 5 人只触发一次半价资格，第 10 人只触发一次免费资格，批量发放重试不重复建券。
5. 免费卡只恢复 7 天；Pro 卡恢复两项；跨等级确认冲突能提示刷新。
6. 卡过期、撤销、并发使用、已满额度、pending 调用和网络重试均不误扣卡。
7. 使用卡保留历史调用与审计，下一次授权开启新周期；历史实际消耗用户仍在后台列表可查。
8. 印制券对规格、页数、上限、运费与宣传一致；取消、退款、锁券、0 元订单端到端验证。
9. 活动名额与发奖预算并发安全，后台发放／补发／撤销均有独立权限和审计。
10. 全链路使用线上服务，测试活动与真实发货奖励隔离；不得因沙盒会员测试自动产生真实免费印制履约。

## 16. Web 登记与账号事件衔接细节

### 16.1 页面状态与公开接口契约

落地页状态：加载中、可登记、发送验证码中、验证码已发、验证提交中、登记成功待跳转、活动结束、名额已满、链接失效、请求失败。错误后保留当前输入但不写入 URL；验证码和联系方式不进入分析埋点。

GET 落地页信息返回 title、poster_template_version、rules_summary、ends_at、availability、contact_methods、download_url；不返回奖励内部成本、邀请人完整资料或密钥。

发送验证返回 challenge_id、retry_after_seconds、expires_at。登记提交 token、challenge_id、code、contact_type、contact_value 及幂等键；服务器重新校验联系方式与 challenge 绑定，不接受前端声称“已验证”。成功返回 registration_id、status=awaiting_app、attribution_expires_at、download_url。

推荐验证码验证仅证明登记联系方式，不创建正式 App 用户、不签发 App 登录 token、不计有效邀请。这样避免 Web 登记提前创建账号后被“已有账号不得参与”规则错误排除。

现有 accounts/urls.py 已有 Web 手机 OTP、手机／邮箱 OTP、身份验证及绑定入口。应复用其底层验证码发送／核验、限频和规范化服务；先核查业务副作用，不能直接套用会创建用户或登录的 Web verify 接口作为邀请登记接口。邀请验证码使用独立 purpose=invitation_registration，不能拿来登录／重置密码，也不能复用登录 OTP 绕过登记校验。

### 16.2 App 身份确认事件

账号模块在真正完成手机号登录或手机号／邮箱绑定后，事务内写入可靠业务事件：event_id、canonical_account_id、verified_identity_id、provider、verified_at、source_flow。只接入 App 认证／绑定路径；邀请 Web challenge 验证不能触发成功事件。

public_experience 消费事件：读取账号规范身份 → 查未过期、已验证登记 → 检查自邀、活动、账号资格和归属 → 锁最终账号 → 插入唯一 Conversion → 更新进度 → 创建符合门槛的 RewardGrant → 提交后通知。事件重复消费是无操作，事件失败保留待处理状态供任务补偿。

每个账号全局一次邀请的约束需通过数据库唯一键落实，不依赖请求前 count。手机号和邮箱分别登记到不同邀请人时，采用最早有效验证登记作为候选，最终只生成一条归属；冲突与人工更正有审计。

绑定和账号合并成功应使用归并后的账号 ID，并核查双方已有 Conversion。若已有两条历史确认，进入异常处理，不自动重新发放奖励。不得通过手机号字符串直接推断账号归属或绕过 accounts 的验证绑定流程。

## 17. 重置卡与奖励事务落地

### 17.1 发放事务

常规发放以 RewardGrant 为入口，管理员和自动任务调用同一服务：锁资格 → 检查规则版本、计数证据、活动预留名额 → 确认 grant_key 未成功 → 创建实际卡或印制券 → 写资产引用与发放审计 → 标记 issued → 提交后投递到账通知。

一次批量发放逐条独立提交并返回结果，个别失败不重复发放成功项。唯一约束冲突读取已存在资产并核对 owner、规则、来源；发现不一致报警，不把任意相同 key 当成功。

新增奖励来源关联字段时使用 nullable 字段扩展既有券，旧制作达标、年费活动来源保留原样；对外显示“邀请奖励”，后台可跳到邀请资格证据。

### 17.2 用卡接口结果

预览返回 card_status、expires_at、plan、scope、before_windows、after_windows、can_use、blocked_reason、server_time。after_windows 为展示预测，不代表已经重置。

使用成功返回 use_id、card_status=used、reset_id、plan、scope、quota。错误用稳定业务码区分 CARD_EXPIRED、CARD_ALREADY_USED、QUOTA_ALREADY_FULL、CALL_IN_PROGRESS、PLAN_CHANGED、MEMBERSHIP_UNAVAILABLE，客户端映射中文说明。

当前 reset_quota 已具备账号锁、幂等、会员校验、pending 调用校验和结束旧周期能力；需补全部额度已满判断、卡所有权和卡消费、重置来源及授权边界。数据库操作同事务，外部会员刷新放在事务外准备，在事务内验证有效快照与等级，避免长时间持锁访问 RevenueCat。

重置审计保存卡 ID、规则版本、原窗口快照、新周期启动语义、使用前等级和请求 ID。授权调用与用卡使用统一账号锁，禁止一边授权一边重置造成跨窗口漏扣。

发放页默认筛选已达标待发，显示“将发重置卡 N 张、半价券 N 张、免费券 N 张”；确认提交再次核对规则版本，版本冲突要求刷新。自动发放开关仅影响发放方式，不改变资格；切换后可显式补发历史待发项，需提供影响预览。

现有 /print-campaigns/configure、/print-campaigns/participants 增加邀请来源筛选和详情跳转；邀请活动不出现页数上传／页数审核按钮。/print-coupons 展示邀请来源与对应人数门槛，仍使用现有券核销状态。

## 19. 印制订单接入与核销细节

客户端继续使用 /api/v1/print/coupons/mine/ 获取邀请券；现有 quotes、订单创建和优惠快照接入新来源，不另建邀请专属下单流程。订单保存券 ID、来源、折扣比例、包含页数、上限和实际抵扣额快照，后续活动编辑不改旧订单价格。

同一张券并发创建订单必须锁券并验证 order 为空；已关联待支付订单显示“使用中”，不作为可用券返回。免费券抵扣后仍有运费／加页差额则正常支付；应付为 0 时走既有 not_required 分支，不伪造支付成功交易。

已核对 services.release_cancelled_coupon：仅 cancelled 且支付状态 unpaid / not_required / refunded、无活跃支付尝试、无 start 生产事件时释放券。邀请券没有 PrintEnrollment 也应正常解除 order 关联；该方法后续页数达标升级分支只适用于原页数活动，不触发邀请券升级。

取消退款未完成前不提前释放；已开工订单通过售后处理。释放时不延长券原有效期；如因履约故障需要补偿，由后台单独补发并审计。实施验收覆盖取消后支付迟到回调、重复退款通知、同时用券、0 元订单和已开工取消。

活动发布时锁定标准产品与赠送范围。券按现有动态产品报价计算，后续产品涨价可能使 cap_fen 不足：发布承诺的有效期内应保持对应标准规格价格／履约范围，或通过受审计的补贴调整保证兑现；不能静默把已承诺免费改成部分抵扣。
